## 1. 源代码风格规范

### 1.1 字符编码与换行符

| 规则 | 要求 |
|------|------|
| 字符编码 | 所有源文件必须使用 **UTF-8** 编码 |
| 换行符 | **Unix 换行符（LF）**，禁止使用 Windows 换行符（CRLF） |
| BOM 文件头 | 禁止（UTF-8 无 BOM） |
| 文件末尾 | 必须保留一个空行（trailing newline） |

### 1.2 缩进与空格

| 规则 | 要求 |
|------|------|
| 缩进单位 | 4 个空格，**禁止使用 Tab 字符（\\t）** |
| 最大行宽 | 120 字符。超过时必须换行，续行缩进 8 字符（相对于首行） |
| 禁止尾部空白 | 行尾不得包含任何空白字符（space / tab） |

### 1.3 大括号风格

采用 **K&R 风格（左大括号不换行）**，与 Google Java Style 一致：

```java
// ✅ 正确
if (condition) {
    doSomething();
} else {
    doOther();
}

// ❌ 错误 — 左大括号换行
if (condition)
{
    doSomething();
}
```

**空块可写成 `{}`**（不需要换行），但 `if (cond) ;` 形式的空语句块**禁止**。

### 1.4 空行规则

| 位置 | 规则 |
|------|------|
| 类/接口的第一个成员前 | **不加**空行 |
| 类/接口的最后一个成员后 | **不加**空行（直接 `}`） |
| 方法与方法之间 | **必须**以空行分隔 |
| 同一方法内的逻辑段 | 可用单一空行分隔，但**禁止连续多个空行** |

### 1.5 源文件结构顺序

```java
package 声明

import 声明              // 按 3.1 节规则排序

/**
 * 类 Javadoc 注释
 */
public class Example {
    
    // 1. static final 常量
    // 2. static 变量
    // 3. 实例变量
    // 4. 构造方法
    // 5. 静态方法
    // 6. 实例方法（按可见性 / 功能分组）
    // 7. 重写方法（@Override 集中放）
    // 8. 内部类 / 接口
}
```

## 2. 命名规范

### 2.1 命名总则

| 规则 | 要求 |
|------|------|
| 字符集 | ASCII 字母、数字、下划线；禁止中文拼音混合、禁止拼音首字母缩写 |
| 命名风格 | 严格遵循驼峰命名，禁止下划线命名（常量除外） |
| 自解释性 | 命名必须"见名知意"，禁止 `a`、`b`、`tmp`、`data` 等无意义命名 |
| 正词法 | 避免否定命名（`isNotEnabled` → 重构逻辑方向）；布尔变量使用 `has`/`is`/`can` 前缀 |
| 分布式 ID | 字段名统一使用 `id`，禁止使用 `uid`、`userId` 混用 |

### 2.2 各元素命名规则

| 元素 | 规范 | 示例 |
|------|------|------|
| 类名 | UpperCamelCase，名词或名词短语 | `UserService`、`OrderDTO` |
| 方法名 | lowerCamelCase，动词或动宾短语 | `findUserById()`、`save()` |
| 变量名 | lowerCamelCase | `userName`、`orderList` |
| 常量名 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT`、`DEFAULT_TIMEOUT` |
| 包名 | 全小写，点分隔，单数形式 | `com.njydsz.common.util` |
| 异常类 | 以 `Exception` 结尾 | `BusinessException` |
| 抽象类 | 以 `Abstract` 或 `Base` 开头 | `AbstractEntity`、`BaseResponse` |
| 接口 | 形容词/名词，不加 `I` 前缀 | `Serializable`、`UserService` |
| 测试类 | 以 `Test` 结尾 | `UserServiceTest` |
| 测试方法 | `test_被测场景_期望行为` | `test_findUserById_notFound_throwException` |

### 2.3 命名反例

```java
// ❌ 错误
int d;                    // 无意义
String getPingJiaByName(); // 拼音混合
boolean flag;             // 语义不清
final int max_count = 10; // 下划线命名

// ✅ 正确
int elapsedDays;
String getCommentByName();
boolean enabled;
final int MAX_COUNT = 10;
```

## 3. 常量定义规范

### 3.1 禁止魔法值

> **【强制】** 禁止在代码中直接出现魔法值（Magic Number / Magic String），必须定义为常量或枚举。

```java
// ❌ 错误 — 魔法值
if (status == 3) { ... }
if ("success".equals(result)) { ... }

// ✅ 正确 — 定义为常量
private static final Integer ORDER_STATUS_SHIPPED = 3;
private static final String RESULT_SUCCESS = "success";

if (ORDER_STATUS_SHIPPED.equals(status)) { ... }
if (RESULT_SUCCESS.equals(result)) { ... }
```

### 3.2 long/Long 赋值规范

> **【强制】** `long` 或 `Long` 初始赋值时，必须使用大写的 `L`，不能是小写的 `l`。小写 `l` 容易与数字 `1` 混淆。

```java
// ❌ 错误
long value = 2l;  // 看起来像 21？

// ✅ 正确
long value = 2L;
```

### 3.3 常量分类维护

> **【推荐】** 不要使用一个常量类维护所有变量，要按常量功能进行归类，分开维护。

```java
// ❌ 错误 — 大而全的常量类
public class Constants {
    public static final int MAX_RETRY = 3;
    public static final String SUCCESS = "success";
    public static final int REDIS_EXPIRE = 3600;
    public static final String MQ_TOPIC_ORDER = "order_topic";
}

// ✅ 正确 — 按功能归类
public class RetryConstants { ... }
public class RedisConstants { ... }
public class MqTopicConstants { ... }
```

### 3.4 枚举优先于常量类

> **【推荐】** 如果变量值仅在一个固定范围内变化，用 `enum` 类型来定义。推荐使用枚举代替 `int` 常量，即使取值只有两个。

```java
// ✅ 推荐 — 使用枚举
public enum OrderStatus {
    PENDING(0, "待支付"),
    PAID(1, "已支付"),
    SHIPPED(2, "已发货"),
    COMPLETED(3, "已完成"),
    CANCELLED(4, "已取消");

    private final int code;
    private final String desc;

    OrderStatus(int code, String desc) {
        this.code = code;
        this.desc = desc;
    }
    // getter ...
}
```

## 4. 代码格式规范

### 4.1 大括号规则

> **【强制】** 遵循以下大括号换行约定（与 Google Java Style 完全一致）：

1. 左大括号前不换行，后换行
2. 右大括号前换行
3. 右大括号后还有 `else` 等代码则不换行；表示终止的右大括号后必须换行

```java
// ✅ 正确
public void method() {
    if (condition) {
        doSomething();
    } else {
        doOther();
    }
}

// ❌ 错误 — 左大括号前换行或右大括号后错误地换行
public void method()
{
    if (condition)
    {
        doSomething();
    }
}
```

### 4.2 空格规则

> **【强制】** 以下场景必须添加空格：

| 场景 | 示例 |
|------|------|
| 保留字与括号之间 | `if (condition)`、`for (...)`、`while (...)`、`switch (...)` |
| 二目运算符左右两侧 | `a + b`、`a == b`、`a && b` |
| 三目运算符左右两侧 | `condition ? a : b` |
| 赋值运算符左右两侧 | `int a = 1` |
| 注释双斜线与内容之间 | `// 这是注释` |
| 方法调用点号两侧不空格 | `obj.method()` |
| 类型转换括号与被转换对象之间 | `(int) value` |

```java
// ✅ 正确
if (flag == 0) {
    int result = a + b;
    String text = flag > 0 ? "yes" : "no";
}

// ❌ 错误
if(flag==0){
    int result=a+b;
    String text=flag>0?"yes":"no";
}
```

### 4.3 缩进与换行

> **【强制】** 采用 **4 个空格**缩进，禁止使用 Tab 字符。

> **【强制】** 单行字符数限制 **120** 字符。超出时必须换行，续行缩进 **8 字符**（相对于首行双倍缩进）。

```java
// ✅ 正确 — 换行示例
List<String> result = data.stream()
        .filter(item -> item.getStatus() == Status.ACTIVE)
        .map(Item::getName)
        .collect(Collectors.toList());
```

### 4.4 单行单语句

> **【强制】** 每条语句独占一行，禁止多语句合并为一行。

### 4.5 方法最大行数

> **【推荐】** 单方法不超过 **80 行**（不含空行与注释）。超过时说明方法职责过重，应拆分。

## 5. Import 导入规范

### 5.1 核心红线：禁止行内全限定名（FQN）

> **【强制】** 所有类型引用必须通过文件顶部的 `import` 语句声明，**严禁在代码体中使用全限定类名（Fully Qualified Name）**。

```java
// ✅ 正确 — 顶部 import，代码体使用简单名
import org.apache.ibatis.io.Resources;

public class SqlParseContext {
    private static final ThreadLocal<String> CACHED_SQL =
            new Resources.NamedThreadLocal<>("SqlParseContext.CachedSql");
}

// ❌ 错误 — 代码体中使用全限定名
public class SqlParseContext {
    private static final ThreadLocal<String> CACHED_SQL =
            new org.apache.ibatis.io.Resources.NamedThreadLocal<>("SqlParseContext.CachedSql");
}
```

**正例参考**：`org.apache.ibatis.io.Resources.NamedThreadLocal` 必须通过 `import org.apache.ibatis.io.Resources` 引入后使用 `Resources.NamedThreadLocal` 形式。

### 3.2 禁止通配符 import

> **【强制】** 禁止使用 `import xxx.*` 通配符导入。每个类型必须显式 import。

```java
// ❌ 错误
import org.springframework.beans.factory.*;
import java.util.*;

// ✅ 正确
import org.springframework.beans.factory.BeanFactory;
import org.springframework.beans.factory.ListableBeanFactory;
import java.util.List;
import java.util.Map;
```

### 3.3 import 排序与分组

import 语句按以下顺序排列，组间以**单个空行**分隔：

| 顺序 | 分组 | 示例 |
|------|------|------|
| 第 1 组 | `java.*` / `javax.*` | `java.util.List`、`javax.crypto.Cipher` |
| 第 2 组 | 第三方库（按字母序） | `org.springframework.*`、`com.google.common.*` |
| 第 3 组 | 公司内部包 | `com.njydsz.common.*` |
| 第 4 组 | 静态导入（单独一组） | `import static org.junit.jupiter.api.Assertions.*` |

**注意**：第 1 组和第 2 组之间、第 2 组和第 3 组之间必须有空行分隔。

```java
// ✅ 正确示例
import java.util.List;
import java.util.Map;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Service;

import com.njydsz.common.core.response.BaseResponse;

import lombok.extern.slf4j.Slf4j;
```

### 3.4 名称冲突处理

当两个同名类必须同时使用时，**仅对冲突的类使用全限定名**，其余仍正常 import：

```java
// ✅ 正确 — 名称冲突时的处理方式
import com.obs.services.model.ObjectMetadata;  // 正常 import 其中一个

public class FileStorage {
    public void upload() {
        // 冲突的另一个使用全限定名
        com.qcloud.cos.model.ObjectMetadata cosMeta = 
                new com.qcloud.cos.model.ObjectMetadata();
    }
}
```

**注意**：上述情况仅在名称冲突时允许，且必须在行末添加注释 `// FQN-OK: name conflict with Xxx` 说明原因。

### 3.5 未使用的 import

> **【强制】** 禁止保留未使用的 import 语句。IDE 应开启 "Optimize Imports" 自动清理。

## 6. OOP 规约

### 6.1 静态变量/方法访问方式

> **【强制】** 避免通过对象引用访问静态变量/静态方法，直接用类名访问。

```java
// ❌ 错误
Thread thread = new Thread(() -> {});
thread.sleep(1000);  // 看起来是实例方法

// ✅ 正确
Thread.sleep(1000);  // 明确是静态方法
```

### 6.2 覆盖 equals 必须同时覆盖 hashCode

> **【强制】** 覆盖 `equals` 方法时，必须同时覆盖 `hashCode` 方法。

> **【强制】** 所有整形包装类对象之间值的比较，全部使用 `equals` 方法，禁止使用 `==` 比较。

```java
// ❌ 错误 — 只覆盖 equals 未覆盖 hashCode
public class UserId {
    private final Long value;
    
    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof UserId)) return false;
        UserId that = (UserId) o;
        return Objects.equals(value, that.value);
    }
    // 缺少 hashCode 覆盖！
}

// ✅ 正确 — 同时覆盖 equals 和 hashCode
public class UserId {
    private final Long value;
    
    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof UserId)) return false;
        UserId that = (UserId) o;
        return Objects.equals(value, that.value);
    }
    
    @Override
    public int hashCode() {
        return Objects.hash(value);
    }
}

// ✅ 正确 — 包装类比较使用 equals
Integer a = 128;
Integer b = 128;
boolean equal = a.equals(b);  // 不要用 ==
```

### 6.3 浮点数比较规范

> **【强制】** 浮点数之间等值判断，基本类型不能用 `==` 进行比较，包装类型不能用 `equals` 进行判断。

> **【强制】** 禁止定义为 `double`、`float` 类型，一律使用 `BigDecimal`。

```java
// ❌ 错误 — 浮点数精确比较
float f1 = 1.0f - 0.9f;
float f2 = 0.9f - 0.8f;
if (f1 == f2) { ... }  // 结果为 false

BigDecimal a = new BigDecimal(0.1);  // 精度丢失

// ✅ 正确 — 指定误差范围或使用 BigDecimal
float delta = 1e-6f;
if (Math.abs(f1 - f2) < delta) { ... }

BigDecimal a = new BigDecimal("0.1");  // 用字符串构造
```

### 6.4 货币金额存储

> **【强制】** 任何货币金额，均以最小货币单位且为整型类型进行存储。

```java
// ❌ 错误 — 使用 double 存储金额
double price = 19.99;

// ✅ 正确 — 以分（最小单位）存储
long priceInCents = 1999;  // 19.99 元 = 1999 分
```

### 6.5 POJO 类布尔属性规范

> **【强制】** POJO 类中布尔类型的变量，都不要加 `is` 前缀，否则部分框架解析会引起序列化错误。

```java
// ❌ 错误
public class User {
    private Boolean isDeleted;  // 序列化后字段名可能变成 "deleted"
    public Boolean isDeleted() { return isDeleted; }
}

// ✅ 正确
public class User {
    private Boolean deleted;
    public Boolean getDeleted() { return deleted; }
}
```

### 6.6 避免使用 BigDecimal(double) 构造函数

> **【强制】** 禁止使用 `BigDecimal(double)` 构造方法，推荐使用 `BigDecimal(String)` 或 `BigDecimal.valueOf()`。

```java
// ❌ 错误 — 精度丢失
BigDecimal amount = new BigDecimal(0.1);  // 0.1000000000000000055511151231257827021181583404541015625

// ✅ 正确
BigDecimal amount = new BigDecimal("0.1");  // 精确值 0.1
BigDecimal amount = BigDecimal.valueOf(0.1); // 推荐
```

### 6.7 接口规范

> **【推荐】** 接口类中的方法和属性不要加任何修饰符号（`public` 也不要加），保持代码简洁。

```java
// ✅ 正确 — 接口方法默认 public
public interface UserService {
    void save(User user);  // 不需要写 public
    User findById(Long id);
}

// ❌ 错误 — 冗余修饰符
public interface UserService {
    public abstract void save(User user);
    public abstract User findById(Long id);
}
```

### 6.8 可变参数规范

> **【推荐】** 避免使用可变参数，参数类型避免定义为 `Object`。可变参数放置在参数列表最后。

### 6.9 过时方法禁止

> **【强制】** 不能使用过时的方法/类。使用过时的接口必须加 `@Deprecated` 注解，并清晰说明替代方案。

## 7. 日期时间规范

### 7.1 SimpleDateFormat 线程安全问题

> **【强制】** 禁止使用 `SimpleDateFormat` 作为共享变量（静态字段或实例字段），它是非线程安全的。

```java
// ❌ 错误 — 线程不安全
private static final SimpleDateFormat SDF = new SimpleDateFormat("yyyy-MM-dd");

public String formatDate(Date date) {
    return SDF.format(date);  // 多线程下会出现错误结果
}

// ✅ 正确 — 使用 DateTimeFormatter（线程安全）
private static final DateTimeFormatter FMT = DateTimeFormatter.ofPattern("yyyy-MM-dd");

public String formatDate(LocalDate date) {
    return date.format(FMT);
}
```

### 7.2 Java 8 时间 API 优先

> **【强制】** 日期时间操作使用 Java 8+ 时间 API（`java.time.*`），避免使用 `java.util.Date` / `Calendar`。

| 旧 API（禁止） | 新 API（推荐） | 说明 |
|---------------|---------------|------|
| `java.util.Date` | `Instant` | 时间戳 |
| `SimpleDateFormat` | `DateTimeFormatter` | 线程安全格式化 |
| `Calendar` | `LocalDateTime` | 日期时间操作 |
| — | `LocalDate` | 仅日期 |
| — | `LocalTime` | 仅时间 |
| — | `Duration` | 时间间隔 |
| — | `Period` | 日期间隔 |

### 7.3 时间精度规范

> **【推荐】** 时间存储统一使用毫秒级时间戳（`long`）或 `Instant`，避免精度混淆。

> **【推荐】** 避免使用 `System.currentTimeMillis()` 做耗时计算，改用 `System.nanoTime()`。

```java
// ❌ 错误 — 用 currentTimeMillis 做耗时计算（受系统时钟影响）
long start = System.currentTimeMillis();
doWork();
long elapsed = System.currentTimeMillis() - start;

// ✅ 正确 — 用 nanoTime 做耗时计算
long start = System.nanoTime();
doWork();
long elapsedMs = (System.nanoTime() - start) / 1_000_000;
```

## 8. 控制语句规范

### 8.1 switch 语句规范

> **【强制】** 在一个 `switch` 块内，每个 `case` 要么通过 `continue`/`break`/`return` 等来终止，要么注释说明程序将继续执行到哪一个 `case` 为止。

> **【强制】** 在一个 `switch` 块内，都必须包含一个 `default` 语句并且放在最后，即使它什么代码也没有。

```java
// ✅ 正确
switch (status) {
    case PENDING:
        return handlePending();
    case PAID:
        return handlePaid();
    default:
        throw new IllegalStateException("未知状态: " + status);
}
```

### 8.2 if-else 嵌套限制

> **【强制】** `if-else` 嵌套不超过 **3 层**。超过时必须重构为策略模式、卫语句（Guard Clause）或提取方法。

```java
// ❌ 错误 — 多层嵌套
if (user != null) {
    if (user.isActive()) {
        if (user.hasPermission()) {
            if (order != null) {
                // 业务逻辑
            }
        }
    }
}

// ✅ 正确 — 使用卫语句（Guard Clause）扁平化
if (user == null) return;
if (!user.isActive()) return;
if (!user.hasPermission()) return;
if (order == null) return;
// 业务逻辑
```

### 8.3 for 循环规范

> **【强制】** 禁止在 for 循环中修改循环变量（`for-each` 循环中修改集合结构）。

```java
// ❌ 错误 — ConcurrentModificationException
for (Item item : itemList) {
    if (item.isExpired()) {
        itemList.remove(item);  // 抛出异常
    }
}

// ✅ 正确 — 使用 Iterator 或 removeIf
itemList.removeIf(Item::isExpired);
```

## 9. 集合与数据结构规范

### 9.1 集合初始化

> **【强制】** 集合初始化时必须指定初始容量（已知大小时）。

```java
// ✅ 正确
List<String> list = new ArrayList<>(16);
Map<String, User> map = new HashMap<>(32);

// ❌ 错误 — 使用默认容量，频繁扩容
List<String> list = new ArrayList<>();
```

### 9.2 集合返回值

> **【强制】** 方法返回集合类型时，禁止返回 `null`，必须返回空集合。

```java
// ✅ 正确
public List<User> findUsers() {
    if (noData) {
        return Collections.emptyList();
    }
    return userList;
}
```

### 9.3 Map 快捷操作

> **【推荐】** 使用 `Map` 的快捷操作方法替代冗余判断：

```java
// ❌ 错误 — 冗余判断
String v = map.get("key");
if (v == null) {
    v = computeValue("key");
    map.put("key", v);
}

// ✅ 正确 — 使用 computeIfAbsent
String v = map.computeIfAbsent("key", k -> computeValue(k));

// ✅ 正确 — 使用 getOrDefault
String v = map.getOrDefault("key", DEFAULT_VALUE);
```

### 9.4 不可变集合

> **【推荐】** 需要返回不可变集合时，使用 `Collections.unmodifiableXxx()` 或 Guava `ImmutableXxx`。

```java
// ✅ 正确 — 返回不可变视图
public Map<String, String> getConfig() {
    return Collections.unmodifiableMap(configMap);
}

// ✅ 正确 — 使用 Guava（不可变集合）
List<String> list = ImmutableList.of("a", "b", "c");
Map<String, String> map = ImmutableMap.of("key1", "value1", "key2", "value2");
```

### 9.5 Arrays.asList 的坑

> **【强制】** 警惕 `Arrays.asList()` 返回的是固定大小列表，不能增删元素。

```java
// ❌ 错误 — UnsupportedOperationException
String[] arr = {"a", "b", "c"};
List<String> list = Arrays.asList(arr);
list.add("d");  // 抛出异常

// ✅ 正确 — 需要增删时创建新的可变集合
List<String> list = new ArrayList<>(Arrays.asList(arr));
list.add("d");  // OK
```

### 9.6 遍历与 Stream

| 场景 | 推荐方式 |
|------|---------|
| 简单遍历 | `for-each` 循环 |
| 过滤/映射/聚合 | Stream API |
| 并行流 | 仅在数据量大（>10000）且无状态时使用 `parallelStream()` |
| 修改外部变量 | 禁止在 lambda 中修改外部非 final 变量 |

### 9.7 contains/keySet 遍历优化

> **【强制】** 判断集合中是否存在元素，优先使用 `contains()` 而非 `keySet()` 遍历。

```java
// ❌ 错误 — 性能差
for (String key : map.keySet()) {
    if (key.equals(target)) {
        // found
    }
}

// ✅ 正确
if (map.containsKey(target)) {
    // found
}
```

### 9.8 Entry 遍历 Map

> **【推荐】** 遍历 Map 时优先使用 `entrySet()` 而非 `keySet()`。

```java
// ❌ 错误 — 两次查找
for (String key : map.keySet()) {
    String value = map.get(key);
    System.out.println(key + "=" + value);
}

// ✅ 正确 — 一次遍历
for (Map.Entry<String, String> entry : map.entrySet()) {
    System.out.println(entry.getKey() + "=" + entry.getValue());
}

// ✅ 推荐 — Java 8 forEach
map.forEach((key, value) -> System.out.println(key + "=" + value));
```

## 11. 异常处理规范

### 11.1 异常分类

| 异常类型 | 使用场景 | 示例 |
|---------|---------|------|
| `BusinessException` | 业务规则校验失败 | 用户余额不足、权限不足 |
| `SystemException` | 系统级错误 | 数据库连接失败、外部服务不可用 |
| `IllegalArgumentException` | 参数非法 | 必填参数为空、格式错误 |
| `IllegalStateException` | 状态不允许 | 订单已支付不允许取消 |

### 11.2 异常处理规则

> **【强制】** 禁止捕获 `Exception` / `Throwable` 后不处理（空 catch 块）。

```java
// ❌ 错误 — 吞掉异常
try {
    doSomething();
} catch (Exception e) {
    // 什么都不做
}

// ✅ 正确 — 至少记录日志
try {
    doSomething();
} catch (BusinessException e) {
    log.warn("业务异常: {}", e.getMessage());
    throw e;
} catch (Exception e) {
    log.error("系统异常", e);
    throw new SystemException("操作失败", e);
}
```

> **【强制】** 异常信息必须包含上下文（参数值、业务 ID 等），便于排查。

```java
// ✅ 正确
throw new BusinessException("用户[%s]余额不足，当前余额：%d", userId, balance);
```

### 11.3 自定义异常

- 继承 `RuntimeException`（业务异常）或 `Exception`（系统异常）
- 提供带 `message` 和 `cause` 的构造方法
- 禁止暴露敏感信息（密码、密钥、Token 等）

## 13. 单元测试规范

### 13.1 测试基本原则

> **【强制】** 单元测试必须独立运行，禁止测试之间有依赖顺序。

> **【强制】** 单元测试必须确定性执行，相同输入必须产生相同输出（禁止随机数、当前时间等非确定性依赖）。

### 13.2 测试命名与结构

> **【强制】** 测试方法命名采用 `test_被测场景_期望行为` 格式，测试体使用 **AAA（Arrange-Act-Assert）** 模式。

```java
// ✅ 正确
@Test
void test_findUserById_notFound_throwsException() {
    // Arrange（准备）
    Long notExistId = 9999L;
    
    // Act（执行）
    Executable action = () -> userService.findById(notExistId);
    
    // Assert（断言）
    assertThrows(UserNotFoundException.class, action);
}
```

### 13.3 断言规范

> **【推荐】** 使用 AssertJ 流式断言，提高断言可读性。

```java
// ❌ 错误 — 可读性差
assertTrue(user != null);
assertEquals("张三", user.getName());

// ✅ 正确 — AssertJ 流式断言
assertThat(user)
    .isNotNull()
    .extracting(User::getName, User::getAge)
    .containsExactly("张三", 25);

// ✅ 集合断言
assertThat(userList)
    .hasSize(3)
    .extracting(User::getName)
    .containsExactlyInAnyOrder("张三", "李四", "王五");
```

### 13.4 Mock 规范

> **【推荐】** 使用 Mock 隔离外部依赖，仅验证业务逻辑。

```java
// ✅ 正确
@Test
void test_createUser_duplicateEmail_throwsException() {
    // Given
    CreateUserRequest request = new CreateUserRequest("test@test.com");
    when(userRepository.existsByEmail(anyString())).thenReturn(true);
    
    // When & Then
    assertThrows(DuplicateEmailException.class, () -> userService.create(request));
    verify(userRepository, never()).save(any());
}
```

### 13.5 测试覆盖率要求

| 覆盖率类型 | 要求 |
|-----------|------|
| 核心业务逻辑覆盖率 | ≥ 80% |
| 分支覆盖率 | ≥ 70% |
| Controller/Repository 层 | 建议集成测试覆盖 |

## 15. 并发规范

### 15.1 线程安全

| 规则 | 要求 |
|------|------|
| 共享变量 | 必须使用 `volatile`、`AtomicXxx` 或同步机制 |
| 单例 | 使用枚举或静态内部类实现，禁止双重检查锁 |
| 线程池 | 统一使用 `ydsz-common-thread` 管理，禁止自建线程池（详见 15.4 节） |
| ThreadLocal | 必须在 `finally` 块中调用 `remove()` 清理 |

### 15.2 锁规范

```java
// ✅ 正确 — 使用 NamedThreadLocal 避免泄漏
private static final ThreadLocal<Connection> CONNECTION_HOLDER =
        new NamedThreadLocal<>("DB Connection") {
            @Override
            protected Connection initialValue() {
                return dataSource.getConnection();
            }
        };

// ✅ 正确 — finally 清理
try {
    threadLocal.set(value);
    doWork();
} finally {
    threadLocal.remove();
}
```

### 15.3 原子操作

优先使用 `java.util.concurrent` 包下的原子类，避免 `synchronized`：

```java
// ✅ 推荐
private final AtomicLong counter = new AtomicLong(0);
long next = counter.incrementAndGet();

// ❌ 避免
private long counter = 0;
private synchronized long next() {
    return ++counter;
}
```

### 15.4 统一线程池管理规范

> **【强制】** 所有异步任务必须通过 `ydsz-common-thread` 模块统一管理，禁止业务代码直接 `new ThreadPoolExecutor(...)` 或 `new ThreadPoolTaskExecutor()`。

#### 15.4.1 线程池创建禁止规则

| 禁止行为 | 正确做法 |
|---------|---------|
| `new ThreadPoolExecutor(core, max, ...)` | 配置 `ydsz.thread.pools.<name>` 声明式创建 |
| `new ThreadPoolTaskExecutor()` | 配置 `ydsz.thread.pools.<name>` 声明式创建 |
| `Executors.newFixedThreadPool()` | 配置 `ydsz.thread.pools.<name>` 声明式创建 |
| `Executors.newCachedThreadPool()` | 配置 `ydsz.thread.pools.<name>` 声明式创建 |

**豁免场景**（需 `// CHECKSTYLE.OFF: ThreadPoolCreate` + 注释说明）：
- `ydsz-common-thread` 模块内部实现
- 方法内短生命周期临时线程池（执行完毕后立即 `shutdown()`），如 `ConcurrentExcelWriter`
- JDK 21 虚拟线程工厂 `Executors.newThreadPerTaskExecutor()`

#### 15.4.2 配置规范

```yaml
# ✅ 正确 — 通过配置文件声明线程池
ydsz:
  thread:
    enabled: true
    bean-name-prefix: ydsz-                    # 推荐：统一前缀
    hot-update:
      enabled: true                            # 推荐：启用热更新
    pools:
      searchExecutor:                          # 命名：{module}{biz}Executor
        type: PLATFORM
        core-size: 4
        max-size: 16
        queue-capacity: 256
        thread-name-prefix: ydsz-search-       # 命名：ydsz-{module}-{biz}-
        reject-policy: CALLER_RUNS
        await-termination-seconds: 30
        slow-task-threshold-ms: 3000           # 按业务特征配置
        enable-detailed-metrics: true          # 关键池启用详细指标
        task-decorator-bean-names:             # 上下文传播装饰器
          - tenantContextTaskDecorator
```

#### 15.4.3 注入使用规范

```java
// ✅ 正确 — 通过 @Resource 注入 common-thread 管理的线程池
@Service
public class SearchService {

    @Resource(name = "searchExecutor")
    private ThreadPoolTaskExecutor searchExecutor;

    public CompletableFuture<SearchResponse> searchAsync(SearchRequest request) {
        return CompletableFuture.supplyAsync(() -> doSearch(request), searchExecutor);
    }
}

// ✅ 正确 — 通过 @Async 指定线程池
@Service
public class NotificationService {

    @Async("emailExecutor")
    public void sendEmail(String to, String content) {
        // 异步发送逻辑
    }
}

// ❌ 错误 — 自建线程池
@Service
public class BadExampleService {

    private final ThreadPoolTaskExecutor executor;

    public BadExampleService() {
        this.executor = new ThreadPoolTaskExecutor();  // 禁止！
        this.executor.setCorePoolSize(4);
        this.executor.initialize();
    }
}
```

#### 15.4.4 线程命名规范

| 元素 | 规范 | 示例 |
|------|------|------|
| Bean 名称 | `{module}{biz}Executor` | `searchExecutor`, `emailExecutor` |
| 线程名前缀 | `ydsz-{module}-{biz}-` | `ydsz-search-`, `ydsz-email-` |
| 配置 key | `{module}{biz}Executor` | `searchExecutor`, `jobDispatchExecutor` |

**注意**：`bean-name-prefix` 设置为 `ydsz-` 后，Bean 名称变为 `ydsz-{module}{biz}Executor`。

#### 15.4.5 上下文传播规范

> **【强制】** 所有通过 `ydsz-common-thread` 管理的线程池必须自动传播以下上下文：
> - `TenantContext`（租户 ID）
> - `RequestContext`（请求上下文）
> - MDC（日志追踪 ID）

配置示例：

```yaml
ydsz:
  thread:
    pools:
      bizExecutor:
        task-decorator-bean-names:
          - tenantContextTaskDecorator
          - mdcTaskDecorator
```

#### 15.4.6 虚拟线程使用规范

| 场景 | 推荐方式 |
|------|---------|
| IO 密集型（HTTP/DB/文件） | `type: VIRTUAL`（JDK 21+） |
| CPU 密集型 | `type: PLATFORM` |
| 混合负载 | `type: PLATFORM`（默认） |

```yaml
ydsz:
  thread:
    pools:
      ioExecutor:
        type: VIRTUAL
        thread-name-prefix: ydsz-io-
```

**注意**：虚拟线程不支持自定义 `core-size`/`max-size`/`queue-capacity`，仅 `thread-name-prefix` 生效。

#### 15.4.7 与 ydsz-common-util 的边界

| 维度 | `ydsz-common-util.ExecutorUtils` | `ydsz-common-thread` |
|------|---------------------------------|---------------------|
| 使用场景 | 非 Spring 场景、短生命周期临时线程池 | Spring 托管、长生命周期业务线程池 |
| 生命周期 | 调用方自行 shutdown | 随 Spring 容器统一优雅关闭 |
| 监控 | 无自动指标 | 自动暴露 Micrometer 指标 |
| 健康检查 | 无 | 自动注册 HealthIndicator |

**推荐**：Spring 环境优先使用 `ydsz-common-thread`；仅在非 Spring 工具方法内使用 `ExecutorUtils`。

## 16. 前后端规约

### 16.1 API 设计规范

> **【强制】** 前后端交互的 API，需要明确协议、域名、路径、请求方法、请求内容、状态码、响应体。

| 要素 | 规范 |
|------|------|
| 协议 | 生产环境必须使用 **HTTPS** |
| 路径 | 代表一种资源，只能为名词，推荐使用复数，不能为动词 |
| 路径分隔 | URL 路径不能使用大写，单词分隔统一使用**下划线** |
| 请求方法 | `GET`（查询）、`POST`（新增）、`PUT`（更新）、`DELETE`（删除） |
| 请求内容 | URL 参数必须无敏感信息；body 带参数时必须设置 `Content-Type` |
| 响应体 | 由 `Content-Type` 头确定数据类型 |

```java
// ✅ 正确 — RESTful API 设计
@GetMapping("/api/v1/users/{id}")           // GET 查询
@PostMapping("/api/v1/users")               // POST 新增
@PutMapping("/api/v1/users/{id}")           // PUT 更新
@DeleteMapping("/api/v1/users/{id}")        // DELETE 删除
```

### 16.2 响应结构规范

> **【强制】** 统一响应结构，包含 `code`、`message`、`data` 三个字段。

```java
// ✅ 正确 — 统一响应结构
public class BaseResponse<T> implements IResponse {
    private int code;       // 业务状态码：0=成功，非0=失败
    private String message; // 提示信息
    private T data;         // 业务数据
    
    // 成功响应
    public static <T> BaseResponse<T> success(T data) {
        BaseResponse<T> resp = new BaseResponse<>();
        resp.setCode(0);
        resp.setMessage("success");
        resp.setData(data);
        return resp;
    }
    
    // 失败响应
    public static <T> BaseResponse<T> fail(IResponse errorCode) {
        BaseResponse<T> resp = new BaseResponse<>();
        resp.setCode(errorCode.getCode());
        resp.setMessage(errorCode.getMessage());
        return resp;
    }
}
```

### 16.3 分页响应规范

> **【强制】** 分页接口返回空数据时，返回空数组 `[]` 或空集合 `{}`，禁止返回 `null`。

```java
// ✅ 正确 — 分页响应
public class PageResponse<T> {
    private long total;       // 总记录数
    private int pageNum;      // 当前页码
    private int pageSize;     // 每页大小
    private List<T> list;     // 数据列表（空数据时为 []）
    
    public static <T> PageResponse<T> empty(int pageNum, int pageSize) {
        PageResponse<T> resp = new PageResponse<>();
        resp.setTotal(0);
        resp.setPageNum(pageNum);
        resp.setPageSize(pageSize);
        resp.setList(Collections.emptyList());
        return resp;
    }
}
```

### 16.4 错误响应规范

> **【强制】** 服务端发生错误时，返回给前端的响应信息必须包含 HTTP 状态码、`errorCode`、`errorMessage`、用户提示信息四个部分。

```json
{
    "code": "USER-BIZ-001",
    "message": "用户邮箱已被注册",
    "userTip": "该邮箱已被使用，请更换",
    "data": null
}
```

### 16.5 JSON 数据格式规范

> **【强制】** 前后端交互的 JSON 格式数据中，所有的 key 必须为小写字母开始的 `lowerCamelCase` 风格。

```java
// ✅ 正确
{"errorCode": "USER-BIZ-001", "errorMessage": "邮箱已被注册", "assetStatus": "active"}

// ❌ 错误
{"ErrorCode": "USER-BIZ-001", "error_message": "邮箱已被注册", "AssetStatus": "active"}
```

### 16.6 幂等性规范

> **【强制】** 涉及写操作的接口必须支持幂等性（多次调用结果一致），通过唯一请求 ID 或数据库唯一约束实现。

```java
// ✅ 正确 — 通过唯一请求 ID 实现幂等
@PostMapping("/api/v1/orders")
public BaseResponse<OrderVO> createOrder(
        @RequestHeader("X-Idempotent-Key") String idempotentKey,
        @RequestBody @Valid CreateOrderRequest request) {
    // 检查幂等键是否已处理
    if (orderService.isDuplicateRequest(idempotentKey)) {
        return BaseResponse.success(orderService.getResultByKey(idempotentKey));
    }
    // 处理业务逻辑
    OrderVO order = orderService.create(request, idempotentKey);
    return BaseResponse.success(order);
}
```

## 17. 安全规范

### 17.1 输入校验

> **【强制】** 所有外部输入（HTTP 参数、RPC 参数、消息体）必须进行参数校验。

```java
// ✅ 正确 — 使用 JSR-380 Bean Validation
public void createUser(@Valid CreateUserRequest request) {
    // ...
}

// DTO 中使用注解
public class CreateUserRequest {
    @NotBlank(message = "用户名不能为空")
    @Size(min = 2, max = 32)
    private String username;
    
    @Email(message = "邮箱格式不正确")
    private String email;
}
```

### 17.2 敏感数据处理

| 数据类型 | 处理方式 |
|---------|---------|
| 密码 | BCrypt 哈希存储，禁止 MD5/SHA1 |
| 手机号/身份证 | 脱敏显示（`138****1234`） |
| Token/密钥 | 禁止日志打印，禁止 URL 参数传递 |
| 数据库连接串 | 加密存储（ydsz-common-config） |

### 17.3 SQL 注入防护

> **【强制】** 禁止拼接 SQL 字符串，必须使用参数化查询（PreparedStatement / MyBatis `#{}`）。

```java
// ❌ 错误 — SQL 注入风险
String sql = "SELECT * FROM user WHERE name = '" + name + "'";

// ✅ 正确 — 参数化查询
String sql = "SELECT * FROM user WHERE name = #{name}";
```

### 17.4 XSS 防护

> **【强制】** 所有用户输入输出必须进行 XSS 过滤，使用 `ydsz-common-safe` 提供的工具类。

### 17.5 接口安全

> **【强制】** 涉及用户数据的接口必须进行权限校验，确保用户只能访问自己的数据。

> **【强制】** 敏感操作（删除、修改密码、支付）必须进行二次验证（验证码/密码确认）。

### 17.6 common-safe 安全能力复用规范（v2.4 新增）

> **【强制】** 业务模块必须优先使用 `ydsz-common-safe` 提供的安全能力，禁止重复造轮子。

| 安全能力 | common-safe 统一 API | 禁止行为 | 适用场景 |
|---------|---------------------|---------|---------|
| 密码强度校验 | `PasswordStrengthValidator` | 自行编写正则规则校验密码强度 | 注册/修改密码 |
| 字段级加密 | `@EncryptField` + `EncryptTypeHandler` | 在 Service 层手动加解密 | 身份证、姓名等 PII 字段 |
| 安全事件上报 | `SecurityEventPublisher.publish(SecurityEvent)` | 静默处理安全事件不聚合 | 登录失败、非法访问 |
| IP 访问控制 | `IpAccessService` | 自建 IP 封禁逻辑/过滤器 | 所有业务接口 |
| 图形验证码 | `CaptchaGenerator` | 自建验证码生成/存储逻辑 | 登录/注册验证 |
| 敏感数据脱敏 | `@Sensitive`（字段级，推荐） | 在 Controller/VO 中硬编码脱敏逻辑 | API 返回值脱敏 |
| 安全响应头 | `SecurityHeaderFilter` + `SecurityHeaderConfigurer` | 在 Gateway 和业务服务中分别实现 | 所有 HTTP 响应 |
| PII 扫描 | `SensitiveUtil.scanAndMask()` | 自行编写正则匹配敏感信息 | 日志/LLM 输出清洗 |

#### 17.6.1 密码强度校验

> **【强制】** 密码强度校验必须使用 `common-safe` 的 `PasswordStrengthValidator`，禁止自行实现校验规则。

```java
// ✅ 正确 — 使用统一 API
@Service
@RequiredArgsConstructor
public class UserServiceImpl {
    private final PasswordStrengthValidator passwordStrengthValidator;

    public void changePassword(String newPassword) {
        passwordStrengthValidator.validate(newPassword);  // 默认 MEDIUM 级别
        // ... 更新密码
    }
}

// ❌ 错误 — 自行编写正则
public void changePassword(String newPassword) {
    if (newPassword.length() < 8 || !newPassword.matches(".*\\d.*")) {
        throw new BusinessException("密码强度不足");
    }
}
```

#### 17.6.2 字段级加密（@EncryptField）

> **【强制】** 数据库字段级加密必须使用 `@EncryptField` + `EncryptTypeHandler`，禁止在 Service 层手动加解密。

```java
// ✅ 正确 — 声明式加密
@Data
@TableName("ydsz_user_account")
public class UserAccount extends MpBaseEntity<String> {
    @TableField(typeHandler = EncryptTypeHandler.class)
    @EncryptField
    private String realName;  // 自动入库加密、出库解密
}

// ❌ 错误 — 手动加解密
public void createUser(UserDTO dto) {
    UserAccount entity = new UserAccount();
    entity.setRealName(aesService.encrypt(dto.getRealName()));  // 重复造轮子
}
```

> **【注意】** `@EncryptField` 使用 AES-256-GCM 随机 IV，**加密字段不可用于 WHERE/LIKE 条件查询**。需要查询的字段（如 `phone`、`email`）不建议加密，或采用应用层哈希索引方案。

#### 17.6.3 安全事件上报

> **【强制】** 业务模块发生安全相关事件（登录失败、权限校验失败、非法参数访问）必须通过 `SecurityEventPublisher` 上报，禁止静默处理。

```java
// ✅ 正确 — 发布安全事件，驱动 SecurityEventAggregator 自动响应
@Service
@RequiredArgsConstructor
public class AuthServiceImpl {
    private final ObjectProvider<SecurityEventPublisher> securityEventPublisherProvider;

    public LoginVO login(LoginDTO dto) {
        if (!passwordMatched) {
            // 发布 BRUTE_FORCE 事件，驱动滑动窗口计数 + 自动 IP 封禁
            securityEventPublisherProvider.getIfAvailable()
                .publish(new SecurityEvent(
                    SecurityEventType.BRUTE_FORCE,
                    "/auth/login", loginIp, userAgent,
                    "Failed login for: " + username,
                    SecurityEvent.Severity.MEDIUM
                ));
            throw new BusinessException(PASSWORD_INCORRECT);
        }
    }
}
```

> **【强制】** 必须同时配置 `ydsz.safe.ip-access.enabled=true` 和 `ydsz.safe.auto-block.enabled=true`，确保事件聚合器能调用 `IpAccessService.block()` 完成闭环。

#### 17.6.4 IP 访问控制收敛

> **【强制】** IP 封禁/黑白名单必须使用 `common-safe` 的 `IpAccessService`，禁止在业务模块自建 IP 拦截逻辑。

```java
// ✅ 正确 — 使用 IpAccessService
// 配置：ydsz.safe.ip-access.enabled=true, mode=BLACKLIST
// 自动封禁：SecurityEventAggregator → IpAccessService.block() → Redis 持久化
// 过滤器：IpAccessFilter（HIGHEST_PRECEDENCE）自动拦截黑名单 IP

// ❌ 错误 — 自建 IP 封禁
public class InternalApiIpFilter implements Filter {
    private final Set<String> blacklist = Set.of("10.0.0.1");  // 硬编码
    // ... 重复实现
}
```

#### 17.6.5 验证码能力统一

> **【强制】** 图形验证码必须使用 `common-safe` 的 `CaptchaGenerator`，禁止自建验证码生成、Redis 存储、校验逻辑。

```java
// ✅ 正确 — CaptchaGenerator 已由 SafeConfiguration 自动注册为 Bean
// 配置：ydsz.safe.captcha.enabled=true, ttl-seconds=300, code-length=4

// ❌ 错误 — 自建验证码
public class MyCaptchaService {
    // 重复实现图形绘制、Redis 存储、校验逻辑
}
```

#### 17.6.6 脱敏规范

> **【强制】** 字段级脱敏优先使用 `@Sensitive`（`common-safe/desensitize` 包，推荐方案），禁止在 Controller/VO 中硬编码脱敏逻辑。

| 脱敏方案 | 适用场景 | 优先级 |
|---------|---------|-------|
| `@Sensitive(type = SensitiveType.MOBILE)` | 字段级、JSON 序列化时脱敏 | **推荐** |
| `@SensitiveData(SensitiveType.PHONE)` | 需要基于角色白名单动态脱敏 | 可选 |
| `ColumnDesensitizationContext` | SQL 数据层（查询结果集）脱敏 | 可选 |
| Controller 中 `phone.replaceAll("(\\d{3})\\d{4}(\\d{4})", "$1****$2")` | 无 | **禁止** |

#### 17.6.7 CSRF 配置策略

> **【强制】** `ydsz-cloud` 采用 JWT Bearer Token 架构，CSRF 默认关闭（`ydsz.safe.csrf.enabled=false`）。仅当存在 Cookie/Session 认证端点时启用。

> **【原因】** 浏览器无法在跨站请求中自动添加 `Authorization: Bearer <token>` 头，因此 CSRF 攻击无法携带有效凭证，CSRF 防护在此架构下无意义。

#### 17.6.8 安全响应头收敛

> **【强制】** 安全响应头注入逻辑必须下沉到 `common-safe` 的 `SecurityHeaderConfigurer`，禁止在 Gateway 和业务服务中分别实现。

```java
// Gateway 侧 — 委托给 SecurityHeaderConfigurer
SecurityHeaderConfigurer.applyWebFluxHeaders(response, commonProps);

// 业务服务侧 — SecurityHeaderFilter 内部使用 SecurityHeaderConfigurer.computeHeaders()
// 禁止：在 filter 中直接 setHeader("X-Frame-Options", ...)
```

### 17.7 common-safe 配置清单

> **【建议】** 业务模块接入 common-safe 后，应在 `application.yml` / Nacos 配置中启用以下能力：

| 配置项 | 默认值 | 说明 |
|-------|-------|------|
| `ydsz.safe.security-headers.enabled` | true | 安全响应头 |
| `ydsz.safe.xss.enabled` | true | XSS 防护（默认 converter 模式） |
| `ydsz.safe.csrf.enabled` | false | CSRF（JWT 架构默认关闭） |
| `ydsz.safe.sensitive.enabled` | true | 字段级脱敏 |
| `ydsz.safe.field-encryption.enabled` | true | 字段级加密（需配置 keys） |
| `ydsz.safe.ip-access.enabled` | false | IP 访问控制（按需启用） |
| `ydsz.safe.auto-block.enabled` | true | 自动封禁（需配合 ip-access） |
| `ydsz.safe.captcha.enabled` | true | 验证码（需 Redis） |
| `ydsz.safe.api-signature.enabled` | false | API 签名（对外接口启用） |

## 18. 性能规范

### 18.1 资源管理

> **【强制】** 所有 IO 资源（InputStream、Connection、Reader）必须使用 try-with-resources 自动关闭。

```java
// ✅ 正确
try (InputStream is = Files.newInputStream(path)) {
    // 使用 is
}

// ❌ 错误 — 手动 close 容易遗漏
InputStream is = Files.newInputStream(path);
// 使用 is
is.close();
```

### 18.2 字符串拼接

| 场景 | 推荐方式 |
|------|---------|
| 单线程大量拼接 | `StringBuilder` |
| 多线程 | `StringBuffer` |
| 简单拼接（<5 次） | `+` 运算符（编译器自动优化） |
| 格式化 | `String.format()` 或 `MessageFormat` |

### 18.3 对象创建

- 避免在循环内创建不必要的对象
- 优先使用对象池（数据库连接池、线程池）
- 大对象（>1MB）避免频繁创建

### 18.4 N+1 查询防护

> **【强制】** 禁止在循环中执行数据库查询（N+1 问题），必须使用批量查询。

```java
// ❌ 错误 — N+1 查询
List<Order> orders = orderMapper.findAll();
for (Order order : orders) {
    User user = userMapper.findById(order.getUserId());  // 每次循环都查数据库
}

// ✅ 正确 — 批量查询
List<Order> orders = orderMapper.findAll();
List<Long> userIds = orders.stream().map(Order::getUserId).collect(Collectors.toList());
Map<Long, User> userMap = userMapper.findByIds(userIds).stream()
        .collect(Collectors.toMap(User::getId, Function.identity()));
```

### 18.5 缓存使用规范

#### 18.5.1 本地缓存总则

> **【强制】** 本地缓存必须统一使用 `ydsz-common-cache` 模块，**禁止直接使用 Caffeine、Guava Cache、EhCache 等第三方缓存库**。

> **【强制】** 禁止业务代码直接 `new Caffeine.newBuilder()` 或 `new Guava Cache()`，必须通过 `YdszCache.newBuilder()` 创建。

```java
// ❌ 错误 — 直接使用 Caffeine
Cache<String, User> cache = Caffeine.newBuilder()
        .maximumSize(1000)
        .expireAfterWrite(10, TimeUnit.MINUTES)
        .build();

// ✅ 正确 — 使用 ydsz-common-cache
Cache<String, User> cache = YdszCache.<String, User>newBuilder()
        .type(CacheType.STRIPED)
        .name("user:info")                              // 必须指定 name 用于健康检查
        .maximumSize(1000)
        .expireAfterWrite(10, TimeUnit.MINUTES)
        .build();
```

#### 18.5.2 Spring Cache 注解驱动（标准场景优先）

> **【推荐】** 对于标准的缓存读取-回填场景，优先使用 Spring Cache 注解（`@Cacheable` / `@CacheEvict` / `@CachePut`），减少样板代码。

```java
@Service
public class DictItemServiceImpl implements DictItemService {

    @Cacheable(value = "dictItem", key = "@cacheKeyBuilder.dictItem(#p0, #p1)")
    public DictItemDTO getByTypeAndCode(String typeCode, String code) {
        return dictItemMapper.selectByTypeAndCode(typeCode, code);
    }

    @Cacheable(value = "dictList", key = "@cacheKeyBuilder.dictList(#p0)")
    public List<DictItemDTO> listEnabledByTypeCode(String typeCode) {
        return dictItemMapper.selectEnabledByType(typeCode);
    }

    @CacheEvict(value = {"dictItem", "dictList"}, allEntries = true)
    public void save(DictItemDTO dto) {
        // 保存逻辑
    }
}
```

**注意事项**：
- `allEntries = true` 用于清除整个缓存字典，适用于写操作后全量失效
- key 生成使用 `CacheKeyBuilder` SpEL 表达式，确保租户隔离
- 缓存名称必须在 `CacheConstants` 中统一定义，避免魔法字符串

#### 18.5.3 编程式缓存规范

> **【强制】** 编程式创建缓存时，必须通过 `.name()` 方法指定健康检查标识，格式为 `{模块}:{用途}`。

```java
// ✅ 正确 — 命名规范
YdszCache.<String, RolePermissions>newBuilder()
        .type(CacheType.STRIPED)
        .name("auth:role-permissions")      // 模块:用途
        .maximumSize(maxSize)
        .expireAfterWrite(ttl, TimeUnit.MINUTES)
        .build();

// ❌ 错误 — 缺少 name() 绑定
YdszCache.<String, RolePermissions>newBuilder()
        .type(CacheType.STRIPED)
        .maximumSize(maxSize)
        .expireAfterWrite(ttl, TimeUnit.MINUTES)
        .build();
```

#### 18.5.4 缓存配置外部化

> **【强制】** TTL（过期时间）和 `maximumSize`（最大容量）**禁止硬编码在代码中**，必须通过 `@ConfigurationProperties` 从 YAML 配置读取。

```yaml
# ✅ 正确 — application.yml
ydsz:
  tenant:
    sql-cache:
      enabled: true
      max-size: 2000
      expire-minutes: 10
  cronjob:
    spel:
      enabled: true
      max-size: 1024
```

```java
// ✅ 正确 — 配置类
@Component
@ConfigurationProperties(prefix = "ydsz.tenant")
public class TenantProperties {

    private SqlCacheConfig sqlCache = new SqlCacheConfig();

    @Data
    public static class SqlCacheConfig {
        private boolean enabled = true;
        private int maxSize = 2000;         // 默认值在配置类中定义
        private int expireMinutes = 10;
    }
}

// ❌ 错误 — 硬编码 TTL/容量
private static final long TTL = 600;        // 10分钟
private static final int MAX_SIZE = 1000;
```

#### 18.5.5 缓存防护三防策略

> **【推荐】** 对高并发热点数据，使用 `CacheProtectionGuard` 实现三层防护：
> - **防穿透**：缓存空值占位，避免不存在的数据反复穿透到数据库
> - **防击穿**：单个 key 并发加载互斥，只允许一个线程回源
> - **防雪崩**：空值随机过期时间，避免集中失效

```java
// ✅ 正确 — 使用 CacheProtectionGuard
public User getUserWithProtection(String userId) {
    return CacheProtectionGuard.getWithProtection(
        userCache,                      // 缓存实例
        userId,                         // 缓存键
        id -> userMapper.findById(id),  // 加载器
        5000,                           // 空值最小过期（ms）
        30000                           // 空值最大过期（ms）
    );
}
```

**说明**：`SpringYdszCache` 已内置 single-flight（防击穿）和 `allowNullValues=true`（防穿透），通过 Spring Cache 注解使用时自动获得基础防护能力。

#### 18.5.6 缓存 Key 命名规范

| 层级 | 格式 | 示例 |
|------|------|------|
| Spring Cache 名称 | `{模块}:{业务}` | `dictItem`, `dictList`, `variable` |
| 编程式缓存 name | `{模块}:{用途}` | `auth:role-permissions`, `flow:def-nodes` |
| 缓存 key 前缀 | `项目统一约定` | 通过 `CacheKeyBuilder` SpEL 生成 |

> **【强制】** 多租户场景下，缓存 key 必须包含租户 ID，使用 `CacheKeyBuilder` 确保隔离。

```java
// ✅ 正确 — 租户隔离的 key 生成
@Cacheable(value = "dictItem", key = "@cacheKeyBuilder.dictItem(#p0, #p1)")
// SpEL 表达式内部自动拼接 tenantId

// ❌ 错误 — 未隔离的 key
@Cacheable(value = "dictItem", key = "#p0 + ':' + #p1")
// 不同租户的 key 可能冲突！
```

#### 18.5.7 跨实例缓存一致性

> **【强制】** 当本地缓存数据发生变更时，必须通过事件广播（`CrossModuleEventListener` 或业务自定义事件）通知其他节点清除缓存。

```

## 19. 正则表达式规范

### 19.1 Pattern 预编译

> **【强制】** 禁止在循环中编译正则表达式，必须预编译为 `static final Pattern`。

```java
// ❌ 错误 — 每次循环都编译正则
for (String str : list) {
    if (str.matches("\\d{11}")) { ... }
}

// ✅ 正确 — 预编译
private static final Pattern PHONE_PATTERN = Pattern.compile("^1[3-9]\\d{9}$");

for (String str : list) {
    if (PHONE_PATTERN.matcher(str).matches()) { ... }
}
```

### 19.2 正则表达式可读性

> **【推荐】** 复杂正则表达式必须添加注释说明匹配规则。

```java
// ✅ 正确 — 带注释的正则
// 手机号：1开头，第二位3-9，后面9位数字
private static final Pattern PHONE = Pattern.compile(
    "^" +
    "1" +           // 第一位：1
    "[3-9]" +       // 第二位：3-9
    "\\d{9}" +      // 后面9位数字
    "$"
);
```

### 20.6 Excel 处理规范（v2.7 新增）

> **【强制】** 所有 Excel 导入导出操作必须通过 `ydsz-common-excel` 模块完成，**严禁业务模块直接使用 Apache POI API**（`ydsz-common-excel` 内部与 `ydsz-common-docs` 除外）。

#### 20.6.1 核心原则

1. **统一入口**：Excel 读写统一通过 `ExcelFacade`（门面）、`ExcelExportHelper`（导出辅助）、`ExcelWebSupport`（Web 下载）三个公共入口完成，禁止自行创建 `ByteArrayOutputStream + ExcelFacade.write()` 流水线。
2. **统一 Web 下载**：Controller 层下载 Excel 一律通过 `ExcelWebSupport.write()` / `writeBytes()` 完成，禁止手动拼接 `HttpHeaders`（Content-Type / Content-Disposition / 文件名编码）。
3. **统一导出辅助**：服务层生成 Excel 字节数组一律通过 `ExcelExportHelper.export()` 完成，禁止自行创建 `ByteArrayOutputStream` 并调用 `ExcelFacade.write()`。
4. **注解驱动优先**：有固定 VO 类型的场景，优先使用 `@ExcelProperty` / `@ExcelSheet` / `@ExcelHead` 等注解驱动映射，减少手动 `List<List<Object>>` 动态数据编码。

#### 20.6.2 能力清单与接入方式

| 场景 | 推荐入口 | 说明 |
|------|---------|------|
| 简单导出（有 VO 类型） | `ExcelExportHelper.export(sheetName, Class<T>, List<T>)` | 自动映射注解，一行代码完成 |
| 动态导出（自定义表头） | `ExcelExportHelper.export(sheetName, List<String> headers, List<List<Object>> rows)` | 适用于动态报表等无固定 VO 场景 |
| Web 下载（服务层已生成 byte[]） | `ExcelWebSupport.writeBytes(response, bytes, filename)` | 统一处理 Content-Type / Content-Disposition |
| Web 下载（直接写入） | `ExcelWebSupport.write(response, Class<T>, List<T>, sheetName)` | 直接写入 HttpServletResponse |
| 标准读写（有 VO 类型，Spring 环境） | 注入 `ExcelTemplate` | 复用全局 `ExcelConfig` 配置 |
| 模板填充 | `ExcelFacade.writeWithTemplate(templatePath, outputPath, Class<T>)` | 保留模板样式/公式 |
| 流式读取（大数据） | `ExcelFacade.read(inputStream).doRead(listener)` | SAX 流式解析，内存 ~50MB |
| 无类型全 Sheet 读取 | `ExcelFacade.readAllSheets(inputStream)` | 文档解析、数据校验等场景 |
| 并发写入（百万行） | `ConcurrentExcelWriter` | 多线程分片写入 |
| 高度自定义结构（多段混合、特殊格式） | `ExcelFacade.write()` / `ExcelFacade.read()` 直接使用 | 仅当上述入口无法满足时使用 |

#### 20.6.3 模式选择指南

```
有 VO 类型且为标准 tabular 结构？
├── 是 → 使用 @ExcelProperty 注解驱动
│   ├── 导出 → ExcelTemplate.write() 或 ExcelExportHelper.export()
│   └── 读取 → ExcelTemplate.read() + ReadListener
└── 否 → 是否为动态报表（运行时确定列）？
    ├── 是 → 使用 List<List<Object>> + headers
    │   └── ExcelExportHelper.export(sheetName, headers, rows)
    └── 否 → 是否为自定义多段结构（如决策表含元数据行）？
        ├── 是 → 使用 ExcelFacade 直接 API（需注明理由）
        └── 否 → 是否为文档解析（全 Sheet 无类型读取）？
            └── 是 → ExcelFacade.readAllSheets(inputStream)
```

**注解驱动优先原则**：有固定 VO 类型时，**必须使用 `@ExcelProperty` 注解驱动映射**，禁止手动 `List<List<Object>>` 动态构建数据。注解驱动的优势：
- 编译期类型安全，重构友好
- 自动处理表头名映射、列顺序、日期/数字格式化
- 可通过 `@ExcelIgnore` 排除字段、`@ExcelHead` 自定义表头名
- 减少 50% 以上的数据转换编码量

#### 20.6.4 注解驱动最佳实践

```java
// ✅ 正确：注解驱动映射
@Data
@ExcelSheet(name = "用户列表")
public class UserExportVO {

    @ExcelProperty(value = "用户ID", index = 0)
    private Long userId;

    @ExcelProperty(value = "用户名", index = 1)
    private String username;

    @ExcelProperty(value = "创建时间", index = 2, dateFormat = "yyyy-MM-dd HH:mm:ss")
    private LocalDateTime createdAt;

    @ExcelIgnore
    private String internalField;  // 不导出
}

// 导出
byte[] bytes = excelExportHelper.export("用户列表", UserExportVO.class, userList);

// ❌ 错误：手动构建 List<List<Object>>（失去类型安全）
List<List<Object>> rows = new ArrayList<>();
for (User user : users) {

```

### 21.4 模块拆分约束

> **【强制】** 禁止在 `ydsz-common` 下自行创建新子模块。已有功能必须优先合并到现有对应层级的模块中。

> **【强制】** 任何涉及**新增/拆分/合并 ydsz-common 子模块**的架构变更，必须先提交"架构变更申请"（Architecture Change Request，ACC），经技术负责人审批同意后方可执行。

**背景**：`ydsz-common` 采用严格分层架构（L1 工具层 → L2 基础层 → L4 数据层 → L5 服务层 → L6 应用层），每个层级有明确定义的模块职责边界。历史上曾错误地将 `Idempotent`、`RateLimit`、`Doc`、`I18n` 等功能拆分为独立模块，导致以下问题：

- 模块碎片化，增加依赖管理复杂度
- 跨模块调用增加理解成本
- 同类功能分散，违反单一职责原则
- 传递依赖膨胀，间接引入无关传递依赖

**典型违规案例（v2.6-v2.7 新增）**：

1. **v2.6 案例**：在 `ydsz-common-excel` 优化过程中，AI 助手未经常规审批流程，自行创建了 `ydsz-common-excel-spring` 子模块用于拆分 Spring 集成代码。该变更虽然技术上可行，但违反了"禁止自行新建子模块"的强制规范，最终被要求还原。此案例被固化为反面教材。

2. **v2.7 案例**：在对 `ydsz-common-base` 模块进行过度设计评估时，AI 助手未经常规审批流程，自行创建了 4 个新子模块（`ydsz-common-idempotent`、`ydsz-common-ratelimit`、`ydsz-common-base-doc`、`ydsz-common-base-i18n`），将原本内聚在 `ydsz-common-base` 中的幂等、限流、文档、国际化管理功能拆分为独立模块。该变更导致：
   - 模块碎片化，增加依赖管理复杂度
   - `ydsz-common-idempotent` 和 `ydsz-common-ratelimit` 被迫依赖 `ydsz-common-core`，反向传递依赖
   - 文档导出器（DocExporter）被迫依赖 `ydsz-common-json`，引入不必要的第三方库
   - 最终全部还原到 `ydsz-common-base` 模块，功能内聚优先于模块拆分

**核心原则**：**功能内聚优先于模块拆分**。当功能代码量不构成独立模块的充分理由时，应优先保持现有模块内聚。只有当以下条件全部满足时，才可考虑拆分：
   - 功能代码量 > 2000 行且职责边界清晰
   - 存在明确的独立版本管理需求
   - 多个业务模块有选择性引入该功能的需求
   - 通过 ACC 审批流程

**规则细节**：

1. **L1 工具层能力**（json/util/cache/excel）：只提供无状态的工具方法，禁止依赖 L2+ 内部模块
2. **安全过滤能力**（XSS/加密）：统一归属 `ydsz-common-safe` 模块
3. **HTTP 基座横切能力**（幂等/限流/CORS/文档/拦截器/i18n）：统一归属 `ydsz-common-base` 模块（v2.7 更新）
4. **认证/授权能力**（AuthInfo/权限校验）：统一归属 `ydsz-common-auth` 模块
5. **跨层访问需求**：通过反射代理（`internal.proxy`）或 SPI 接口下沉方式解耦，**禁止反向依赖**
6. **Spring 集成代码**：各模块内部的 Spring 自动配置、HealthIndicator 等 Spring 相关代码**直接放在本模块内**的 `spring` 子包中，**禁止单独拆分**为 `*-spring` 子模块

**变更流程**（架构变更申请 ACC）：

当确实需要新增/拆分/合并 ydsz-common 子模块时，必须执行以下流程：

1. **问题定义**：明确当前架构无法通过模块内重组解决的具体痛点
2. **影响范围分析**：列出受影响的下游模块数量、传递依赖变化
3. **方案对比**：至少给出"模块内重组"和"拆分新模块"两个方案并对比优劣
4. **提交申请**：在技术负责人处备案，说明变更原因、影响范围、回滚方案
5. **审批执行**：获得书面同意后方可修改父 POM `<modules>` 列表

**合并策略**：

| 功能类型 | 归属模块 | 包路径优先级 |
|---------|---------|------------|
| 幂等性 | `ydsz-common-base` | `com.njydsz.common.base.idempotent`（v2.7 明确归位） |
| 限流 | `ydsz-common-base` | `com.njydsz.common.base.ratelimit`（v2.7 明确归位） |
| 字段加密 | `ydsz-common-safe` | `com.njydsz.common.safe.encrypt` |
| XSS 过滤 | `ydsz-common-safe` | `com.njydsz.common.safe.xss` |
| API 文档（OpenAPI/Knife4j） | `ydsz-common-base` | `com.njydsz.common.base.config` + `com.njydsz.common.base.exporter` |
| 国际化（i18n） | `ydsz-common-base` | `com.njydsz.common.base.i18n` + `com.njydsz.common.base.config` |
| 认证模型 | `ydsz-common-auth` | `com.njydsz.common.auth.model` |
| 认证工具 | `ydsz-common-auth` | `com.njydsz.common.auth.context` |
| Excel Spring 集成 | `ydsz-common-excel` | `com.njydsz.common.excel.spring` |

#### 20.4.3 common 能力不足时的处理

> **【强制】** 当 common 模块现有能力无法满足业务需求时，遵循以下优先级：

1. **扩展 common 模块**：向 common 模块提交 PR 扩展能力（如新增 QueueType、新增序列化器）
2. **组合调用**：通过组合多个 common API 实现业务需求（如 `MessageDeduplicator` + `RetryPolicy`）
3. **业务层薄封装**：仅当语义差异较大时，在业务模块创建薄封装类（内部委托调用 common API）

```java
// ✅ 正确 — 扩展而非替代：在业务模块创建薄封装，内部委托 common API
@Component
public class MessagePublisherWrapper {
    private final IMessagePublisher publisher;

    public MessagePublisherWrapper(IMessageQueueProvider provider) {
        this.publisher = provider.createMessageQueue(QueueType.ROCKET)
                .createPublisher(QueueChannels.MESSAGE_TOPIC);
    }

    public void publishBusinessEvent(BusinessEvent event) {
        QueueMessage message = QueueMessage.of(YdszJson.toJson(event));
        publisher.publish(message);
    }
}
```

#### 20.4.6 通知领域专项规范（ADR-001 落地）

> **【强制】** 业务模块发送通知时，**必须使用 `ydsz-common-notify` 模块的 `NotifyHelper` 作为统一业务入口**，禁止直接调用 `ydsz-message` 模块的内部 API 或自行构建通知请求。

##### 架构定位

根据 ADR-001（`docs/module-review/ADR-001-notify-message-convergence.md`）决策：

- `ydsz-common-notify` 是唯一通知业务入口（`NotifyHelper`）
- `ydsz-message` 退化为通道 Provider，通过 `NotifyChannelBridgeConfiguration` 自动桥接
- 业务模块不感知通道具体实现，仅依赖 `NotifyHelper`

##### 禁止行为

```java
// ❌ 错误 — 业务模块直接使用 MessageChannel（ydsz-message 内部 API）
@Autowired
private MessageChannel dingTalkChannel; // 违反 ADR-001

// ❌ 错误 — 业务模块自行构建通知请求
NotifyRequest request = new NotifyRequest();
request.setChannel("DINGTALK");
notifyService.send(request);

// ✅ 正确 — 统一使用 NotifyHelper
@Autowired
private NotifyHelper notifyHelper;

notifyHelper.sendDingTalk(webhookUrl, title, content);
notifyHelper.sendFeishu(webhookUrl, title, content);
notifyHelper.sendWeCom(webhookUrl, title, content);
notifyHelper.sendInApp(userId, title, content);
notifyHelper.sendEmail(to, subject, content);
notifyHelper.sendSystemAlert(title, content);
```

##### 跨模块告警事件

> **【强制】** 业务模块的跨模块告警/事件通知，必须通过 `UnifiedAlertEvent` 事件总线发布，由统一的告警分发器消费并委托 `NotifyHelper` 发送，禁止各模块自建告警分发逻辑。

```java
// ✅ 正确 — 发布事件，由总线统一处理
applicationEventPublisher.publishEvent(
    new UnifiedAlertEvent(this, alertType, channels, target, title, content));

// ❌ 错误 — 模块内直接调用通知 API
if (alertType.equals("DINGTALK")) {
    notifyHelper.sendDingTalk(url, title, content);
} else if (alertType.equals("FEISHU")) {
    notifyHelper.sendFeishu(url, title, content);
}
```

##### 通道扩展

> **【强制】** 如需新增通知通道，必须通过实现 `NotifyChannelStrategy` SPI 接口注册为 Spring Bean，禁止修改 `NotifyHelper` 或 `NotifyServiceImpl` 内部代码（开闭原则）。

```java
// ✅ 正确 — 通过 SPI 扩展通道
@Component
@ConditionalOnProperty(prefix = "ydsz.notify.sms", name = "enabled", havingValue = "true")
public class SmsNotifySender implements NotifyChannelStrategy {
    @Override
    public NotifyChannel getChannel() { return NotifyChannel.SMS; }

    @Override
    public NotifySendResult send(String receiver, String title, String content) {
        // 短信发送逻辑
    }
}
```

##### 依赖约束

> **【强制】** 业务模块的 `pom.xml` 中**仅允许声明 `ydsz-common-notify` 依赖**，禁止直接声明 `ydsz-message` 依赖（`ydsz-message` 通过 `NotifyChannelBridgeConfiguration` 运行时自动桥接）。

```xml
<!-- ✅ 正确 -->
<dependency>
    <groupId>com.njydsz</groupId>
    <artifactId>ydsz-common-notify</artifactId>
</dependency>

<!-- ❌ 错误 — 禁止直接依赖 ydsz-message -->
<dependency>
    <groupId>com.njydsz</groupId>
    <artifactId>ydsz-message-api</artifactId>
</dependency>
```

### 20.7 网络通信能力专项规范（v2.8 新增）

> **【强制】** 业务模块在实现 TCP 长连接、UDP 通信、IoT 设备接入等网络通信能力时，**必须优先使用 `ydsz-common-netty` 模块提供的抽象和组件，禁止在业务模块中重复实现相同功能**。

##### 架构定位

根据 v2.8 架构决策：

- `ydsz-common-netty` 是 TCP/UDP 网络通信的统一基座（Server/Client 抽象、编解码、SSL/TLS、断线重连、流量整形、指标监控）
- `ydsz-common-socket` 是 WebSocket 实时通信的统一基座（STOMP 协议、集群广播、在线状态、指标监控）
- 两个模块通过 `ConnectionMetrics` 接口实现指标契约共享

##### 强制规范

> **【强制】** 所有 TCP Server 必须继承 `AbstractNettyServer`，所有 TCP Client 必须继承 `AbstractNettyClient`，禁止自行封装 `Bootstrap` + `EventLoopGroup`。

> **【强制】** 编解码必须使用 `LengthFieldCodec.addToPipeline()` 一站式 API，禁止在业务代码中直接组合 `LengthFieldFrameDecoder` + `LengthFieldPrepender`。

> **【强制】** 连接管理必须使用 `ChannelGroupManager`（`addToGroup` / `broadcastToGroup` / `remove`），禁止在业务模块自建 `ConcurrentHashMap<userId, Channel>` 做双轨管理。

> **【强制】** 空闲检测必须使用 `IdleStateHandler` + `userEventTriggered` 模式，禁止在 `channelRead` 中硬编码 PING/PONG 协议级心跳判断。

> **【强制】** 网络指标必须实现 `ConnectionMetrics` 接口（`ydsz-common-netty.api` 包），保证 TCP 与 WebSocket 通道的指标契约统一。

##### 禁止行为

```java
// ❌ 错误 — 业务模块自行组合编解码器（LengthFieldCodec 已提供一站式 API）
ch.pipeline()
    .addLast(new LengthFieldFrameDecoder())
    .addLast(new LengthFieldPrepender(4))
    .addLast(new MyHandler());

// ❌ 错误 — 业务模块自建 userId→Channel 映射（ChannelGroupManager 已提供分组管理）
private final Map<String, ChannelHandlerContext> userChannelMap = new ConcurrentHashMap<>();
userChannelMap.put(userId, ctx);

// ❌ 错误 — 在 channelRead 中硬编码 PING/PONG 判断（应使用 IdleStateHandler）
if ("PING".equals(type)) {
    ctx.writeAndFlush(createPong());
}

// ✅ 正确 — 使用 LengthFieldCodec 一站式编解码
LengthFieldCodec.addToPipeline(ch.pipeline());
ch.pipeline().addLast(new MyHandler());

// ✅ 正确 — 使用 ChannelGroupManager 管理连接分组
channelGroupManager.addToGroup("user:" + userId, channel);
channelGroupManager.broadcastToGroup("user:" + userId, message);

// ✅ 正确 — 使用 IdleStateHandler + userEventTriggered 处理空闲
@Override
public void userEventTriggered(ChannelHandlerContext ctx, Object evt) {
    if (evt instanceof IdleStateEvent event) {
        if (event.state() == IdleState.READER_IDLE) {
            ctx.close();
        }
    }
}
```

##### HTTP 客户端场景说明

> **【强制】** 基于 Reactor Netty 的 HTTP 客户端（如 `WebClient`、`OpenFeign`）**不适用** `AbstractNettyClient` 抽象（后者为 raw TCP 设计）。HTTP 客户端应通过 `application.yml` 的 `ydsz.netty.*` 配置项管理连接池参数，禁止在业务代码中硬编码 `ConnectionProvider` 配置。

// ydzs.netty.max-idle-time: 30s
// ydzs.netty.pending-acquire-timeout: 10s
```

// ✅ 正确 — 委托 ydsz-common-config 的 ConfigCliTool

- 加密算法、迭代次数、池大小、Salt/IV 生成器等参数由 `ydsz-common-config` 统一管理
- 业务模块仅需提供主密码（从配置属性或环境变量获取），无需关心加密算法细节

### 23.2 配置变更监听规范

> **【强制】** 业务模块需要监听配置中心（Nacos / Apollo / Spring Cloud Config）的配置变更时，必须使用 `ydsz-common-config` 的 `ConfigChangeListener` 接口或 `@EventListener ConfigChangeEvent`，**禁止自行创建 `EnvironmentChangeEvent` / `RefreshEvent` 监听器**。

@Component

```

**规范要点**：
- `ConfigChangeBridge` 已实现属性快照、diff 计算、事件发布、监听器分发全链路
- 业务模块仅需实现 `ConfigChangeListener` 接口或监听 `ConfigChangeEvent`，无需重复造轮子
- 转换旧监听器时，确保删除原有的 `ApplicationListener<RefreshEvent>` / `ApplicationListener<EnvironmentChangeEvent>` 实现

### 23.3 多层配置合并规范

> **【强制】** 业务场景涉及多层配置合并（如：全局默认 → 环境覆盖 → 租户自定义）必须使用 `ydsz-common-config` 的 `ConfigMergeUtils`，**禁止自行实现 JSON 深度合并或手动字段覆盖逻辑**。

```java

    // 自行实现递归合并逻辑（容易遗漏 null 值删除、嵌套对象处理等边界情况）

**规范要点**：

- 合并失败时降级返回 override 配置，不抛异常

## 23. 分布式事务规范

### 23.1 Common 模块优先原则

> **【强制】** 所有跨服务、跨数据库的分布式事务场景，必须使用 `ydsz-common-seata` 提供的 `DistributedTransactionManager` 统一接口，**禁止业务代码自行实现 TCC / SAGA 编排逻辑**。

> **【强制】** 禁止业务代码直接 `import org.apache.seata.*` 原生 API，所有 Seata 能力必须通过 `com.njydsz.common.seata.*` 包访问。

**核心原则**：common 模块能力优先，业务模块不重复造轮子。

```java
// ❌ 错误 — 直接使用 Seata 原生 API
import org.apache.seata.tm.api.GlobalTransaction;
import org.apache.seata.tm.api.GlobalTransactionContext;

public class OrderService {
    public void createOrder() {
        GlobalTransaction globalTx = GlobalTransactionContext.getCurrentOrCreate();
        globalTx.begin();
        // ... 业务逻辑
    }
}

// ✅ 正确 — 使用 ydsz-common-seata 统一接口
import com.njydsz.common.seata.api.DistributedTransactionManager;
import com.njydsz.common.seata.api.TransactionType;

public class OrderService {
    private final DistributedTransactionManager txManager;

    public void createOrder() throws Exception {
        txManager.execute("createOrder", TransactionType.TCC, () -> {
            // ... 业务逻辑
            return null;
        });
    }
}
```

**违规判定标准**：
- 业务代码中出现 `import org.apache.seata.` → 违规
- 业务代码中手写 TCC Try/Confirm/Cancel 三阶段状态机 → 违规
- 业务代码中手写 SAGA 正向链 + 逆序补偿逻辑 → 违规
- `pom.xml` 中声明了 `ydsz-common-seata` 但 `enabled: false` 且无代码使用 → 幽灵依赖违规（需移除）

### 23.2 事务模式选择规范

| 模式 | 适用场景 | 业务代码职责 | 配置项 |
|------|---------|-------------|--------|
| `LOCAL` | 单机降级、非关键路径 | 无特殊要求 | `ydsz.seata.default-type=LOCAL` |
| `TCC` | 需要强一致性的资源预留（库存冻结/余额冻结） | 实现 `TccAction<T>` 接口 | `ydsz.seata.default-type=TCC` |
| `SAGA` | 长事务、多步骤、可最终一致（审批链/跨系统集成） | 构造 `SagaStep<?>` 列表 | `ydsz.seata.default-type=SAGA` |
| `SEATA_AT` | CRUD 型跨库事务、无需业务补偿 | 配合 `undo_log` 表使用 | `ydsz.seata.default-type=SEATA_AT` |

**模式选择决策树**：

```
是否需要跨服务/跨数据库？
├── 否 → 使用 Spring @Transactional（本地事务）
└── 是 → 是否需要业务层实现补偿逻辑？
    ├── 否 → SEATA_AT（自动补偿，推荐 CRUD 场景）
    └── 是 → 是否涉及多步骤长事务（>3 个服务参与）？
        ├── 是 → SAGA（编排模式）
        └── 否 → TCC（Try-Confirm-Cancel 三阶段）
```

### 23.3 TCC 使用规范

#### 23.3.1 TCC 业务接口实现

```java
import com.njydsz.common.seata.api.TccAction;
import com.njydsz.common.seata.api.TccContext;
import org.springframework.stereotype.Component;

@Component
public class InventoryTccAction implements TccAction<Boolean> {

    @Override
    public Boolean tryAction(TccContext ctx) {
        // 冻结库存：查询库存余量，插入冻结记录
        String skuId = ctx.get("skuId");
        Integer qty = ctx.get("qty");
        inventoryMapper.freeze(skuId, qty);
        return Boolean.TRUE;
    }

    @Override
    public void confirmAction(TccContext ctx) {
        // 确认扣减：将冻结记录转为实际扣减
        String skuId = ctx.get("skuId");
        Integer qty = ctx.get("qty");
        inventoryMapper.deductFrozen(skuId, qty);
    }

    @Override
    public void cancelAction(TccContext ctx) {
        // 取消释放：解冻库存
        String skuId = ctx.get("skuId");
        Integer qty = ctx.get("qty");
        inventoryMapper.unfreeze(skuId, qty);
    }
}
```

#### 23.3.2 TCC 调用规范

```java
// ✅ 正确 — 通过 TccTransactionManager 调用（自动处理空回滚/悬挂/幂等）
tccTransactionManager.executeTcc("deductInventory", inventoryTccAction);

// ❌ 错误 — 手动调用 tryAction，跳过框架防护
inventoryTccAction.tryAction(ctx);  // 失去空回滚/悬挂/幂等保护
```

#### 23.3.3 TCC 日志存储

| 环境 | 要求 | 配置 |
|------|------|------|
| 开发/测试 | `memory`（默认） | `ydsz.seata.tcc-log-store=memory` |
| 生产 | `redis`（必须） | `ydsz.seata.tcc-log-store=redis` |

> **【强制】** 生产环境必须使用 `redis` 存储 TCC 事务日志，确保跨实例恢复能力。所有参与同一分布式事务的服务必须使用相同的 `ydsz.seata.tcc-log-redis-key-prefix`。

### 23.4 SAGA 使用规范

#### 23.4.1 SAGA 步骤定义

```java
import com.njydsz.common.seata.api.SagaStep;
import java.util.List;

List<SagaStep<Void>> steps = List.of(
    SagaStep.of("deduct",
        () -> { accountMapper.deduct(fromId, amount); return null; },
        () -> { accountMapper.add(fromId, amount); }),
    SagaStep.of("add",
        () -> { accountMapper.add(toId, amount); return null; },
        () -> { accountMapper.deduct(toId, amount); })
);

// 执行编排
sagaOrchestrator.execute("transfer", steps);
```

#### 23.4.2 SAGA 补偿原则

> **【强制】** `SagaStep.of()` 的 `compensation` 必须能撤销 `forwardAction` 的副作用，补偿操作必须幂等。

> **【推荐】** 不可逆的最后一步使用 `SagaStep.terminal()` 创建（如发送通知、写入审计日志），失败时不触发补偿。

### 23.5 XID 跨服务传播规范

> **【强制】** 服务间通过 Feign 调用且存在活跃分布式事务时，必须确保 `FeignXidRequestInterceptor` 在 Spring 容器中注册。

> **【强制】** 下游服务必须确保 `XidServletFilter` 在 Spring 容器中注册，自动接收上游传播的 XID。

> **【推荐】** 生产环境必须启用 XID 签名校验，配置 `ydsz.seata.xid-sign-secret`。

## 24. Feign 远程调用规范

> **版本**：v1.0（2026-08-16 新增）  
> **适用范围**：所有使用 `ydsz-common-feign` 的跨服务 FeignClient 接口

### 24.1 核心原则：业务模块优先使用 common 模块能力

> **【强制】** 业务模块在实现跨服务 Feign 调用时，**必须优先使用 `ydsz-common-feign` 提供的公共能力**，禁止重复造轮子。

| 公共能力 | 所在模块 | 业务模块要求 |
|----------|----------|-------------|
| Feign 自动配置 | `ydsz-common-feign` | 通过 `@EnableYdszFeign` 启用，**禁止**使用原生 `@EnableFeignClients` |
| 服务名常量 | `FeignClientConstants` | FeignClient `name` 属性必须使用常量，**禁止**硬编码服务名字符串 |
| 路径常量 | `FeignClientConstants` | URL 路径必须使用常量，**禁止**硬编码路径字符串 |
| HTTP 连接池/超时 | `ydsz.feign.*` 配置项 | 通过 `application.yml` 调整，**禁止**自建 `Feign.Builder` |
| 分布式跟踪 | `FeignRequestInterceptor`（traceparent 注入） | 自动生效，**禁止**手动拼接 TraceId Header |
| 服务降级统一错误码 | `FeignClientConstants.FEIGN_SERVICE_UNAVAILABLE` | Fallback 必须返回此错误码，**禁止**返回 `success(null)` / `success(emptyList)` |
| ID→名称富化 | `NameAssembler` 接口 | 禁止自建同类批量查询逻辑 |

### 24.2 FeignClient 注解规范

> **【强制】** `@FeignClient` 的 `name` 属性必须使用 `FeignClientConstants` 中定义的常量。

```java
// ✅ 正确
@FeignClient(name = FeignClientConstants.WORKFLOW, contextId = "workflowClient",
        fallbackFactory = WorkflowClientFallback.class)

// ❌ 错误 — 硬编码服务名
@FeignClient(name = "ydsz-workflow", contextId = "workflowClient")
```

> **【强制】** `@PostMapping` / `@GetMapping` 等路径必须使用 `FeignClientConstants` 中的路径常量。

```java
// ✅ 正确
@PostMapping(FeignClientConstants.WORKFLOW_PATH_START)
BaseResponse<String> startProcess(@RequestBody Map<String, Object> body);

// ❌ 错误 — 硬编码路径
@PostMapping("/api/v1/workflow/engine/instance/start")
BaseResponse<String> startProcess(@RequestBody Map<String, Object> body);
```

> **【建议】** 新增服务或路径常量时，先在 `FeignClientConstants` 中定义，再使用。

### 24.3 Fallback 降级规范

> **【强制】** FeignClient 必须定义 Fallback 处理（优先使用 `FallbackFactory` 而非 `fallback` 属性），保证目标服务不可用时调用方有明确感知。

> **【强制】** Fallback 中所有返回 `BaseResponse` 的方法必须返回 `BaseResponse.error(FeignClientConstants.FEIGN_SERVICE_UNAVAILABLE, "xxx服务不可用")`，**严禁**返回以下形式：

| 禁止形式 | 问题 |
|----------|------|
| `BaseResponse.success(null)` | 调用方 `isSuccess()` 返回 true，误判为成功 |
| `BaseResponse.success(Collections.emptyList())` | 调用方误认为查询结果为空（实际是服务不可用） |
| `BaseResponse.success()` | 操作类接口误判为执行成功 |
| `BaseResponse.success(false)` | 布尔校验接口误判为校验失败（实际是服务不可用） |

```java
// ✅ 正确 — 返回统一错误码
@Override
public BaseResponse<String> trigger(String jobId) {
    log.warn("[CronjobClient] trigger 降级: jobId={}", jobId);
    return BaseResponse.error(FeignClientConstants.FEIGN_SERVICE_UNAVAILABLE, "定时任务服务不可用");
}

// ❌ 错误 — 返回 success(null)
@Override
public BaseResponse<String> trigger(String jobId) {
    return BaseResponse.success(null);
}
```

> **【强制】** Fallback 类必须使用 `@Slf4j` 注解，并在降级时输出 WARN 日志，记录降级原因和关键参数。

### 24.4 NameAssembler ID→名称富化规范

> **【强制】** 跨服务查询 ID → 名称映射（如 userId→userName、deptId→deptName）时，必须使用 `NameAssembler` 接口，**禁止**在各模块中自建同类批量查询逻辑。

```java
// ✅ 正确 — 注入 NameAssembler
@Autowired
private NameAssembler nameAssembler;

Map<String, String> userNames = nameAssembler.batchResolveNames(NameType.USER, userIds);

// ❌ 错误 — 自建 Feign 调用 + 手动拼 Map
// 应在 userinfo-api 中暴露 batch-names 接口，通过 OrgQueryClient.batchUserNames() 调用
```

> **【建议】** 提供本地数据源的业务模块应实现 `NameAssembler` 接口并标注 `@Component`，替换默认的 `NoOpNameAssembler`。

### 24.5 FeignClient 命名与 contextId 规范

> **【强制】** 同一业务模块内若存在多个调用同一服务的 FeignClient，必须通过 `contextId` 区分，避免 Bean 名称冲突。

> **【建议】** FeignClient 接口命名以 `Client` 结尾（如 `WorkflowServiceClient`），Fallback 类命名以 `Fallback` 或 `FallbackFactory` 结尾。

### 24.6 配置项使用规范

> **【强制】** Feign 相关配置（超时、重试、连接池、熔断、Bulkhead 等）必须通过 `application.yml` 的 `ydsz.feign.*` 命名空间调整，**禁止**在代码中硬编码或通过 `@Bean` 覆盖 `ydsz-common-feign` 的默认配置（确有需求时应先反馈给 common 模块负责人）。

| 常用配置项 | 默认值 | 说明 |
|-----------|--------|------|
| `ydsz.feign.timeout.connect` | 5000ms | 连接超时 |
| `ydsz.feign.timeout.read` | 10000ms | 读取超时 |
| `ydsz.feign.retry.max-attempts` | 3 | 最大重试次数 |
| `ydsz.feign.client.max-connections` | 200 | HTTP 连接池总连接数 |
| `ydsz.feign.client.max-per-route` | 50 | 单路由最大连接数 |

### 24.7 接入 Checklist

业务模块首次接入 FeignClient 时，需完成以下步骤：

- [ ] `pom.xml` 中添加 `ydsz-common-feign` 依赖
- [ ] 启动类或配置类上添加 `@EnableYdszFeign` 注解
- [ ] FeignClient 接口 `name` 属性使用 `FeignClientConstants` 常量
- [ ] 所有 URL 路径使用 `FeignClientConstants` 对应路径常量
- [ ] 定义 FallbackFactory（返回 `FEIGN_SERVICE_UNAVAILABLE` 错误码）
- [ ] 在 `application.yml` 中按需调整超时/重试配置
- [ ] 涉及 ID→名称富化的场景，使用 `NameAssembler` 接口

## 25. 领域事件规范

> **核心原则：业务模块必须优先使用 common 模块的事件发布能力，禁止重复造轮子。**
>
> 领域事件（Domain Event）是 DDD 中用于表示"已发生事实"的跨模块通信载体。
> 本规范统一事件的发布入口、类型注册、消费方式，确保模块间事件契约清晰、可追溯。

### 25.1 事件发布入口（强制）

**规则 25.1.1**：业务模块发布领域事件**必须**使用 `DomainEventPublisher` 统一门面，**禁止**直接注入 `OutboxService` 或手动构建 `OutboxMessage`。

```java
// ✅ 正确：使用统一门面
private final ObjectProvider<DomainEventPublisher> eventPublisherProvider;

public void doSomething() {
    DomainEventPublisher publisher = eventPublisherProvider.getIfAvailable();
    if (publisher != null) {
        publisher.publish(DomainEvent.builder()
                .aggregateType("Order")
                .aggregateId(order.getId())
                .eventType(DomainEventTypes.ORDER_CREATED)
                .metadata("amount", order.getAmount())
                .build());
    }
}

// ❌ 错误：直接使用 OutboxService（重复造轮子）
private final ObjectProvider<OutboxService> outboxServiceProvider;
// outboxService.appendToOutbox(OutboxMessage.builder()...)
```

**理由**：`DomainEventPublisher` 封装了可选依赖降级、异常处理、JSON 序列化逻辑。
重复实现会导致 150+ 行代码冗余、降级行为不一致、异常处理遗漏等典型问题。

**规则 25.1.2**：**废弃** `EventStore` 接口（`@Deprecated 1.8.0`）。新代码不得实现或注入该接口。
如需事件发布能力使用 `DomainEventPublisher`；如需直接写入 Outbox 使用 `OutboxService.appendToOutbox(DomainEvent)`。

### 25.2 事件类型注册（强制）

**规则 25.2.1**：所有跨模块事件类型**必须**在 `DomainEventTypes` 中注册为常量，**禁止**使用字符串字面量。

```java
// ✅ 正确：事件类型在 DomainEventTypes 集中注册
public void onProjectCreated(Project project) {
    publisher.publish(DomainEvent.builder()
            .eventType(DomainEventTypes.PROJECT_INITIATION_CREATED)  // 常量引用
            .build());
}

// ❌ 错误：使用字符串字面量（失去编译期检查）
public void onProjectCreated(Project project) {
    publishEvent("PROJECT_INITIATION_CREATED", ...);  // 字符串硬编码
}
```

**规则 25.2.2**：`DomainEventTypes` 遵循"活类型原则"——仅注册有实际发布方或消费方的事件类型。
无头事件类型（定义但无人使用）必须在代码清理时移除，避免注册表膨胀导致认知负担。

**规则 25.2.3**：命名格式 `{MODULE}_ENTITY_ACTION`（如 `ORDER_CREATED`、`USER_DISABLED`），使用过去时或完成时语态。
每个常量 Javadoc 必须注明发布方模块与消费方模块。

### 25.3 事件消费方式（强制）

**规则 25.3.1**：消费 Outbox 事件时必须使用 `@EventListener(condition = "...")` SpEL 引用 `DomainEventTypes` 常量：

```java
// ✅ 正确：SpEL 引用常量
@Async
@EventListener(condition = "#message.eventType == T(com.njydsz.common.event.api.DomainEventTypes).FLOW_INSTANCE_APPROVED")
public void onFlowApproved(OutboxMessage message) { ... }

// ❌ 错误：字符串硬编码条件
@EventListener(condition = "#message.eventType == 'FLOW_INSTANCE_APPROVED'")
public void onFlowApproved(OutboxMessage message) { ... }
```

**规则 25.3.2**：监听器必须为异步（`@Async`），异常必须 try-catch 吞掉（不能因消费失败回滚发布方事务）。

**规则 25.3.3**：空壳监听器（仅 `log.info` 无实际业务逻辑）必须删除，避免无意义的 Outbox 流量与日志噪音。

### 25.4 可选依赖注入模式（强制）

**规则 25.4.1**：`DomainEventPublisher` / `OutboxService` 等 common 能力在业务模块中**必须**使用 `ObjectProvider<T>` 可选注入，实现安全降级：

```java
// ✅ 正确：ObjectProvider 可选注入
private final ObjectProvider<DomainEventPublisher> eventPublisherProvider;

// ❌ 错误：直接注入（common-event 未引入时启动失败）
private final DomainEventPublisher eventPublisher;
```

### 25.5 metadata 传输规范（建议）

**规则 25.5.1**：事件 payload 使用 `DomainEvent.metadata(key, value)` Map 结构传输扩展字段，**禁止**构建独立的 JSON 对象再序列化为 payload 字符串（这是 `OutboxMessage.builder().payload()` 的旧用法）。

```java
// ✅ 正确：metadata Map
publisher.publish(DomainEvent.builder()
        .aggregateType("FlowInstance")
        .aggregateId(instanceId)
        .eventType(DomainEventTypes.FLOW_INSTANCE_REJECTED)
        .metadata("rejectReason", dto.getComment())
        .metadata("operatorId", dto.getUserId())
        .build());

// ❌ 错误：手动 JSON 序列化构建 payload
String payload = YdszJson.toJson(payloadMap);
outboxService.appendToOutbox(OutboxMessage.builder()...payload(payload));
```

**规则 25.5.2**：metadata 字段应精简（≤10 个键），仅携带消费方必须的字段。大对象（如完整实体）不放入 metadata，通过 aggregateId 按需查询。

### 25.6 事件发布 Checklist

业务模块新增事件发布时，需完成以下检查：

- [ ] `DomainEventTypes` 中已注册对应常量（含发布方/消费方 Javadoc）
- [ ] 使用 `DomainEventPublisher` 注入，未直接使用 `OutboxService`
- [ ] 事件类型字段引用 `DomainEventTypes.XXX` 常量，未使用字符串字面量
- [ ] 监听器使用 `T(com.njydsz.common.event.api.DomainEventTypes).XXX` SpEL 引用
- [ ] 监听器为 `@Async` + try-catch 吞异常
- [ ] 事件发布在事务内执行（配合 Outbox afterCommit 机制保证一致）
- [ ] metadata 精简，未塞入完整实体对象

## 27. 可观测性统一接入规范（v2.8 新增）

> **版本**：v1.0
> **生效日期**：2026-08-16
> **适用范围**：ydsz-cloud 全部 Java 模块的指标采集、链路追踪、告警发布、熔断降级、SLA 上报
> **规范目的**：消除各业务模块重复自建可观测性能力（重复造轮子）的现状，将 ydsz-common-sentry 确立为全系统唯一的可观测性基座

### 27.1 核心原则：sentry 优先，禁止重复造轮子

> **【强制】** 所有业务模块的可观测性需求（指标采集、链路追踪、告警发布、熔断降级、SLA 上报）必须使用 `ydsz-common-sentry` 模块提供的统一能力，**禁止**在业务模块中自建对应实现。

```java
// ❌ 错误 — 业务模块自建指标注册
@Service
public class MyService {
    private final MeterRegistry meterRegistry;

    public MyService(MeterRegistry meterRegistry) {
        this.meterRegistry = meterRegistry;
    }

    public void doWork() {
        Counter.builder("my_module_work_total")
            .tag("status", "success")
            .register(meterRegistry)
            .increment();
    }
}

// ✅ 正确 — 使用 sentry 统一入口
@Service
public class MyService {

    public void doWork() {
        SentryObservation.count("work.total", "业务处理总数", Map.of("status", "success"));
    }
}
```

### 27.2 指标采集（MetricsCollector SPI）

#### 27.2.1 禁止直接操作 MeterRegistry

> **【强制】** 业务模块**禁止**直接注入 `io.micrometer.core.instrument.MeterRegistry` 注册指标，禁止继承 `AbstractModuleMetrics` 基类注册指标。所有指标上报必须通过 `SentryObservation.count/time/gauge/histogram` 方法。

```java
// ❌ 错误 — 直接操作 MeterRegistry
Counter.builder("order.create.total").register(meterRegistry).increment();

// ❌ 错误 — 继承 AbstractModuleMetrics
@Component
public class OrderMetrics extends AbstractModuleMetrics {
    public OrderMetrics(MeterRegistry registry) {
        super(registry, "ydsz_order_");
    }
}

// ✅ 正确 — 通过 sentry 上报
SentryObservation.count("order.create.total", "订单创建总数", Map.of("channel", "app"));
```

#### 27.2.2 指标命名规范

> **【强制】** 指标名必须遵循 `{业务域}.{实体}.{动作}` 三段式命名，使用小写英文 + 点分隔。

| 正确示例 | 错误示例 |
|---------|---------|
| `order.create.total` | `ORDER_CREATE_TOTAL`（大写+下划线） |
| `order.create.duration` | `orderCreateDuration`（驼峰） |
| `agent.invoke.success` | `agentInvoke`（太简单） |

#### 27.2.3 维度标签规范

> **【强制】** 指标维度标签（tag）的 key 使用 snake_case，value 必须为有限枚举值，禁止使用用户输入、请求 ID 等高基数数据作为标签值。

```java
// ✅ 正确 — 有限枚举值
SentryObservation.count("order.create.total", "订单创建总数",
    Map.of("channel", "app",        // 枚举：app/web/api
         "status", "success"));    // 枚举：success/fail/timeout

// ❌ 错误 — 高基数标签
SentryObservation.count("order.create.total", "订单创建总数",
    Map.of("userId", user.getId(),       // 高基数！
         "requestId", requestId));       // 高基数！
```

### 27.3 链路追踪（TraceContext SPI）

#### 27.3.1 禁止自建 traceId 管理

> **【强制】** 业务模块**禁止**自建 traceId 生成、传递、MDC 管理逻辑。所有链路追踪必须使用 `SentryService.traceId()` / `SentryService.tag()` 或 sentry 的 `TraceContext` SPI。

```java
// ❌ 错误 — 自建 MDC traceId 管理
MDC.put("traceId", UUID.randomUUID().toString());
try {
    biz();
} finally {
    MDC.clear();
}

// ✅ 正确 — 使用 sentry 追踪上下文
String traceId = SentryService.traceId();
SentryService.tag("orderId", orderId);
```

#### 27.3.2 W3C TraceContext 传播

> **【推荐】** 跨服务调用时，traceparent/tracestate 头的注入由 sentry 的 `FeignRequestInterceptor` 自动完成，业务代码无需手动处理。

### 27.4 告警发布（AlertConverger + AlertPublisher）

#### 27.4.1 禁止 log.warn/error 作为告警通道

> **【强制】** 业务模块**禁止**通过 `log.warn()`/`log.error()` 直接输出告警信息。所有告警事件必须通过 `SentryObservation.alert()` 经 `AlertConverger` 收敛后发布。

```java
// ❌ 错误 — 使用日志作为告警
log.warn("订单创建失败率超过阈值：当前 {}%", failureRate);

// ✅ 正确 — 通过 sentry 发布告警
SentryObservation.alert(AlertEvent.builder()
    .severity(AlertSeverity.P1)
    .message("订单创建失败率超阈值")
    .tag("failure_rate", String.valueOf(failureRate))
    .tag("threshold", "10")
    .build());
```

#### 27.4.2 告警严重级别定义

| 级别 | 场景 | 响应 SLA |
|------|------|---------|
| P0 | 核心服务不可用、数据丢失 | 5 分钟 |
| P1 | 非核心服务降级、失败率 > 10% | 15 分钟 |
| P2 | 性能劣化、偶发超时 | 1 小时 |
| P3 | 预警、容量提醒 | 1 天 |

### 27.5 熔断降级（CircuitBreaker）

#### 27.5.1 禁止自建熔断器

> **【强制】** 业务模块**禁止**自建熔断器实现（包括基于 AtomicInteger 的手动状态机、Resilience4j 直接调用等）。所有熔断降级必须使用 sentry 提供的 `CircuitBreaker` 封装。

```java
// ❌ 错误 — 自建熔断器
private final AtomicInteger failureCount = new AtomicInteger(0);
private volatile boolean circuitOpen = false;

// ✅ 正确 — 使用 sentry 熔断器
SentryService.circuitBreaker("orderService").executeSupplier(() -> orderService.create(dto));
```

### 27.6 SLA 上报（@SlaMetric 注解）

#### 27.6.1 禁止自建性能统计

> **【推荐】** 业务关键方法的 SLA（耗时、成功率）通过 `@SlaMetric` 注解声明式采集，禁止自建耗时统计和慢请求检测逻辑。

```java
// ❌ 错误 — 自建慢请求检测
long start = System.currentTimeMillis();
biz();
long cost = System.currentTimeMillis() - start;
if (cost > 1000) {
    log.warn("慢操作：{}ms", cost);
}

// ✅ 正确 — 使用 @SlaMetric 自动采集
@SlaMetric(name = "order.create", thresholdMillis = 1000)
public void create(OrderDTO dto) {
    // 业务逻辑
}
```

### 27.7 模块接入清单

#### 27.7.1 Pom 依赖显式声明

> **【强制】** 业务模块在 pom.xml 中必须**显式声明** `ydsz-common-sentry` 依赖，不得仅依赖传递引入。

```xml
<!-- ✅ 正确 — 显式声明 common-sentry -->
<dependency>
    <groupId>com.njydsz</groupId>
    <artifactId>ydsz-common-sentry</artifactId>
</dependency>

    <groupId>com.njydsz</groupId>
    <artifactId>ydsz-common-docs</artifactId>
</dependency>
```

PII 脱敏能力需 `ydsz-common-safe`（通常通过 `ydsz-common-web` 传递引入）；临时文件管理需 `ydsz-common-util`（L3 基础依赖，默认已传递）。

#### 29.3.3 接入模式

业务模块接入统一文档处理需完成以下步骤：

**步骤 1：注入 DocumentService 解析文档**

```java
@Service
@RequiredArgsConstructor
public class XxxService {
    private final DocumentService documentService;

    public String extractText(InputStream stream, String fileName) {
        DocumentParseResult result = documentService.parseAndPreprocess(stream, fileName, null);
        if (!result.isSuccess()) {
            throw new BusinessException("文档解析失败: " + result.getErrorMessage());
        }
        return result.getContent().getText();
    }
}
```

**步骤 2：使用 SensitiveUtil 执行 PII 脱敏**

```java
// 对解析后的文本执行 PII 扫描并脱敏
String safeText = SensitiveUtil.scanAndMask(rawText);
```

**步骤 3：使用 TempFileManager 管理临时文件**

```java
private final TempFileManager tempFileManager;

public void processLargeFile(InputStream stream) throws IOException {
    Path tempFile = tempFileManager.createAndWrite("xxx-", ".tmp", stream);
    try {
        // 处理临时文件...
    } finally {
        tempFileManager.deleteTracked(tempFile);
    }
}
```

### 29.4 禁止行为

#### 29.4.1 禁止自建文档解析逻辑

```java
// ❌ 错误 — 自建 PDF/Office 解析

```

```java
// ❌ 错误 — 自建手机号正则扫描
private static final Pattern PHONE_PATTERN = Pattern.compile("^1[3-9]\\d{9}$");
public static String maskMobile(String mobile) { ... }

// ✅ 正确 — 使用 SensitiveUtil（正则统一维护）

```

#### 29.4.3 禁止自建临时文件管理

```java
// ❌ 错误 — 自建临时文件（无跟踪、无 ShutdownHook 兜底）

// ... 可能遗漏清理

// ✅ 正确 — 使用 TempFileManager

try { ... } finally { tempFileManager.deleteTracked(tempFile); }
```

在实现以下功能前，必须确认 `ydsz-common-docs` / `ydsz-common-safe` / `ydsz-common-util` 是否已提供：

### 29.6 common 能力不足时的处理

> **【强制】** 当 `ydsz-common-docs` 现有能力无法满足业务需求时，遵循以下优先级：

3. **业务层薄封装**：仅当语义差异较大时，在业务模块创建薄封装类（内部委托调用 common API）

## 24. 审计日志规范

### 24.1 核心原则：common-audit 优先

> **【强制】** 所有业务模块的操作审计必须使用 `ydsz-common-audit` 模块提供的统一能力，**禁止**在业务模块中自建操作日志表、独立的审计采集器或重复实现审计落库逻辑。

```java
// ❌ 错误 — 业务模块自建操作日志表和写入逻辑
@Entity
@TableName("ydsz_biz_operation_log")
public class BizOperationLog { ... }

@Service
public class BizAuditService {
    public void record(String userId, String action) {
        // 独立实现审计数据落库
        BizOperationLog log = new BizOperationLog();
        bizAuditMapper.insert(log);
    }
}

// ✅ 正确 — 使用 ydsz-common-audit 统一能力
@Audit(module = "业务模块", type = AuditType.OPERATION, action = AuditAction.CREATE,
        content = "'操作描述: ' + #param.name")
public void doSomething(SomeParam param) {
    // 切面自动拦截并记录审计
}
```

### 24.2 审计注解使用规范

#### 24.2.1 必须添加 @Audit 的场景

| 场景 | 注解示例 |
|------|--------|
| 用户写操作（增/删/改） | `@Audit(module = "模块", action = AuditAction.CREATE, content = "...")` |
| 敏感查询（导出/批量获取） | `@Audit(module = "模块", action = AuditAction.EXPORT, content = "'导出'")` |
| 权限变更（角色/菜单/配置） | `@Audit(module = "权限", action = AuditAction.UPDATE, content = "...")` |
| 认证事件（登录/登出/刷新Token） | `@Audit(module = "认证", action = AuditAction.CREATE, content = "'用户登录'")` |

#### 24.2.2 SpEL content 规范

> **【推荐】** `content` 字段使用 SpEL 表达式动态构建操作描述，格式为 `'操作对象: ' + #param.field`，便于审计查询与展示。

> **【强制】** `type` 和 `action` 必须使用枚举常量（`AuditType` / `AuditAction`），禁止传整数字面量。

```java
// ✅ 正确
@Audit(module = "用户管理", type = AuditType.OPERATION, action = AuditAction.CREATE,
        content = "'创建用户: ' + #userDTO.username")

// ❌ 错误 — 硬编码 action 为整数
@Audit(module = "用户管理", type = 1, action = 1, content = "创建用户")
```

#### 24.2.3 事件驱动审计（非 Web 场景）

> **【推荐】** 在非 Web 场景（如消息消费者、定时任务、RPC 回调）中，由于无法使用 `@Audit` 注解（无 Servlet 上下文），应通过事件发布方式记录审计：

```java
// 消息消费者中
@Service
public class EventConsumer {
    private final ApplicationEventPublisher eventPublisher;

    @RocketMQMessageListener(topic = "events")
    public void onMessage(EventMessage msg) {
        // 业务逻辑...

        // 发布审计事件（无事务场景下自动触发 fallback）
        eventPublisher.publishEvent(OperationLogEvent.builder()
                .module("事件消费")
                .action("PROCESS")
                .userId(msg.getUserId())
                .bizId(msg.getBizId())
                .status("SUCCESS")
                .costMs(processingTime)
                .traceId(msg.getTraceId())
                .tenantId(msg.getTenantId())
                .build());
    }
}
```

### 24.3 审计配置规范

#### 24.3.1 必须配置项

```yaml

### 24.4 审计数据生命周期

| 阶段 | 操作方式 | 触发条件 |
|------|---------|--------|
| 创建 | 切面/事件 → `AuditRecorder` 异步写入 | 每次 @Audit 标注方法执行 |
| 查询 | 通过 `AuditQueryService` 分页查询 | 运营后台展示、链路追踪 |
| 清理 | cronjob `LogCleaner` 联动 `cleanExpiredLogs` | 每天凌晨 3 点，清除 retentionDays 前数据 |

> **【强制】** 审计日志的清理**必须**通过 `JdbcAuditStorage#cleanExpiredLogs(int)` 统一清理，禁止业务代码直接 DELETE 审计表。

### 24.5 网关审计集成

> **【强制】** Spring Cloud Gateway（响应式栈）必须通过 `GatewayAuditEventBridge` 桥接审计事件，**禁止**绕过 common-audit 模块独立实现审计日志。

审计数据流：
```
Gateway Filter → GatewayAuditEventBridge#publishAuditEvent(Mono<Void>)
    → ApplicationEventPublisher#publishEvent(OperationLogEvent)
    → @Async AuditEventListener → AuditRecorder → sys_audit_log
```

> **【强制】** 网关审计日志与业务模块审计日志**统一存储**在 sys_audit_log 表中，使用 `module="网关路由"` 区分来源。

| 接口 | 方法 | 用途 |
|------|------|------|
| `/api/v1/admin/audit/logs` | GET | 按时间范围分页查询 |
| `/api/v1/admin/audit/operator/{id}` | GET | 按操作人查询 |
| `/api/v1/admin/audit/action/{code}` | GET | 按行为查询 |

### 24.7 审计链路追踪关联

> **【强制】** 审计记录必须携带 `traceId`，用于跨服务的操作链路追踪。

> **【强制】** 网关层的审计记录 `traceId` 必须与下游业务模块的审计记录 `traceId` 一致（通过请求头透传 X-Trace-Id）。

### 24.8 违规判定标准

| 违规行为 | 严重级别 | 处理 |
|---------|---------|------|
| 业务模块自建操作日志表（如 ydsz_xxx_log）用于审计 | P0 阻断 | 必须接入 ydsz-common-audit |
| 业务模块直接 INSERT sys_audit_log | P1 警告 | 改用 @Audit 注解或事件发布 |
| 业务模块独立实现审计清理脚本 | P1 警告 | 纳入 cronjob LogCleaner 统一清理 |
| 网关侧审计不通过桥接器，直接写文件或独立存储 | P1 警告 | 必须使用 GatewayAuditEventBridge |
| 未配置 `ydsz.audit.retention-days` 导致审计数据无限增长 | P2 建议 | 添加保留策略 |

## 26. 认证授权标准用法

> **版本**：v1.0
> **生效日期**：2026-08-16
> **适用范围**：ydsz-cloud 全部业务模块的认证授权实现

### 26.1 核心原则：common-auth 优先，禁止重复造轮子

> **【强制】** 所有业务模块的认证、授权、数据权限控制必须使用 `ydsz-common-auth` 模块提供的统一能力，**禁止**在业务模块中自建 JWT 解析器、权限评估器、数据权限过滤逻辑或 Token 黑名单管理。

```java
// ❌ 错误 — 业务模块自建 JWT 校验和权限判断
@Service
public class MyAuthService {
    public boolean checkPermission(String token, String permission) {
        Claims claims = Jwts.parser().verifyWith(key).build().parseSignedClaims(token);
        List<String> roles = claims.get("roles", List.class);
        return roles.contains(permission);
    }
}

// ✅ 正确 — 使用 ydsz-common-auth 统一能力
@AuthApiPermission(apiCodes = PermissionCodes.MY_MODULE_CREATE)
public void doSomething(SomeParam param) {
    // AuthPermissionAspect 统一拦截并校验权限
}
```

### 26.2 模块接入标准模式

#### 26.2.1 Pom 依赖显式声明

> **【强制】** 业务模块在 pom.xml 中必须**显式声明** `ydsz-common-auth` 依赖，不得仅依赖传递引入。

```xml
<!-- ✅ 正确 — 显式声明 common-auth -->
<dependency>
    <groupId>com.njydsz</groupId>
    <artifactId>ydsz-common-auth</artifactId>
</dependency>
```

#### 26.2.2 启动注解启用

> **【强制】** 业务模块的 Spring Boot 启动类必须标注 `@EnableYdszAuth`，启用 auth 模块的自动配置。

```java
@SpringBootApplication
@EnableYdszAuth  // 启用 auth 模块全局能力
public class MyApplication { }
```

### 26.3 接口权限控制（@AuthApiPermission）

#### 26.3.1 权限码三段式命名规范

> **【强制】** 权限码必须遵循三段式命名：`{领域}:{资源}:{操作}`，使用小写英文 + 冒号分隔。

| 正确示例 | 错误示例 |
|---------|---------|
| `cronjob:job:create` | `CRONJOB_JOB_CREATE`（大写+下划线） |
| `agent:definition:view` | `VIEW`（太简单） |
| `workflow:task:operate` | `WORKFLOW_TASK_OPERATE`（应为小写+冒号） |

#### 26.3.2 权限码统一定位

> **【强制】** 所有权限码必须在 `ydsz-common-auth` 模块的 `PermissionCodes` 类中统一定义，禁止在业务模块内硬编码权限字符串。

#### 26.3.3 注解使用规范

> **【强制】** 所有对外暴露的 Controller 方法必须添加 `@AuthApiPermission(apiCodes = PermissionCodes.XXX)` 注解。

> **【推荐】** 查询接口也应添加权限码，遵循最小权限原则。

```java
// 查询接口 — 使用 _VIEW 后缀
@AuthApiPermission(apiCodes = PermissionCodes.MY_MODULE_VIEW)
@GetMapping("/{id}")
public BaseResponse<MyVO> getById(@PathVariable String id) { ... }

// 写接口 — 使用 _CREATE / _UPDATE / _DELETE 后缀
@AuthApiPermission(apiCodes = PermissionCodes.MY_MODULE_CREATE)
@PostMapping
public BaseResponse<MyVO> create(@RequestBody MyDTO dto) { ... }
```

### 26.4 用户上下文获取（AuthContextUtils）

#### 26.4.1 统一入口

> **【强制】** 获取当前登录用户信息必须使用 `AuthContextUtils`，禁止通过 `HttpServletRequest` 手动解析 token、禁止调用 `SecurityContextHolder` 获取认证信息、禁止自建用户信息获取工具类。

```java
// ✅ 正确 — 使用 AuthContextUtils 统一获取上下文
String userId = AuthContextUtils.getUserId();
String username = AuthContextUtils.getUsername();
String tenantId = AuthContextUtils.getTenantId();
LoginUser loginUser = AuthContextUtils.getCurrentOrNull();

// ❌ 错误 — 手动解析 token 或获取 SecurityContext
String token = request.getHeader("Authorization");
Claims claims = Jwts.parser().build().parseSignedClaims(token.substring(7));
```

#### 26.4.2 租户 ID 严格获取

> **【强制】** 获取租户 ID 时禁止使用 `getTenantIdOrDefault("1")` 硬编码兜底，必须使用严格模式：

```java
// ❌ 错误 — 硬编码兜底租户 ID（可能导致跨租户数据污染）
String tenantId = AuthContextUtils.getTenantIdOrDefault("1");

// ✅ 正确 — 严格获取
String tenantId = AuthContextUtils.getTenantId();
```

### 26.5 数据权限控制（@DataScope）

#### 26.5.1 注解适用场景

> **【推荐】** 在多租户 + 多部门场景下，Service 层的查询方法应添加 `@DataScope` 注解：

```java
// 按部门+用户过滤
@DataScope(deptColumn = "dept_id", userColumn = "created_by")
public List<MyEntity> listByCondition(MyQueryParam query) { ... }

// 仅按用户过滤（无部门维度时）
@DataScope(userColumn = "created_by")
public List<MyEntity> listMyOwn(String userId) { ... }
```

#### 26.5.2 使用 checklist

1. 确认实体表是否有对应列（`dept_id` / `user_id` / `created_by`）
2. 确认 Mapper XML 是否正确引用了注解生成的 SQL 片段
3. 集成测试覆盖：不同部门用户查询只能看到本部门数据
4. 管理员角色应配置为 ALL 范围（不受数据权限过滤限制）
5. 避免双层注解：Facade 层和实现层只保留一处

### 26.6 权限码颗粒度规范

#### 26.6.1 禁止权限码复用

> **【强制】** 不同业务操作必须使用独立权限码，禁止多个接口复用同一权限码。

```java
// ❌ 错误 — 连接器测试复用统计查看权限码
@AuthApiPermission(apiCodes = PermissionCodes.CRONJOB_STATS_VIEW)
public void testConnection() { ... }

// ✅ 正确 — 独立定义连接器管理权限码
@AuthApiPermission(apiCodes = PermissionCodes.CRONJOB_CONNECTOR_TEST)
public void testConnection() { ... }
```

#### 26.6.2 版本历史接口权限覆盖

> **【强制】** `versions`、`detail`、`compare` 等读接口必须单独控制权限，禁止因为历史版本是附属功能就跳过权限校验。

### 26.7 安全反模式清单

| 反模式 | 正确做法 |
|--------|---------|
| 手动解析 JWT token 获取用户信息 | 使用 `AuthContextUtils.getUserId()` |
| 硬编码权限字符串在 Controller 中 | 使用 `PermissionCodes` 常量引用 |
| 依赖传递引入 common-auth | pom.xml 显式声明 common-auth 依赖 |
| 跨租户查询不加租户过滤 | 使用 `@DataScope` 或框架自动注入 |
| 双层 @DataScope 注解（Facade + Impl） | 仅在实现层标注一处 |
| 权限码命名使用大写+下划线 | 使用三段式 `domain:resource:action` |
| 公共缓存服务重复实现 | 使用 auth 模块 `RolePermissionCacheService` |
| 统计查看权限码复用给其他操作 | 独立定义权限码常量 |

### 26.8 全局利用率要求

> **【推荐】** 业务模块接入 common-auth 后，应充分利用以下能力（覆盖率 ≥ 80%）：

| 能力 | 说明 |
|------|------|
| `@AuthApiPermission` | Controller 方法接口级权限 |
| `AuthContextUtils` | 用户上下文获取 |
| `@DataScope` | 行级数据权限过滤 |
| `PermissionCodes` | 统一权限码常量池 |
| `TokenBlacklistService` | Token 登出失效 |
| `@EnableYdszAuth` | 模块启动注解 |
| pom 显式声明 | Maven 依赖管理 |

### 26.9 权限预检（PermissionPreChecker）

#### 26.9.1 使用场景

> **【推荐】** 在执行业务逻辑前预检权限（而非直接抛异常），适用于前端按钮显隐控制、批量操作前校验、权限变更模拟等场景。

#### 26.9.2 API 预检

```java
@RequiredArgsConstructor
@Service
public class MyService {

    private final PermissionPreChecker preChecker;

    /**
     * 批量删除前预检：返回详细结果供前端决策是否展示确认框。
     */
    public PermissionCheckResult preCheckBatchDelete(List<String> ids) {
        return preChecker.checkApiPermissions(
            Set.of(PermissionCodes.MY_MODULE_DELETE),
            PermissionPreChecker.PermissionCheckMode.ALL
        );
    }
}
```

#### 26.9.3 @PermissionPreCheck 注解

```java
// 返回模式：预检结果注入到参数，业务方自行处理
@PermissionPreCheck(resultParamName = "checkResult")
public void batchDeleteUsers(List<Long> ids, PermissionCheckResult checkResult) {
    if (!checkResult.isCheckPassed()) {
        throw newBusinessException("您没有批量删除的权限");
    }
    // 执行业务逻辑
}

// 抛出异常模式（与普通注解行为一致）
@PermissionPreCheck(mode = PreCheckMode.THROW, checkType = CHECK_API, apiCodes = {"sys:user:delete"})
public void deleteUser(Long id) {
    // 业务逻辑
}
```

#### 26.9.4 权限预检使用 Checklist

1. 优先使用 `PermissionPreChecker` 而非手动遍历权限列表
2. 批量操作前使用 `checkApiPermissions(Set, ALL)` 统一校验
3. 前端按钮显隐使用 RETURN 模式获取 `PermissionCheckResult`
4. 微服务间调用前使用预检提前拦截无效请求
5. 避免在循环中调用预检（缓存已加载的权限）
```

## 30. 公共能力复用与反重复造轮子规范（v30-新增）

> **版本**：v2.11  
> **生效日期**：2026-08-16（v2.10 → v2.11：新增**第 30 章公共能力复用规范**，基于全局引用分析结果固化复用清单与禁止行为清单，明确"业务模块优先使用 common 模块能力，禁止重复造轮子"原则）

### 30.1 总则

**核心原则：业务模块必须优先使用 ydzs-common-* 提供的公共能力，严禁在业务模块中自建重复实现。**

在新增任何工具类、过滤器、拦截器、指标器、健康检查器之前，开发者必须确认 ydzs-common 中没有对应能力方可自建。自建实现若与 common 模块功能重叠，必须在 Code Review 阶段被拒绝。

### 30.2 必用 common 能力清单

| 能力域 | common 模块 | 公共类 | 业务模块用法 | 禁止行为 |
|--------|-------------|--------|-------------|----------|
| 统一响应 | common-base / common-web / common-app | `BaseGlobalResponseAdvice` / `GlobalResponseAdvice` / `AppGlobalResponseAdvice` | 继承后覆写 `wrapStringBody()` | 自建 `ResponseBodyAdvice` 实现相同包装逻辑 |

| 请求日志拦截 | common-base / common-web | `BaseRequestLogInterceptor` / `RequestLogInterceptor` | 继承或声明 Bean | 自建拦截器处理请求耗时计算和 MDC 设置 |

| i18n 国际化 | common-base | `BaseI18nConfiguration` / `MessageResolverRegistry` | 继承基类 + 使用 `MessageResolverRegistry` 注入 | 自建 `ReloadableResourceBundleMessageSource` |
| OpenAPI 文档 | common-base / common-web / common-app | `BaseOpenApiConfiguration` / `WebOpenApiConfiguration` | 继承 + 覆写 `apiInfo()` / `groupedOpenApi()` | 自建 `GroupedOpenApi` Bean 替代 OpenAPI 自动装配 |

### 30.4 新能力下沉原则

自建工具类确认无 common 对应能力后，**首次实现应考虑下沉到 ydzs-common** 供全项目复用：

1. **发现重复**：PR 审查时发现两个模块有相同/相似实现 → 标记为"应下沉"
2. **评估通用性**：确认 3 个以上模块有相同需求 → 必须下沉到 common
3. **选择层级**：
   - 所有 Web/App 通用 → `ydsz-common-base`
   - 仅 Web 端特有 → `ydsz-common-web`
   - 仅 App 端特有 → `ydsz-common-app`（需同时新增业务消费方激活 app-profile）
   - 与具体中间件绑定 → 对应 `ydsz-common-*` 模块（redis/safe/cache 等）
4. **迁移原代码**：业务模块改为继承 common 基类，删除原实现

### 30.5 违规自检 Checklist

- [ ] 新增的类是否与 ydzs-common-* 中某个类功能重叠？

- [ ] 是否可以直接继承 `AbstractModuleHealthIndicator` 实现健康检查？

- [ ] 自建工具类是否已评估下沉到 common 的必要性？
- [ ] 健康检查器是否仅承担健康检查职责，未混入指标转发？
