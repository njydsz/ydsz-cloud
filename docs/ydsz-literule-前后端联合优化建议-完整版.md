# ydsz-literule 前后端联合优化建议（完整版）

> **基线**：后端 ydsz-literule（312 Java 源文件）+ 前端 ydsz-micro/apps/literule-web（21 API 文件 + 9 视图页面）
> **对标**：Drools 9.x / URule Pro / QLExpress 4.1 / AviatorScript 5.4 + 互联网大厂研发规范
> **维度**：架构优化、功能增强、性能提升、体验改善、过度设计识别、前后端协同
> **方法**：代码事实为准，全部论断附类名/文件名证据；输出按 P0/P1/P2 可执行待办组织
> **日期**：2026-08-26

## 一、前后端现状基线

### 1.1 后端基线

| 维度 | 事实 |
|---|---|
| 规模 | 312 Java 文件；server 146 类；最长类 DefaultRuleEngine 1716 行、LiteRuleAutoConfiguration 1664 行 |
| 表达式引擎 | 自研 LiteExpr（ExprLexer 516 行 / ExprParser 392 行 / AST 编译缓存 / TreeInterpreter 树遍历执行） |
| 规则类型 | 表达式 / 决策表（6 命中策略）/ 评分卡 / 决策树 / 脚本（JSR-223）/ CEP（窗口计数）共 6 类 |
| 编排 | RuleChain 支持 THEN/WHEN/IF/ELIF/SWITCH 五语义 + 画布图模型 |
| 热更新 | 事件驱动 + 三级粒度 + 版本去重 + Redis Pub/Sub 广播 + Outbox 兜底 |
| 测试 | 全模块仅 4 个测试类（均在 server）；api/app/domain/infra/web 测试数为 0 |

### 1.2 前端基线

| 维度 | 事实 |
|---|---|
| 技术栈 | Vue 3 + Element Plus + Vxe-Table + ECharts + Pinia + Vue Router + TypeScript |
| 工程化 | pnpm monorepo + Turbo + Vite + Vitest + ESLint + Stylelint + Prettier + Commitlint + Lefthook |
| 规模 | 21 API 文件（auto-generated by gen-contract.py）+ 9 视图页面 + 2 语言包 |
| 路由 | 规则管理 / 看板 / DSL管理 / 规则变量 / CEP / 断点调试 / 审计日志 7 个菜单项 |
| API 覆盖 | 后端 128 个端点，前端仅覆盖约 60 个（47%），大量后端能力前端未暴露 |
| 测试 | literule-web 无 vitest.config.ts，无测试文件 |

### 1.3 前后端协同现状

| 维度 | 事实 |
|---|---|
| API 契约 | openapi.json + gen-contract.py 自动生成，契约驱动 |

#### A. 决策表管理页面（最高优先级）

**目标**：让后端决策表 8 端点真正可用

| 待办 | 描述 | 预估工时 |

| 决策表列表页 | 展示决策表列表，支持搜索、分页、启停、删除 | 1-2 天 |

## 六、过度设计识别与瘦身建议

### 6.1 后端过度设计

| # | 过度设计点 | 现状 | 建议 |
|---|---|---|---|
| 1 | SPI 层数过多 | 4 层抽象，36 个 SPI 文件 | 收敛为 2 层 |
| 2 | 分布式分片完整实现但从未使用 | ShardAwareRuleEngine + ConsistentHashSharder + NodeRegistry | 若业务无多节点诉求，整体下线 |
| 3 | 决策表 6 种命中策略 | UNIQUE/FIRST/PRIORITY/COLLECT/ANY/RULE_ORDER | 保留 FIRST/PRIORITY/COLLECT 三种高频策略 |
| 4 | 脚本规则三语言支持 | groovy/js/python 宣称，pom 无依赖 | 裁剪为 groovy+liteexpr 双轨 |
| 5 | CEP 引擎独立实现 | CEPEngine 完整实现但仅支持窗口计数 | 明确"轻量 CEP"定位 |

### 6.2 前端过度设计

| # | 过度设计点 | 现状 | 建议 |
|---|---|---|---|
| 1 | 微前端框架 | micro-kernel + micro-runtime 完整实现 | 评估实际使用率，若仅单应用运行则简化 |
| 2 | 多主题系统 | 完整的主题配置系统 | 评估是否需要多主题，若仅需单主题则简化 |
| 3 | 功能开关 | feature-flags 完整实现 | 评估实际使用场景 |

## 九、核心原则与风险提示

### 9.1 核心原则

1. **前端投资优先级高于引擎新特性**——后端 128 端点仅 60 个有前端页面，补齐页面的 ROI 远高于对齐 Drools 任何引擎特性
2. **后端空壳补真前，前端不做对应页面**——避免制造"前后端一致的假象"
3. **画布编排是差异化竞争力**——URule Pro 的核心优势就是可视化编排，补齐画布执行能力是竞争关键
4. **决策表是高频使用场景**——金融风控、营销规则等场景大量使用决策表，必须优先补齐

### 9.2 风险提示

1. **画布开发周期长**——可视化编排器开发需要 5-7 天，且交互复杂，需预留充足时间
2. **前后端类型不一致风险**——自动生成的类型定义可能与后端实际行为不一致，需人工校验
3. **测试补齐需要持续投入**——测试体系建立是长期工程，需持续投入资源
4. **微前端框架复杂度**——micro-kernel 框架增加了系统复杂度，需评估是否真正需要
