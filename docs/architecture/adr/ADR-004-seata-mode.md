# ADR-004：Seata 分布式事务模式选择

**状态：** 接受
**日期：** 2025-02-10
**决策者：** ydsz-team

## 背景与问题陈述

ydsz-cloud 作为中台系统，跨服务事务场景高频出现：workflow 引擎调用 agent 服务、message 模块触发 cronjob 执行、system 模块关联 userinfo 用户数据。单库事务无法满足跨服务调用的一致性要求。需选择 Seata 分布式事务框架的模式组合，平衡性能、一致性、团队复杂度。

## 决策驱动因素

* AT 模式无业务侵入，适合绝大多数自动提交场景
* TCC 模式强一致，适合资金、库存、关键状态机等关键链路
* SAGA 模式长事务支持，适合 cross-service 编排型流程
* 编码规范 YDIZ-TX-001~004 已对四种模式分别给出编码模板
* DynamicRoutingDataSource 多数据源切换需求与 Seata AT 代理层存在潜在冲突，需试点验证

## 考虑的选项

* **纯 TCC：** 一致性最强但每个接口需实现 Try/Confirm/Cancel，三倍编码量
* **纯 2PC（Seata XA）：** 数据库层协议支持但 MSSQL 驱动 XA 兼容性存疑，锁持有时间过长导致性能瓶颈
* **纯 AT：** 无侵入但反向 SQL 解析依赖数据库方言，MSSQL 特殊类型（如 HIERARCHYID、GEOGRAPHY）可能解析失败
* **自研事务框架：** 完全可控但跨服务两阶段提交协议复杂，消息可靠+幂等+悬挂处理缺一不可
* **组合模式（AT + TCC + SAGA）：** 按场景分工，不同链路使用不同模式

## 决策结果

选择 **组合模式：默认 AT 模式、关键链路可选 TCC、长事务使用 SAGA**，因为不同业务场景对一致性和性能的需求不同，单一模式无法兼顾，且编码规范 YDIZ-TX 系列已为每种模式提供标准模板降低学习成本。

### 正面后果

* AT 模式覆盖 80% 以上场景，业务代码零侵入
* TCC 模式应对资金、库存等强一致需求，符合 YDIZ-TX-002 规范
* SAGA 支持长事务编排，适合 workflow 跨服务流程
* 三种模式可渐进式引入，不要求一次性全量改造

### 负面后果

* 多模式并存增加理解和调试复杂度
* AT 模式的反向 SQL 解析在 MSSQL 特殊类型上存在不确定性，需试点
* DynamicRoutingDataSource 与 Seata AT 的 datasource proxy 竞争，需明确代理顺序
* TCC 模式的悬挂、空回滚、幂等问题必须在业务层自行处理

## 各选项详细对比

### 纯 TCC

* **优点：** 一致性最强，不依赖数据库日志解析，支持跨数据库和非数据库资源
* **缺点：** 每个接口需三倍编码（Try/Confirm/Cancel）；业务逻辑复杂度剧增；需自行处理空回滚、悬挂、幂等
* **评价：** 仅适合少数关键链路，全量 TCC 成本不可接受

### 纯 2PC（XA）

* **优点：** 数据库原生支持，事务提交由数据库层保证
* **缺点：** MSSQL XA 驱动兼容性存忧；锁持有时间内长，高并发下连接池耗尽风险；prepare 阶段阻塞其他事务
* **评价：** 性能风险高，不适用于 ydsz-cloud 高并发场景

### 纯 AT

* **优点：** 零业务侵入，自动反向 SQL 生成 undo_log；社区文档成熟
* **缺点：** 反向 SQL 解析依赖数据库方言，MSSQL 特殊类型可能失败；datasource proxy 与 DynamicRoutingDataSource 存在代理层冲突
* **评价：** 适合基础场景但无法覆盖长事务需求

### 自研事务框架

* **优点：** 完全可控，可针对业务特点定制
* **缺点：** 跨服务两阶段提交协议实现复杂，消息可靠性、幂等、悬挂问题缺一不可；无社区验证
* **评价：** 团队无自研中间件传统，维护和交接成本不可控

### 组合模式（AT + TCC + SAGA）

* **优点：** 按场景精细匹配，渐进式引入，编码规范已提供模板支撑
* **缺点：** 多模式并存增加调试理解成本；需明确的场景划分标准
* **评价：** 综合评分最高，最契合 ydsz-cloud 跨服务事务实际需求
