## 1. 数据库表设计

### 1.1 现状（已验证）

- **表数量**：bootstrap 174 张（153 基础表 + 21 分区），flyway 增量 13 个脚本、73 张 CREATE TABLE
- **命名规范**：100% `ydsz_` 前缀，零违规
- **字段覆盖**：程序化解析 153 张基础表，**tenant_id / is_deleted / created_at / updated_at / created_by / updated_by / sort / status / revision 九项平台字段 0 缺失**
- **布尔类型**：0 张表使用 `BOOLEAN`/`BOOL`/`TINYINT(1)`，全部 `SMALLINT` 合规
- **实体映射**：140 个实体类，100% 继承 `MpBaseEntity<String>`，137 个 `@TableName` 与表一一对应
- **索引**：bootstrap 614 组 + flyway 70 组索引；但 **129 个 `_id` 列无任何索引**，其中 29 个是 `tenant_id` 列

### 1.2 差距分析（对标业界）

| 项 | 业界主流实践 | 本项目 | 差距 |
|----|------------|--------|------|
| FK 索引 | 所有外键列建索引（避免全表扫描 + 优化器选错计划） | 129 个 FK 列无索引 | **高** |
| 外键约束 | 核心域用 FK 保证引用完整性 | 仅 6 个 FK（全在生成器模块） | **中** |
| 分区表 | 大表按时间/租户分区 | 搜索索引 8 分区 + 审计日志 12 分表（已做） | 达标 |
| 索引审查 | 用 `pg_stat_statements` 驱动索引调优 | 已引入 pg_stat_statements（V26.11.03） | 达标 |

### 1.3 可落地建议

**P0 — 补齐高频 FK 索引（1 个迁移脚本，低风险）**

优先补齐以下高价值索引（按查询频次排序）：
```
tenant_id（29 列，多租户过滤必备）
flow_run_task.instance_id / flow_his_instance.definition_id / flow_his_task.task_id（流程引擎核心查询）
job_daily_stats.job_id / msg_feedback.notification_id / job_log_content.log_id（统计与反馈聚合）
```
落地方式：新增 `data/sqls/flyway/V26.11.07.sql`，全部使用 `CREATE INDEX IF NOT EXISTS`（幂等），通过 `data/scripts/check-sql-migrations.py` 门禁（无 DROP/TRUNCATE）。

**P1 — 建立索引审查机制**
- 在 CI 增加 `EXPLAIN` 慢查询抽检：对核心模块 Top-N 查询做 `EXPLAIN (ANALYZE, BUFFERS)`，输出报告
- 利用已引入的 `pg_stat_statements` 建立"全表扫描次数"周报告，作为索引增删依据

**P2 — 评估核心域外键约束**
- 对 `flow_instance.definition_id`、`file_node.parent_id` 等强引用关系，评估是否加 FK + `ON DELETE CASCADE`/RESTRICT
- 注意：加 FK 前需确认历史数据无孤儿记录，建议先跑数据体检脚本

## 2. 接口与单元测试

### 2.1 现状（已验证）

- **接口规模**：242 个 `@RestController`，1,440 个方法级 mapping
- **响应包装**：`YdszResponse`/`PageResponse` 主导，仅 admin 后台存在 `Map<String,Object>` 裸返回（`I18nAdminController` 8 处、`LockAdminController` 7 处）
- **参数校验**：402 处 `@Valid` vs 357 个 `@RequestBody` 端点
- **OpenAPI**：1,130 `@Operation` vs 1,440 mapping → **约 310 个端点缺 `@Operation`**；仅 295 个 `@ApiResponse`
- **测试规模**：323 个测试文件 vs 4,659 个主文件（7%）；309 个 `@Test`、196 个 Mockito、**仅 6 个 `@SpringBootTest` 集成测试**
- **CI 门禁**：`check-diff-coverage.py` 强制增量行覆盖率 ≥ 40%（仅 diff，不约束存量）

### 2.2 差距分析

| 项 | 业界主流实践 | 本项目 | 差距 |
|----|------------|--------|------|
| 集成测试 | 每个服务 ≥30% 集成测试覆盖（真实 DB/HTTP） | 6 个 `@SpringBootTest`，网关仅 2 个测试 | **高** |
| 契约测试 | Controller ↔ 前端 SDK 契约一致性 | 有生成管线但无契约测试断言 | **中** |
| API 文档 | 100% 端点有 OpenAPI 注解 | 310 个端点缺失 | **中** |
| 测试分层 | 单元 + 集成 + 契约 + E2E 金字塔 | 几乎全是单元/Mockito | **高** |

### 2.3 可落地建议

**P0 — 网关与核心引擎集成测试补位**
- 网关仅 2 个测试覆盖 12 个全局过滤器，是最大风险面。建议用 `WebTestClient` + Testcontainers 补：认证过滤器、限流过滤器、路由转发、W3C 追踪透传 各 1 个集成测试
- 8 个引擎（workflow/message/cronjob/literule/agent）各补 1 个"端到端主链路"集成测试（真实 DB + MockMvc），验证核心流程可用

**P0 — 契约测试断言**
- 在 CI 增加步骤：对比后端生成的 OpenAPI spec 与前端 `src/api/sdk/schema.d.ts` 的漂移（可用 `openapi-diff`），契约变更必须显式确认
- 这能直接解决"310 个端点无 @Operation 导致前端类型缺失"的问题

**P1 — OpenAPI 注解补全**
- 对 310 个缺失 `@Operation` 的端点，按模块分批补全（每批 1 个模块，结合 i18n 文案）
- 门禁：`@Operation` 覆盖率纳入增量门禁（改动文件必须 100% 覆盖）

**P1 — 测试金字塔调整**
- 当前 196 Mockito vs 6 集成测试的比例（32:1）严重倒挂
- 目标：新增测试必须"集成优先"——Service 层测试用 `@SpringBootTest` + Testcontainers（H2/PostgreSQL），Controller 用 MockMvc，仅纯函数用 Mockito

## 3. 前后端能力贯通

### 3.1 现状（已验证）

- **契约生成**：`bash/unified-contract.mts` → `openapi-typescript` 产出 8 份 `schema.d.ts`；`gen-contract.py` 产出各 app `src/api/*.ts`
- **类型安全落地**：`apiClient.GET/POST`（openapi-fetch 强类型）**全仓仅 8 处调用**；手写 `requestClient.get/post<T>` **1,443 处**
- **生成的 SDK 基本是死产物**：`schema.d.ts` 0 个 `any` 但无消费方
- **any 逃逸**：comm 415 处、apps 97 处；`as any` 77 处；**`@ts-nocheck` 266 处**（几乎全在自研 UI 库）
- **类型基线**：`typecheck-baseline.json` 记录 **7,622 条既有 TS 错误**（agent 879 / literule 876 / workflow 850…）
- **请求层**：`comm/effects/request` 有完整客户端（去重、拦截器、追踪、401 双 token 重试），9 份 app `request.ts` 是再导出（良好）

### 3.2 差距分析

| 项 | 业界主流实践 | 本项目 | 差距 |
|----|------------|--------|------|
| SDK 消费 | 生成 SDK 100% 替代手写请求 | 8 处调用（0.5%） | **极高** |
| 类型安全 | 全链路无 any | 266 ts-nocheck + 7,622 基线错误 | **高** |
| 契约漂移 | CI 自动检测 | 无 | **中** |
| 请求层复用 | 统一客户端 | 已达成（9 份再导出） | 达标 |

### 3.3 可落地建议

**P0 — 生成 SDK 替换手写层（分模块灰度）**
- 这是**投入产出比最高**的单项改进：契约生成管线已就绪，只差消费端切换
- 路径：选 1 个模块（建议 `generator-web`，14 个 view、接口最简单）做试点，把 `requestClient.get/post<T>` 全部替换为生成的 `apiClient` 强类型调用
- 试点达标后按模块推进，每模块一个 PR，门禁：该模块 `api/*.ts` 手写封装清零
- 预期收益：类型错误基线下降、字段漂移归零、重构安全性提升

**P0 — `@ts-nocheck` 清理（自研 UI 库是重灾区）**
- 266 处 `@ts-nocheck` 集中在 `ydsz-ui/src/components/*`，导致 UI 库完全无类型保护
- 分批治理：按组件目录分批（每批 10-20 个文件），移除 `@ts-nocheck` 并修复暴露的类型问题
- 门禁：`@ts-nocheck` 数量纳入棘轮基线（只减不增），与 `hardcoded-text-baseline` 同机制

**P1 — 类型基线收敛计划**
- 7,622 条错误不可能一次性清零，但应建立"每月收敛 X%"的节奏
- 建议：每月选 1 个 app 做类型清零专项（如 literule 876 条），完成后从基线移除该 app
- 目标：6 个月内将基线从 7,622 降至 < 2,000

**P1 — 契约漂移 CI 门禁**
- 见 §2.3 P0。后端 OpenAPI 与前端 schema.d.ts 的 diff 纳入 CI，防止"后端改了字段前端不知道"

## 4. 前后端架构优化

### 4.1 后端架构（已验证）

- **DDD 分层**：domain 零内部依赖、infra 逆向依赖 domain、web 组合根——**整体正确**
- **违规**：4 个模块的 `server/pom.xml` 声明了 `*-infra` 依赖（agent、generator、system、userinfo），违反"server 不依赖 infra"
- **Converter 错位**：46 个 Converter 中 20 个在 domain 层，仅 2 个在 infra（DDD-007 要求 infra 转换）
- **Controller 越层**：33 个 Controller 直接注入 Repository/Mapper；50 个 Controller 含 try-catch（应交给全局 advice）
- **循环依赖**：无（pom 图无环）

### 4.2 前端架构（已验证）

- **微前端内核**：73 文件/14,831 行，ESM manifest + 三种沙箱（snapshot/proxy/iframe）+ 4 种预加载 + canary 灰度 + SRI——**能力覆盖面超出同规模项目常见水平**
- **接线现状**：仅 main 使用内核，9 个 app 只导出 bootstrap/mount/unmount（正确，无绕过）
- **死代码/未接线**：
  - `page-cache-manager`（4 文件，9 个 API）——**零引用**
  - `route-predictor`（3 文件）——仅 devtools 消费，生产预加载未使用
  - `preload-metrics`/`preload-usage-stats`——未接线
  - `create-react-sub-app.ts`——仓内无 React app
  - 4 个 app 的 `archived/` 目录共 22 个文件仍在源码树
- **组件重复**：
  - 空状态 3 份（`YdEmpty` / `YdEmptyState` / `YdTableEmpty`），各 62 处引用
  - tabs 3 份、drawer 2 份、alert 2 份、menu 2 份
  - **5 个表格组件零消费**（data-table/pro-table/virtual-table/tree-table），实际全走 `YdTable`
  - `ydsz-vue` 332 个组件在 apps+main 仅 2 个文件引用（实质未进入业务链路）

### 4.3 可落地建议

**P0 — 后端 DDD 违规整改（4 个 pom）**
- 将 agent/generator/system/userinfo 的 `server→infra` 依赖移除，Repository 实现改由 web 组合根装配
- 风险：需确认这些模块的 server 层是否真的 import 了 infra 类（编译期阻断），若只是"声明但未使用"则直接删依赖即可
- 门禁：CI 增加 DDD 依赖方向检查（解析 pom + import 语句）

**P0 — Controller 越层治理**
- 33 个直接注入 Repository/Mapper 的 Controller：业务逻辑下沉到 server 层
- 50 个含 try-catch 的 Controller：改为全局 advice 处理（`MvcExceptionHandler` 已具备能力）
- 分批：按模块推进，每批改 1 个模块，`mvn compile` + checkstyle 增量门禁验证

**P1 — 前端死代码清理**
- 删除：`create-react-sub-app.ts`、`page-cache-manager`（或接线到路由缓存）、4 个 app 的 `archived/` 目录
- 决策：`route-predictor` 要么接线到生产预加载，要么删除（避免"看起来有预测但不生效"的误导）
- 注意：删除前 grep 全局引用（项目规范第 6 条）

**P1 — 组件库去重**
- 空状态：保留 `YdEmptyState`（语义最全），废弃 `YdEmpty`/`YdTableEmpty`，124 处引用迁移
- 表格：保留 `YdTable`（46 处引用），废弃 4 个零消费表格组件
- `ydsz-vue`：332 个组件仅 2 处引用——评估是"预留能力"还是"历史包袱"，若为后者应整体下线（或标记 @deprecated 并移出构建）
- 收益：减小包体积、降低维护成本、消除"改哪个"的困惑

**P2 — Converter 归位**
- 将 domain 层 20 个 Converter 评估迁移到 infra 层（DDD-007）
- 注意：若这些 Converter 是 domain→VO（而非 PO→VO），则属合理，需逐个确认

## 5. 前后端功能增强

### 5.1 现状（已验证）

- 569 个 Micrometer 引用但仅 3 个 `@Timed`——指标基本靠手动 counter

**P1 — 功能性桩清零（按业务价值排序）**
1. **OCR**（nextwiki）：文档引擎核心能力，建议优先接入一个云厂商 SDK
2. **HTML→PDF**（nextwiki）：导出功能依赖，可用 `wkhtmltopdf` 或 Headless Chrome
3. **消息撤回**（message）：三个渠道对齐，DingTalk/Feishu/WeCom 均有官方撤回 API
4. **LLM 任务执行**（agent）：`BatchChatTaskExecutor` 接入真实 ChatService

**P1 — 统一幂等框架**
- 当前 33 个 `@YdszDistributedLock` 分散使用，缺乏统一幂等语义
- 建议：对创建类操作（生成实例、发起流程、提交任务）引入幂等键（`Idempotency-Key` header + Redis 去重），防止前端重试导致重复创建
- 对标：AWS API 幂等设计、Stripe `Idempotency-Key` 方案

**P2 — 前端 e2e 增强**
- 当前 15 个 e2e spec（12 个 smoke + 3 个 workflow）
- 建议：为每个 app 补 2-3 个核心 CRUD 工作流 e2e（参考已有 `dict-item-workflow` 模式）
- 门禁：e2e 纳入 nightly CI（已有 `performance.yml` 可扩展）

## 6. 前后端性能提升

### 6.1 后端性能（已验证）

- **无分页查询**：232 处 `selectList`/`findAll` 无分页（集中在 agent、cronjob infra repository）
- **分页已用**：157 处 PageHelper/IPage/Page
- **缓存**：54 `@CacheEvict`、16 `@Cacheable`、31 处 `getWithProtection`（防击穿已用）
- **缓存 key**：54 文件用 CacheKeyBuilder（语义化），但 **51 处硬编码字符串拼接 key**
- **Redis**：457 处 ops 封装 vs **1,066 处 raw `RedisTemplate`**（租户前缀可能被绕过）
- **线程池**：47 处 raw `new ThreadPoolExecutor` vs 141 处 `ExecutorUtils`
- **事务**：584 个 `@Transactional`，**148 个无 `rollbackFor`（25%）**
- **日志**：0 个 LOG-002 违规（{} 占位符达标）；1 处 printStackTrace、29 处 System.out

### 6.2 前端性能（已验证）

- **路由级代码分割**：10 个 app 100% 覆盖（懒加载 view）
- **Bundle 预算**：main 1054 KB / agent 1381 KB gzip，目标 384 KB（当前约 3 倍）
- **重依赖**：`vxe-table` 421 处引用（全 app 渗透）、`echarts` 2 处全量 `import *`（约 1MB+）
- **keep-alive**：**0 处使用**
- **虚拟滚动**：组件存在（`YdVirtualList` 等）但 apps+main **0 处使用**
- **图片懒加载**：仅 2 处
- **搜索防抖**：仅 4 个文件

### 6.3 可落地建议

**P0 — 无分页查询治理（后端最大性能风险）**
- 232 处无分页 `selectList` 中，优先治理返回大结果集的场景（如 `findAll` 全表扫描）
- 落地：逐个评估，能加默认 limit 的加 limit（如 `last("limit 1000")`），必须分页的改 `Page`
- 门禁：CI 增加检查——新增 `selectList` 必须带分页或 limit（可用 ArchUnit 或自定义脚本）

**P0 — keep-alive + 虚拟滚动落地（前端最大性能收益）**
- **keep-alive**：内核已有 `page-cache-manager` 但零引用。建议接线到路由：对列表页/详情页启用 `keep-alive`，避免重复请求与渲染
- **虚拟滚动**：对消息列表、审计日志、任务日志等长列表场景启用 `YdVirtualList`（组件已存在，只差接线）
- 收益：长列表场景渲染性能数量级提升（对标：飞书/钉钉消息列表均用虚拟滚动）

**P1 — 缓存 key 收口**
- 51 处硬编码字符串拼接 key → 迁移到 `CacheKeyBuilder`（语义化 + 租户前缀自动）
- 优先治理业务侧（非 common 基础设施），门禁：新增硬编码 key 判红

**P1 — Redis 直连治理**
- 1,066 处 raw `RedisTemplate` → 评估迁移到 `RedisStringOps`/`RedisHashOps` 封装
- 重点：确认直连处是否绕过 `TenantRedisKeyPrefixer`（多租户数据隔离风险）

**P1 — echarts 按需加载**
- 2 处 `import * as echarts`（约 1MB+）→ 改为按需引入（`echarts/core` + 所需 chart/组件）
- `vxe-table` 421 处引用：评估是否可替换为自研 `YdTable`（已存在且 46 处引用），逐步减少第三方依赖

**P2 — 事务与线程池规范**
- 148 个无 `rollbackFor` 的 `@Transactional`：补 `rollbackFor = Exception.class`
- 47 处 raw `new ThreadPoolExecutor`：迁移到 `ExecutorUtils`（项目规范已明确禁止直建）

**P2 — Bundle 预算收敛**
- 当前 main 1054 KB vs 目标 384 KB
- 路径：echarts 按需（-1MB）、vxe-table 替换（评估）、vendor chunk 优化
- 门禁：`check-size.mts` 已就绪，保持只减不增

### 7.3 可落地建议

**P0 — 硬编码文案清零（延续现有棘轮机制）**
- 现有 `hardcoded-text-baseline.json` + `check-hardcoded-text.mts` 机制良好（4,508 → 3,754，已降 17%）
- 建议：按模块分批清零（literule 617 / cronjob 639 / message 680 为前三），每批一个 PR
- 目标：3 个月内降至 < 1,000（仅保留图表/第三方组件等合理豁免）
- 收益：18 语种支持真正可用（当前硬编码中文使多语种形同虚设）

**P0 — 无障碍补强**
- 业务侧 a11y 稀薄（62 处 vs 组件库 1,020 处）——说明组件库自身达标，但业务页面未传递 a11y 属性
- 建议：
  1. 为 260 个 view 补基础 a11y（`aria-label`、`role`、键盘导航）
  2. 长列表/模态框补 focus trap（组件库已有 `FocusScope`，业务侧仅 9 处使用）
  3. e2e 增加 axe 扫描（已有 `tests/a11y` 基础设施，扩展到真实页面而非 fixture）
- 对标：WCAG 2.1 AA、字节/阿里无障碍规范

**P1 — 乐观更新（Optimistic UI）**
- 当前 154 处 "rollback/optimistic" 命中多为一般回滚，未见系统性乐观更新
- 建议：对高频操作（标记已读、收藏、排序、状态切换）引入乐观更新 + 失败回滚
- 收益：感知性能提升（对标：Notion/飞书的即时反馈）

**P1 — 搜索防抖推广**
- 仅 4 个文件有防抖，全局搜索/列表筛选场景应统一
- 建议：封装 `useDebounceSearch` composable（项目已有 `@vueuse/useDebounce` 可复用），推广到所有搜索输入

**P2 — 空状态/加载态一致性**
- 3 个空状态组件并存（见 §4.2）——统一后用户体验更一致
- 骨架屏 5 个变体：评估是否过多，保留 2-3 个核心变体
