# 云顶公共模块复用深度检查与下一步优化建议（2026-09-15）

> 检查方式：`scripts/check-common-reuse.py` 全量实跑（退出码 0）+ 全部 W 级命中逐项源码核验。
> 范围：10 个业务模块（agent/cronjob/gateway/generator/literule/message/nextwiki/system/userinfo/workflow），
> 共 2,789 个 main java 文件，对照 ydsz-common 30 个公共模块。

## 评判框架声明（依据《云顶编码规范》§33.7，commit c001a18c5）

本次检查不以"业务侧引用热度"评判公共模块价值（L1 工具模块按需供给属正常形态），
仅以三条硬标准定性"重复造轮子"：

1. **平台内重复**：同一能力在本仓库已有其他实现；
2. **可替代性**：可由既有公共模块以更低成本提供且无独有收益；
3. **负债状态**：无测试、无生命周期标注的能力储备。

## 二、分级发现

### P0：UUID 主键违规 4 处（违反 ADR-008，实体主键必须走 IdGenerator/Snowflake）

全部为源码逐行实锤，`setId(UUID.randomUUID().toString())` 写入持久化主键字段：

| # | 文件:行 | 实体/表 | 备注 |
|---|---------|---------|------|
| 1 | `ydsz-literule/.../audit/RuleAuditLogService.java:582` | AuditLog | 审计日志主键 |
| 2 | `ydsz-system/.../ConfigApprovalServiceImpl.java:38` | ConfigApproval | **实体已声明 `@TableId(type=ASSIGN_ID)`，手工 setId 覆盖了雪花自动分配，双重违规** |
| 3 | `ydsz-workflow/.../FlowCategoryServiceImpl.java:203` | FlowCategoryDTO→落库 | 流程分类主键 |
| 4 | `ydsz-workflow/.../FlowDefinitionDeployManager.java:358` | FlowDefinitionDTO→落库 | 流程定义主键 |

对照正面案例：ydsz-message 的 `OutboxDomainEventPublisher` / `MessageServiceImpl` 已整改为
"主键经 IdGenerator 雪花生成（ADR-008 整改）"并留有 Javadoc 记录——上述 4 处为同模式的漏网点。

**处置**：改为注入 `IdGenerator`（common-util，与 message 模块整改写法一致），
或在实体层依赖 `ASSIGN_ID` 自动分配并删除手工 setId。

### P1：cronjob 自建 Outbox 双轨（ADR-009 未定界的平台内重复）

common-event 已提供完整事务性 Outbox 体系：
`OutboxService / OutboxRepository / OutboxProcessor / OutboxAdminService / OutboxHealthIndicator / OutboxMessage / OutboxStatus`。

而 ydsz-cronjob 平行自建了整条链路（且 Javadoc 自述对标 Debezium/Eventuate/Axon）：

- `ydsz-cronjob-domain/.../entity/OutboxEvent.java`（ydsz_job_outbox 表，零 common-event import）
- `ydsz-cronjob-domain/.../repository/outbox/OutboxEventRepository.java` + infra 实现
- `ydsz-cronjob-server/.../core/outbox/OutboxPublisher.java`（扫描 + 至少一次 + 指数退避 1s/5s/25s + DEAD）

两侧投递语义高度重合（至少一次、幂等、退避、DEAD）。差异仅在路由目标：
cronjob 版路由到进程内订阅者（WebHook/Metrics/Audit），common 版经 Spring ApplicationEventPublisher 发布
——进程内订阅完全可用 `@EventListener` 消费，不构成独有收益。

按硬标准①（平台内重复）成立。ADR-009 收敛了短信签名/线程池/网关/RAG 分块四项，
**Outbox 双轨是其盲区**。

**处置建议（二选一，需 ADR 定界）**：
- 方案 A（推荐）：cronjob 的实体与仓储保留（表结构独立），`OutboxPublisher` 的
  扫描/退避/状态机改为委托 common-event `OutboxService`，进程内订阅者改为 Spring 事件监听；
- 方案 B：在 ADR-009 增补"cronjob Outbox 场景定界"，写明不可替代的独有职责（若无则不应选择本方案）。

### P2：五项完善建议

1. **userinfo AppOpenApiConfiguration 未复用模板**：
   `ydsz-userinfo-app/.../openapi/AppOpenApiConfiguration.java` 硬编码 OpenAPI Info Bean，
   而 common-app 已提供 `BaseOpenApiConfiguration` 模板方法（getTitle/getDescription 覆盖点）。
   建议改为继承并只覆盖标题/描述三行——同包名同名类（E1 命中）即随之消除。
2. **gateway 僵尸依赖 redis，pom 注释承诺落空**：
   `ydsz-gateway/pom.xml:105` 注释称"限流 Lua 脚本统一引用 ydsz-common-redis 的
   RedisScriptConstants 共享常量"，但全模块源码与 resources 零引用（W1 命中）。
   应落实引用或移除依赖，二选一，禁止注释与事实不符。
3. **模板引擎双轨待定界**：ydsz-message `server/template/TemplateEngine`
   （${var} + {{#if}}/{{#each}} 内容渲染语法）与 common-notify `template/TemplateEngine`
   （模板注册表 + SpEL 渲染）接口语义确有差异，属能力分层的灰色地带；
   但两侧 `TemplateVariableValidator` 职责重合度较高。建议在 ADR-009 增补定界，
   或将 message 的富语法引擎上提为 common-notify 的高级实现（消歧方向由 ADR 决定）。
4. **cronjob DomainEvent 接口双轨**：domain 层自建 Event Sourcing 事件接口
   （eventId/aggregateId/aggregateType 元数据），server 层同时使用 common-event `api.DomainEvent`
   发布（AlertDispatcher/DefaultTaskDispatcher/JobServiceImpl）。
   建议评估在 common-event 扩展 ES 元数据接口，或 Javadoc 增补"为何 domain 层不直接用 common 接口"的定界说明。
5. **common-seata 零业务消费**：供给面 30 个模块中唯一直接 import 为 0。
   按 §33.7 属"能力储备"而非过度设计，但 ADR-010 的 Seata PoC 落地后应尽快产生首个业务消费方，
   或按负债状态标准补生命周期标注（`@since` + 储备说明），避免裸奔资产沉淀。
