# 云顶版本管理规范（Ydsz Cloud Version Specification）

> **当前版本**：26.09.01
> **生效日期**：2026-09-01
> **适用范围**：ydsz-cloud 全部模块及相关基础设施
> **规范基线**：日期版本规范（CalVer），格式 YY.MM.DD
> **配套工具**：Git Tag、Maven、CI/CD Pipeline

---

## 概述

### 目的

本规范定义 ydsz-cloud 项目的版本命名、发布流程、分支策略及版本管理规范，确保版本演进可追溯、发布过程可控、协作开发有序。

### 版本格式

本项目采用 **YY.MM.DD** 日期版本格式（Calendar Versioning），与互联网大厂（如 Microsoft Office、Ubuntu YY.MM）保持一致。

```
YY + MM + DD

示例：
  26.09.01  →  2026年9月1日 第一个发布版本
  26.09.15  →  2026年9月15日 发布版本
  26.12.31  →  2026年12月31日 发布版本
```

### 版本规则说明

| 组成部分 | 含义 | 取值范围 |
|----------|------|----------|
| YY | 年份后两位 | 00-99 |
| MM | 月份（两位） | 01-12 |
| DD | 日期（两位） | 01-31 |

### 同日多版本处理

若在同一个自然日内需要发布多个版本，采用追加序号方式区分：

```
26.09.01.1  →  当日第一次发布
26.09.01.2  →  当日第二次发布（紧急修复）
26.09.01.3  →  当日第三次发布
```

正常情况下，每日发布不超过一个版本。

## 版本类型

### 正式版本（Release Version）

面向生产环境发布的稳定版本，格式为标准 **YY.MM.DD** 或 **YY.MM.DD.N**。

发布条件：

- 通过全部自动化测试（单元测试、集成测试）
- Checkstyle 检查通过
- Code Review 至少一人通过
- 功能验收完成

### 快照版本（Snapshot Version）

开发过程中的中间版本，Maven 中版本号追加 `-SNAPSHOT` 后缀。

```
26.09.01-SNAPSHOT  →  开发中的快照版本
```

快照版本特点：

- 允许不稳定，可频繁更新
- 不直接用于生产部署
- 每日构建自动生成

### 预发布版本（Pre-release Version）

用于测试环境验证的版本，追加预发布标签。

```
26.09.01-alpha   →  内部测试阶段
26.09.01-beta    →  公开测试阶段
26.09.01-rc.1    →  候选发布版本 1
26.09.01-rc.2    →  候选发布版本 2
```

### 热修复版本（Hotfix Version）

针对生产环境紧急问题的修复版本，沿用当日版本号追加序号。

```
26.09.01.2   →  26.09.01 当日第二个版本（热修复）
```

热修复发布条件：

- 仅限影响生产的严重问题（P0/P1级别）
- 需经过审批流程
- 修复完成后立即合并回主分支

## 分支策略

### 分支模型

采用 Git Flow 简化版分支策略，核心分支结构如下：

```
main         ─── 生产分支，始终保持可发布状态
  ↑
release/*    ─── 发布分支，准备发布的临时分支
  ↑
develop      ─── 开发集成分支，日常开发主线
  ↑
feature/*    ─── 功能分支，单个功能开发
  ↑
hotfix/*     ─── 热修复分支，紧急问题修复
```

### 分支命名规范

| 分支类型 | 命名格式 | 示例 |
|----------|----------|------|
| 功能分支 | feature/[模块名]-[功能简述] | feature/auth-login |
| 修复分支 | fix/[模块名]-[问题简述] | fix/user-null-pointer |
| 热修复分支 | hotfix/V[版本号]-[修复简述] | hotfix/26.09.01-session-expire |
| 发布分支 | release/V[版本名] | release/26.09.01 |
| 主分支 | main | - |
| 开发分支 | develop | - |

### 分支生命周期

```
feature 分支：创建 → 开发 → PR → Review → 合并到 develop → 删除
hotfix 分支：创建 → 修复 → PR → 合并 main + develop → 删除
release 分支：创建 → 验证 → 合并 main → 打 Tag → 删除
```

## 发布流程

### 标准发布流程

```
┌─────────────────────────────────────────────────────────┐
│  1. 确定版本号（如 26.09.01）                            │
│                         ↓                                │
│  2. 从 develop 创建 release/26.09.01 分支               │
│                         ↓                                │
│  3. release 分支上进行最终验证与冒烟测试                  │
│                         ↓                                │
│  4. 更新 CHANGELOG.md（记录版本变更）                     │
│                         ↓                                │
│  5. 合并 release 分支到 main，并打 Tag                   │
│                         ↓                                │
│  6. CI/CD 自动构建并部署到生产环境                        │
│                         ↓                                │
│  7. 合并回 develop（如有修复）                            │
│                         ↓                                │
│  8. 删除 release 分支                                    │
└─────────────────────────────────────────────────────────┘
```

### Tag 规范

Git Tag 命名与版本号一致，格式如下：

```bash
# 创建标签
git tag -a 26.09.01 -m "Release 26.09.01: 初始正式版本发布"

# 推送标签到远程
git push origin 26.09.01
```

Tag 命名规则：

- 正式版本：`YY.MM.DD` 或 `YY.MM.DD.N`
- 不允许使用模糊命名（如 `latest`、`release` 等）
- Tag 一旦创建不允许删除或移动

## Maven 版本管理

### 项目版本号规范

在 `pom.xml` 中，版本号遵循以下格式：

```xml
<!-- 正式版本 -->
<version>26.09.01</version>

<!-- 快照版本（开发期） -->
<version>26.09.01-SNAPSHOT</version>
```

### 版本号递增规则

```xml
<!-- 开发阶段 -->
<version>26.09.01-SNAPSHOT</version>

<!-- 发布当天，移除 SNAPSHOT -->
<version>26.09.01</version>

<!-- 下一个开发周期开始 -->
<version>26.09.02-SNAPSHOT</version>
```

### 多模块版本同步

项目使用父 POM 统一管理版本，所有子模块版本与父 POM 保持一致：

```xml
<!-- pom.xml 父模块 -->
<groupId>com.njydsz</groupId>
<artifactId>ydsz-cloud</artifactId>
<version>26.09.01</version>
<packaging>pom</packaging>

<modules>
    <module>ydsz-common</module>
    <module>ydsz-gateway</module>
    <!-- ... -->
</modules>
```

版本更新命令：

```bash
# 批量更新所有模块版本
mvn versions:set -DnewVersion=26.09.01
mvn versions:commit
```

## CHANGELOG 规范

### 文件位置

每个版本变更记录在项目根目录 `CHANGELOG.md` 中维护。

### 记录格式

```markdown
# 变更日志（CHANGELOG）

## [26.09.01] - 2026-09-01

### 新增（Added）
- 用户认证模块（ydsz-common-auth）初始发布
- 基于 JWT 的无状态登录机制

### 变更（Changed）
- 升级 Spring Boot 版本至 3.x
- 优化数据库连接池配置

### 修复（Fixed）
- 修复 PostgreSQL 方言兼容性问题

### 安全（Security）
- 修复 XSS 漏洞（CVE-XXXX-XXXX）

### 废弃（Deprecated）
- @OldAuthApi 标记为废弃，请使用 @JwtAuthApi

---

## [26.09.02] - 2026-09-02

### 修复（Fixed）
- 紧急修复会话过期后重定向异常问题

### 变更（Changed）
- 更新文档解析模块，修复内存泄漏
```

### 分类说明

| 分类 | 说明 | 优先级 |
|------|------|--------|
| Added | 新功能 | 高 |
| Changed | 已有功能变更 | 中 |
| Fixed | Bug 修复 | 高 |
| Security | 安全相关修复 | 最高 |
| Deprecated | 即将移除的功能 | 低 |
| Removed | 已移除的功能 | 中 |
| Performance | 性能优化 | 中 |

## 版本兼容性

### API 兼容性原则

| 变更类型 | 兼容性要求 | 示例 |
|----------|------------|------|
| 新增接口 | 向后兼容 ✓ | 新增加载方法 |
| 修改接口签名 | 需评估影响 | 修改参数类型 |
| 删除接口 | 需先标记 @Deprecated | 删除旧认证方式 |
| 内部实现重构 | 保证接口不变 | 优化算法复杂度 |

### 数据库兼容性

- 数据库 Schema 变更必须通过 migration 脚本（Flyway/Liquibase）
- 不允许直接修改已有表结构，仅允许新增列或表
- 删除字段需废弃后至少保留一个版本周期

### 配置文件兼容性

- 配置项新增：提供默认值，保证旧配置仍可用
- 配置项重命名：保留旧配置名作为别名
- 配置项删除：至少一个版本周期内仍支持读取

## 版本回滚规范

### 回滚触发条件

出现以下情况时执行版本回滚：

- 影响核心业务的 P0 级别故障
- 数据损坏或丢失
- 严重安全漏洞
- 性能急剧劣化（响应时间增加 50% 以上）

### 回滚流程

```
┌───────────────────────────────────────────┐
│  1. 确认回滚版本（上一个稳定版本）          │
│                   ↓                        │
│  2. 通知相关方（开发、测试、运维）           │
│                   ↓                        │
│  3. 执行回滚部署（使用上一版本 Tag）         │
│                   ↓                        │
│  4. 验证回滚后系统状态                      │
│                   ↓                        │
│  5. 记录回滚原因及处理过程                  │
│                   ↓                        │
│  6. 修复问题后重新发布新版本                │
└───────────────────────────────────────────┘
```

### 回滚命令示例

```bash
# 部署上一个稳定版本
git checkout 26.08.31
# 通过 CI/CD 触发部署
```

### 附录 C：常见问题

**Q1：如果当天没有发布计划，版本号会跳过吗？**

不会补跳。版本号代表实际发布日期，9月1日发布后若下次发布是9月15日，则版本号为 26.09.15（跳过无发布的日期）。

**Q2：快照版本需要 Tag 吗？**

不需要。快照版本仅存在于 Maven 本地/远程仓库，不创建 Git Tag。

**Q3：热修复版本如何确定序号？**

从 .1 开始递增。如 26.09.01 的第一个热修复为 26.09.01.1，第二个为 26.09.01.2。若正式发布与首个热修复同日，正式发布版本号为 26.09.01，首个热修复为 26.09.01.1。

**Q4：跨年夜版本如何处理？**

按实际发布日期标注。跨年夜（12月31日）发布为 26.12.31，跨年第一天（1月1日）发布为 27.01.01。
