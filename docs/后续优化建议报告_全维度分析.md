## 二、数据库表能力设计优化建议

### 2.1 🔴 P0 — 立即修复（运行时必报错）

#### P0-1：workflow 模块 MySQL 函数误用于 PostgreSQL

**现状**：`FlowRunTaskMapper.xml` 第 342 行和 `FlowInstanceMapper.xml` 第 336 行使用了 `TIMESTAMPDIFF(HOUR, ...)`，这是 MySQL 专有函数，PostgreSQL 不支持。

**影响**：调用 `selectOverdueTopN` 和 `selectStuckInstances` 时直接抛出 `function timestampdiff(integer, timestamp, timestamp) does not exist` 异常，流程监控功能完全不可用。

**修复方案**：
```sql
-- 替换前（错误）
TIMESTAMPDIFF(HOUR, due_at, CURRENT_TIMESTAMP) AS "overdueHours"

-- 替换后（PostgreSQL）
EXTRACT(EPOCH FROM (CURRENT_TIMESTAMP - due_at)) / 3600 AS "overdueHours"
```

**文件**：`ydsz-workflow-infra/src/main/resources/mapper/FlowRunTaskMapper.xml`、`FlowInstanceMapper.xml`

---

#### P0-2：workflow 模块引用不存在的 `due_date` 字段

**现状**：`FlowInstanceMapper.xml` 第 353-354 行 `countOverdueInstances` 方法使用 `WHERE due_date IS NOT NULL AND due_date < #{now}`，但 DDL 中表明该字段实际为 `due_at TIMESTAMP`，不存在 `due_date` 列。

**影响**：超期实例统计接口调用必败。

**修复方案**：统一改为 `due_at`。

---

#### P0-3：workflow 模块审计字段 `updated_by` 硬编码为 0

**现状**：`FlowRunTaskMapper.xml` 中所有 UPDATE 操作（12 处）、`FlowInstanceMapper.xml`（4 处）、`FlowUserMapper.xml`（1 处）、`FlowSkipMapper.xml`（1 处）均写死 `updated_by = 0`。

**影响**：所有变更操作的更新人记录为 '0'，审计追踪完全失效，无法定位操作人，违反合规要求。

**修复方案**：改为通过方法参数传入 `#{updatedBy}`，或启用 MyBatis-Plus `MetaObjectHandler` 自动填充审计字段。

**文件**：
- `ydsz-workflow-infra/src/main/resources/mapper/FlowRunTaskMapper.xml`
- `ydsz-workflow-infra/src/main/resources/mapper/FlowInstanceMapper.xml`
- `ydsz-workflow-infra/src/main/resources/mapper/FlowUserMapper.xml`
- `ydsz-workflow-infra/src/main/resources/mapper/FlowSkipMapper.xml`

### 2.2 🟠 P1 — 尽快修复（性能/安全缺陷）

#### P1-1：12 个实体继承 MpBaseAuditEntity 导致多租户隔离失效

**现状**：以下实体直接继承 `MpBaseAuditEntity`，跳过了 `MpSimpleEntity`，导致缺少 `tenant_id`、`status`、`is_deleted` 字段：

| 文件 | 模块 |
|------|------|
| `UserProfile.java` / `InsightReport.java` / `AgentApproval.java` | agent |
| `JobDagContext.java` | cronjob |
| `GenDatasource.java` / `GenTemplate.java` / `GenTemplateGroup.java` | generator |
| `UserRecent.java` / `UserFavorite.java` / `SpaceTemplate.java` / `SpaceMember.java` / `Space.java` | nextwiki |

**影响**：多租户 SQL 拦截器会自动注入 `tenant_id = ?` 条件但列不存在导致 SQL 报错；或者实体未映射该字段造成数据隔离失效。

**修复方案**：
- 若需多租户隔离 → 改为继承 `MpSimpleEntity` 或 `MpBaseEntity`
- 若确实不需要（如全局配置表）→ 在表名和注释中显式标注

---

#### P1-2：workflow 缺少复合索引 — 高频查询性能瓶颈

**现状**：`ydsz_flow_run_task` 只有单列索引 `idx_assignee_id`，但高频查询同时过滤 `assignee_id + task_status IN (...) + status + is_deleted`。

**影响**：单列索引仅利用 assignee_id，剩余条件全部回表，任务量大时列表接口响应超时。

**修复方案**：
```sql
CREATE INDEX idx_flow_run_task_assignee_status 
  ON ydsz_flow_run_task (assignee_id, task_status, status, is_deleted);
```

---

#### P1-3：cronjob 缺少 (status, next_fire_time) 复合作业扫描索引

**现状**：`ydsz_job_main` 仅有单列索引 `idx_next_fire`，但 `selectDueJobs` 的 WHERE 包含 `status='NORMAL' AND is_deleted=0 AND next_fire_time<=#{now}` + 排序。

**影响**：任务量接近 5000 上限时每次调度全表扫描，性能急剧下降。

**修复方案**：
```sql
CREATE INDEX idx_job_main_due_scan 
  ON ydsz_job_main (status, is_deleted, next_fire_time);
```

---

#### P1-4：workflow 历史查询缺少分页保护

**现状**：`selectByInitiator`、`selectDoneByAssignee` 等方法无 LIMIT/OFFSET/游标分页，可能全量返回。

**影响**：活跃用户可能发起数千条流程实例/任务，一次性加载导致 OOM 或响应超时。

**修复方案**：增加分页参数或默认 LIMIT，或改用 keyset 分页（参考同文件中 `selectTodoByAssigneeCursor` 的实现模式）。

---

#### P1-5：cronjob `selectAllNormal` 硬编码 LIMIT 5000

**现状**：`JobMapper.xml` 第 55-59 行 `LIMIT 5000` 硬编码。

**影响**：NORMAL 状态任务超过 5000 时不加载新任务，且静默失败无任何告警。

**修复方案**：改为分页循环加载，或至少加上超限告警日志。

---

#### P1-6：userinfo 缺少 email 列索引

**现状**：`ydsz_acct_user` 有 phone、dept_id、company_id 索引，但缺少 email 索引。

**影响**：现代系统邮箱登录已是必备功能，缺失索引导致全表扫描。

**修复方案**：
```sql
CREATE INDEX idx_ydsz_acct_user_email ON ydsz_acct_user (email);
```

---

#### P1-7：message 模块 markAllRead 子查询锁竞争风险

**现状**：`MsgNotificationMapper.markAllRead` 使用 `UPDATE ... WHERE id IN (SELECT ... LIMIT)` 模式。

**影响**：PostgreSQL 中该写法对子查询结果集加锁，高并发场景可能锁竞争。

**修复方案**：改用 CTE + `FOR UPDATE SKIP LOCKED` 写法减少锁持有时间。

---

#### P1-8：agent approval 表冗余索引

**现状**：`idx_ydsz_agt_approval_approval_tenant` (tenant_id) 是 `idx_ydsz_agt_approval_tenant_created` (tenant_id, created_at) 的左前缀冗余。

**影响**：无性能收益，浪费写性能。

**修复方案**：删除 `idx_ydsz_agt_approval_approval_tenant`。

### 4.2 🔴 P0 — 立即修复数据丢失型缺陷

#### P0-1：`sortOrder` → `sort` 字段名静默丢失

**现状**：后端已将排序字段统一命名为 `sort`（Java 字段），但前端多处残留 `sortOrder`：

| 文件 | 位置 |
|------|------|
| `apps/generator-web/src/api/models.ts:123` | `GenTemplateGroup.sortOrder` |
| `apps/generator-web/src/views/template/template-group-form.vue` | 表单 state + submit data |
| `apps/userinfo-web/src/api/sdk/schema.d.ts` (7 处) | 多个 VO：`saml-idp`、`social-client`、`system/dept` 等 |
| `apps/userinfo-web/src/views/saml-idp/index.vue` | 表单字段 |
| `apps/userinfo-web/src/views/social-client/index.vue` | 表单字段 |
| `apps/userinfo-web/src/views/system/dept/dept-form.vue` | 表单字段 |

**影响**：Jackson 反序列化查找 `sort` 字段，前端发送 `sortOrder` 字段的表单提交时被忽略，排序值永远不会生效。属于**数据静默丢失**型缺陷，用户无感知但功能失效。

**修复方案**：

1. **前端**：全局替换所有 `sortOrder` → `sort`
2. **后端**：在前端修复过渡期，可在 DTO 的 `@JsonProperty` 上同时兼容新旧字段名：
   ```java
   @JsonProperty("sort")
   private Integer sort; // 同时 @JsonAlias("sortOrder") 兼容
   ```
3. **契约层**：重新运行 `pnpm gen:api` 同步 SDK spec，确认 `schema.d.ts` 中字段统一为 `sort`

---

#### P0-2：generator-web 缺少 SDK 自动生成的契约

**现状**：`apps/generator-web/src/api/sdk/` 目录不存在，generator 子应用仍使用手写的 `models.ts`，无法享受类型安全调用。

**影响**：无法享受 OpenAPI 自动化契约带来的类型安全；新接口需手动同步模型定义，易漂移。

**修复方案**：
1. 排查后端 `ydsz-generator` 是否产出 `openapi.json`
2. 若未产出：检查 SpringDoc 配置，确保 `@Hidden` 注解未屏蔽路径
3. 重新运行 `pnpm gen:api`，或补充独立生成 task

---

### 4.3 🟠 P1 — 尽快修复贯通隐患

#### P1-1：system-web API 文件冗余治理

**现状**：存在手写版（`config.ts` / `dict.ts` / `tenant.ts`）与 SDK 生成版（`.generated-archived/`）两组 API 文件。当前业务代码以手写版为主，SDK 生成版可能未被实际使用。

**影响**：维护两套代码，容易产生不一致。

**修复方案**：确定以 SDK 生成为主，将手写版标记 deprecated 或清理。

---

#### P1-2：补齐 Swagger `@Operation` / `@ApiResponse` 注解

**现状**：workflow 和 userinfo 模块注解完整，但 message / agent / generator 等模块仅覆盖 `@Operation`，缺少 `@ApiResponse`、`@Schema` 描述。

**影响**：OpenAPI spec 不完整，前端 SDK 生成缺少响应类型描述。

**修复方案**：按模块逐步补齐 `@ApiResponse` + `@Schema`，使 openapi.json 可包含完整错误响应。

---

#### P1-3：WebSocket 后端端点未上线

**现状**：前端 `use-websocket.ts` 基础设施完整（自动鉴权 + 重连 + 心跳 + 可见性自适应），但注释标注"后端 WebSocket 端点上线后传入 URL 即可工作"，目前未发现前端实际调用 `useWebSocket` 的业务场景。

**建议**：明确 WebSocket 何时上线，若近期无需实时推送可暂缓；否则需在 `ydsz-gateway` 增加 WebSocket 路由，后端引擎实现对应 handler。

---

### 4.4 🟡 P2 — 长期贯通质效提升

1. **契约测试自动化**：CI 中新增"前端 SDK ↔ 后端 openapi.json"漂移检测，PR 合入前自动对比 hash
