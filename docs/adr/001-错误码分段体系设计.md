# ADR-001: 错误码分段体系设计

**状态**: 已采纳  
**日期**: 2024-Q3  
**决策者**: ydsz-team

## 背景

系统需要一个统一的错误码体系，用于规范 API 响应中的业务错误标识。需要满足：
1. 前端可根据错误码做统一的错误处理（如 Token 过期统一跳转登录页）
2. 运维根据错误码快速定位问题来源（用户端/服务端/第三方）
3. 开发者能快速判断错误级别和响应 HTTP 状态码

## 决策

采用 **A/B/C 三段式错误码体系**，参考阿里巴巴《Java开发手册》规范：

| 段位 | 含义 | 示例 |
|------|------|------|
| A00000 | 成功 | `SUCCESS` |
| A1xxxx | 用户端通用错误 | `BAD_REQUEST`, `NOT_FOUND`, `RATE_LIMIT` |
| A2xxxx | 认证授权错误 | `UNAUTHORIZED`, `FORBIDDEN`, `TOKEN_EXPIRED` |
| B1xxxx | 系统级业务异常 | `INTERNAL_ERROR`, `SERVICE_UNAVAILABLE` |
| B2xxxx | 系统状态 | `SYSTEM_MAINTENANCE`, `CIRCUIT_BREAKER_OPEN` |
| C1xxxx | 第三方服务异常 | `DB_*`, `CACHE_*`, `MQ_*` |
| C9xxxx | 兜底未知错误 | `UNKNOWN` |

**关键设计决定**：
- 每个枚举**显式声明 HTTP 状态码**（数据驱动，无 switch）
- **禁止通过 code 前缀推断 HTTP 状态码**（如同为 A 开头不能统一映射为 400，MFA_REQUIRED 映射 401）
- 业务模块专用错误码下沉到各模块自定义枚举，实现 `ResultCode` 接口即可

## 替代方案

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 纯 HTTP 状态码 | 标准化程度高 | 无法承载具体业务错误语义 | 不采用 |
| 前缀推断 HTTP 状态码 | 实现简单 | 跨前缀映射不可行，如 A20110(423) | 不采用 |
| 三段式 + 显式 HTTP 映射 | 精确、可扩展 | 枚举膨胀 | **采用** |

## 后果

- 正面：前端可基于 code 做精准 UI 处理，后端可基于段位做分级告警
- 负面：枚举项持续增长，已通过 1.5.0 新增的 `fromCode()`、`authCodes()` 等查询 API 缓解
