五、核心发现 — 6 大架构贯通不足问题

P0-关键
1. ydsz-system 与 ydsz-userinfo 缺少 common-json 显式依赖
两个最早构建的核心模块未在 pom.xml 中显式声明 ydsz-common-json，仅通过 common-web → common-base → common-core → common-json 的长链路传递获取。一旦传递链路中任何模块的依赖范围变更，将导致编译失败。
风险：不可预期的构建失败、依赖可见性不一致、IDE 自动补全缺失。
建议操作： 修复 在 ydsz-system-domain/pom.xml 和 ydsz-userinfo-domain/pom.xml 中，参照其他 6 个模块的模式，显式声明：
<dependency>
  <groupId>com.njydsz</groupId>
  <artifactId>ydsz-common-json</artifactId>
  <!-- 为下游 server/web 模块提供传递依赖 -->
</dependency>
P0-关键
2. ydsz-message / ydsz-cronjob 分页返回未使用统一的 PageResult 信封
两个模块的 Web Controller 层直接使用 BaseResponse<Page<VO>>（MyBatis-Plus 原生 Page），而非项目统一的 PageResult<VO>。共涉及 message 9 个 Controller、cronjob 4 个 Controller。
影响范围：message/MessageController, TemplateController, RouteRuleController, NotificationController, AggregateController, CanaryController, DeadLetterController, MessageArchiveController, MessageFeedbackController；cronjob/JobController, JobGroupController, JobTaskController, JobWebhookController。
建议操作： 修复 将以上 13 个 Controller 的分页返回类型从 BaseResponse<Page<T>> 统一改为 PageResult<T>，与 system/workflow/nextwiki 保持一致。建议在 server 层进行转换。
P0-关键
3. ydsz-common-cache 全模块零采用，存在严重能力浪费
ydsz-common-cache 是一个完整的自研多策略缓存框架（含 LRU/LFU/W-TinyLFU/多级缓存/写穿透/写回/SWR 等）—— 但 9 个业务模块中无一使用其高级特性。MultiLevelCache、@Cached、@CacheRefresh、WriteThroughCache、WriteBehindCache 等均在 0% 采用率。
风险：造成各自重复实现本地缓存逻辑，架构不一致，维护成本分散。
建议操作： 推广 制定 ydsz-common-cache 使用规范，在 S1-S2 阶段逐步将各模块的本地缓存替换为统一缓存框架。优先推荐 W-TinyLFU 作为默认策略（对标 Caffeine），@Cached 注解降低接入门槛。
P1-高
4. common-safe 安全特性在多个模块缺失
@Xss 精确校验：仅 workflow（2个DTO）使用了注解级 XSS 校验。system 的 Variable/Config DTO、userinfo 的用户 DTO、message/cronjob/literule/agent 的所有 DTO 均未标注。虽然全局 XssFilter 生效，但缺少精确字段级校验。
@SensitiveData 脱敏：仅 workflow 大量使用，system/userinfo 的管理 DTO 无脱敏标注。
@RateLimit 频率限制：cronjob 和 literule 完全未使用 @RateLimit。
建议操作： 补全 (a) 为各模块 Web 层 DTO 的字符串字段补充 @Xss 注解；(b) 为 system/userinfo 的 response DTO 补充 @SensitiveData 脱敏；(c) 为 cronjob/literule 的写操作接口补充 @RateLimit。
P1-高
5. ydsz-common-json SPI 扩展仅 3 个模块实现，且 1 个为占位
7 个引用了 ydsz-common-json 的业务模块中，仅 ydsz-agent（7 个完整的自定义序列化器 + AgentJsonModule）和 ydsz-literule（LiteRuleJsonModule）正确实现了 SPI 扩展。ydsz-message 的 MessageJsonModule 全部序列化器抛出 UnsupportedOperationException，属于占位代码。
缺失：workflow（BPMN 模型）、cronjob（DAG 模型）、nextwiki（文档模型）等模块的领域对象仍在走纯反射序列化路径，未利用类型安全的自定义序列化器。
建议操作： 完善 (a) 补充 message 的 MessageJsonModule 实现；(b) workflow 为 FlowDefinition/FlowNode/FlowEdge 等核心域对象实现自定义序列化器；(c) cronjob 为 DagNode/DagEdge 实现序列化器。
P1-高
6. 高级 JSON 特性在 80% 模块中沉睡
流式解析（JsonParser/JsonParserUtil）：全仓零使用。对标 Jackson Streaming API，适合大文件/流式场景。
JsonMapper.Builder 独立配置实例：仅 agent（SNAKE_CASE 命名策略）和 message（convertValue 类型转换）使用了 Builder 模式。大多数模块仅用 YdszJson.toJson/parse 两个静态方法。
树模型：仅 cronjob 和 workflow 使用，其他模块的复杂 JSON 读写场景可能走了字符串操作。
@JsonView 视图过滤：仅 workflow 使用，其他模块未按视图控制序列化字段。
建议操作： 推广 (a) 对于大请求体场景（消息批量、文件导入），推广流式解析；(b) 对于需要不同序列化策略的场景（API鉴权 vs 管理后台），推广 JsonMapper.Builder 创建独立实例；(c) 文档/Agent 模块的大 JSON 场景推广树模型替代字符串拼接。
P2-中
7. 分布式锁（@YdszDistributedLock）仅 workflow 使用
common-lock 提供了可重入锁、公平锁、多锁、读写锁、信号量、看门狗续期等完整能力。但仅 workflow 的 3 个 Service 使用了 @YdszDistributedLock。system/userinfo 等模块存在竞态风险的写操作未使用分布式锁（如 Config 更新、Tenant 创建等）。
建议操作： 补全 为 system 的 Config/Dict 级联更新、userinfo 的 Role/Permission 联级变更等关键操作补充 @YdszDistributedLock。
P2-中
8. SliceQuery 游标分页全仓零使用
common-domain 提供了 SliceQuery（游标分页）用于大数据量高性能分页。但全仓仍使用 PageQuery（OFFSET/LIMIT），这在千万级数据场景下存在性能瓶颈（深分页）。
建议操作： 推广 为 message 的 MsgLog（海量日志）、cronjob 的 JobLog（海量执行日志）等大数据量查询切换为 SliceQuery。

七、可落地的分阶段优化路线图

S1 — 紧急修复（2周内完成，P0）

  • 1.1 补充 ydsz-system / ydsz-userinfo 的 common-json 显式依赖 修复

    涉及：ydsz-system-domain/pom.xml, ydsz-userinfo-domain/pom.xml。在 domain 层显式声明 <dependency> ydsz-common-json，注释"为下游 server/web 模块提供传递依赖"。

  • 1.2 统一 message / cronjob 的 PageResult 分页响应 修复

    涉及 13 个 Controller：将 BaseResponse<Page<T>> 替换为 PageResult<T>，在 server 层进行数据转换。

  • 1.3 补齐 cronjob / literule 的 @RateLimit 防护 修复

    为两个模块的所有写操作接口补充 @RateLimit 注解，配置合理的频率限制策略。

S2 — 能力对齐（1个月内，P1）

  • 2.1 制定并推广 ydsz-common-cache 使用规范 推广

    输出缓存框架接入指南（Builder 链式创建 + @Cached 注解两种模式），优先在 workflow、literule、agent 三个模块试点推广 W-TinyLFU。

  • 2.2 补齐各模块 @Xss / @SensitiveData / @Idempotent 注解 补全

    为 system/userinfo/message/cronjob/literule/agent 的 Web DTO 补全 @Xss；为 system/userinfo 的 response DTO 补全 @SensitiveData；为 message Controller 补全 @Idempotent。

  • 2.3 完善 message 的 MessageJsonModule 实现 完善

    将当前抛 UnsupportedOperationException 的占位序列化器替换为实际实现，对标 ydsz-agent 的定制序列化器模式。

  • 2.4 为 workflow / cronjob 领域对象实现自定义序列化器 新建

    workflow 的 FlowDefinition/FlowNode/FlowEdge, cronjob 的 DagNode/DagEdge 应使用 SerializerRegistry 注册类型安全的序列化器，替代纯反射路径。

S3 — 深度优化（3个月内，P2）

  • 3.1 消息/日志大数据量场景推广 SliceQuery 游标分页 推广

    message 的 MsgLog 和 cronjob 的 JobLog 查询切换为 SliceQuery，消除深分页性能瓶颈。

  • 3.2 关键写操作推广 @YdszDistributedLock 补全

    system 的 Config/Dict 级联更新、userinfo 的 Role/Permission 联级变更补充分布式锁。

  • 3.3 大文件/流式场景推广 JsonParser 流式解析 推广

    消息批量导入、文件导入、Agent 大对话历史等场景从全量读取切换为流式解析。

  • 3.4 补充 ArchUnit 编译期架构测试 新建

    添加 ArchUnit 规则强制禁止 Jackson/FastJSON import、强制 domain 层显式声明 common-json、强制 Controller 分页返回 PageResult。

  • 3.5 探索多租户物理隔离方向 研究

    当前 ydsz-common-tenant 仅支持逻辑隔离（TenantLine 行级过滤），参考 ydsz-common-jdbc 的 DynamicRoutingDataSource 能力，规划数据库级/SCHEMA 级物理隔离方案。

八、总结

本项目在 JSON 引擎统一性 方面达到了国内一流水平——自研 YdszJson 完全替代了 Jackson/FastJSON，且通过根 pom.xml 的 Maven Enforcer 规则从编译期杜绝了竞争库的使用。但 公共能力的深层利用 方面存在显著短板：ydsz-common-json 的高级特性（流式解析、树模型、SPI 扩展、Builder 独立配置）仅 2-3 个模块使用；ydsz-common-cache 的高级缓存框架在 9 个业务模块中零采用；安全特性（@Xss / @SensitiveData）和分页规范（PageResult / SliceQuery）覆盖率严重不足。

上述 8 项发现与 3 阶段 13 条优化建议已按 P0→P1→P2 排列，每项均具备明确的涉及文件路径和改动方案。建议按 S1（2 周）→ S2（1 月）→ S3（3 月） 的节奏分批落地，每阶段完成后回归验证全仓编译通过即可闭环。
