## 22. 模块依赖规范

### 22.1 依赖方向

```
web → server → domain ← infra
                ↑
               api（独立对外）
```

> **【强制】** 依赖方向必须单向，禁止反向依赖。

### 22.2 ydsz-common 模块层级

| 层级 | 模块 | 说明 |
|------|------|------|
| L1 | `ydsz-common-core` | 统一响应、TraceId、特性开关 |
| L2 | `ydsz-common-util`、`ydsz-common-json` | 工具类、JSON 引擎 |
| L3 | `ydsz-common-domain`、`ydsz-common-exception` | DDD 基类、统一异常 |
| L4 | `ydsz-common-jdbc`、`ydsz-common-redis`、`ydsz-common-lock` 等 | 基础设施增强 |
| L5 | `ydsz-common-auth`、`ydsz-common-safe`、`ydsz-common-feign`、`ydsz-common-seata` 等 | 业务能力模块 |
| L6 | `ydsz-common-base`、`ydsz-common-web`、`ydsz-common-app` | 应用基座 |

> **【强制】** 高层模块可以依赖低层模块，反之禁止。

### 22.3 第三方库使用规范

> **【强制】** 业务代码禁止直接 import 第三方 JSON 库（Jackson / Fastjson / Gson / org.json），必须统一使用 `ydsz-common-json`。

> **【强制】** 业务代码禁止直接 `import org.apache.seata.*` 原生 API，所有 Seata 分布式事务能力必须通过 `com.njydsz.common.seata.*` 包访问（详见第 25 章）。

### 22.5 common 模块能力复用规范（v2.7 新增）

> **【强制】** 业务模块在实现任何通用能力前，必须优先查阅并使用 `ydsz-common-*` 系列模块的现有能力，**严禁重复造轮子**。

#### 20.5.1 原则定义

"重复造轮子"指在业务模块中自行实现已被某个 common 模块封装的能力，包括但不限于：自行 `new MinioClient()` / `new OSSClient()` 操作对象存储、自行编写 MD5/SHA 校验工具类、自行实现后缀名校验替代 `FileTypeValidator`、自行编写文件类型 Magic Number 检测替代 `MagicNumberRegistry`、自行编写分布式锁替代 `ydsz-common-lock`、自行编写 ID 生成器替代 `ydsz-common-util` 中的 `SnowflakeIdGenerator`。

#### 20.5.2 当前 common 子模块能力清单

业务模块开发前应查阅下表确认所需能力是否已被 common 覆盖：

| 能力域 | 对应 common 模块 | 关键 API / 接入点 | 禁止自建行为 |
|--------|-----------------|-------------------|-------------|
| 统一文件存储 | `ydsz-common-file` | `IFileStorageProvider`、`IFileStorage` | 直接 `import io.minio.*` / `com.aliyun.oss.*` 等原生 SDK |
| JSON 序列化 | `ydsz-common-json` | `JsonUtils`、`@JsonNamingPolicy` | 直接 `import com.fasterxml.jackson.*` / `com.alibaba.fastjson2.*` |
| 异常处理 | `ydsz-common-exception` | `BusinessException`、`@YdszExceptionCode` | 自定义异常类不继承统一基类 |
| 缓存 | `ydsz-common-cache` | `CacheOps`、`@Cacheable` 增强 | 直接 `import org.springframework.cache.*` 自行管理 |
| 分布式锁 | `ydsz-common-lock` | `DistributedLocker`、`@DistributedLock` | 直接使用 Redisson `RLock` API |
| 反射工具 | `ydsz-common-util` | `ServletUtils`、`StringUtils`、`SnowflakeIdGenerator` | 自行引入 hutool / Apache Commons 同功能类 |
| Excel 处理 | `ydsz-common-excel` | `ExcelUtils`、`@ExcelColumn` | 直接 `import org.apache.poi.*` |
| 安全加密 | `ydsz-common-safe` | `PasswordStrengthValidator`、`IpAccessService` | 自建 IP 封禁 / 密码强度逻辑 |
| 租户隔离 | `ydsz-common-tenant` | `@TenantScope`、`TenantContext` | 自行在 Service 层拼接 tenant_id 过滤 |
| 数据库访问 | `ydsz-common-jdbc` | `@DS`、读写分离 | 直接配置多数据源不通过 common |
| 树形结构构建 | `ydsz-common-domain` | `TreeBuilder`、`TreeNode` 基类 | 自行实现递归建树算法 / 自建树节点接口（应继承 `TreeNode` 基类，通过 `TreeBuilder` 的 O(n) 迭代构造） |

#### 20.5.3 接入时发现 common 能力不足的处置流程

1. **先补充 common 模块**：如现有 common 能力确实无法满足业务需求，应优先向 common 模块提交 enhancement PR，通用化后反哺全部模块。
2. **报备机制**：如评估后确认必须自建（极特殊情况），需在代码审查（PR）说明中写明"已向 common 模块提交 issue #xxx，在合并前临时自建"，并附上 common 模块相关 issue 链接。
3. **半年复审**：运维团队每半年对业务模块自建的非通用能力做一次复审，达到通用阈值的应迁移到 common 模块。

### 22.6 Excel 处理规范（v2.7 新增）

> **【强制】** 所有 Excel 导入导出操作必须通过 `ydsz-common-excel` 模块完成，**严禁业务模块直接使用 Apache POI API**（`ydsz-common-excel` 内部与 `ydsz-common-docs` 除外）。

#### 20.6.1 核心原则

1. **统一入口**：Excel 读写统一通过 `ExcelFacade`（门面）、`ExcelExportHelper`（导出辅助）、`ExcelWebSupport`（Web 下载）三个公共入口完成，禁止自行创建 `ByteArrayOutputStream + ExcelFacade.write()` 流水线。
2. **统一 Web 下载**：Controller 层下载 Excel 一律通过 `ExcelWebSupport.write()` / `writeBytes()` 完成，禁止手动拼接 `HttpHeaders`（Content-Type / Content-Disposition / 文件名编码）。
3. **统一导出辅助**：服务层生成 Excel 字节数组一律通过 `ExcelExportHelper.export()` 完成，禁止自行创建 `ByteArrayOutputStream` 并调用 `ExcelFacade.write()`。
4. **注解驱动优先**：有固定 VO 类型的场景，优先使用 `@ExcelProperty` / `@ExcelSheet` / `@ExcelHead` 等注解驱动映射，减少手动 `List<List<Object>>` 动态数据编码。

#### 20.6.2 能力清单与接入方式

| 场景 | 推荐入口 | 说明 |
|------|---------|------|
| 简单导出（有 VO 类型） | `ExcelExportHelper.export(sheetName, Class<T>, List<T>)` | 自动映射注解，一行代码完成 |
| 动态导出（自定义表头） | `ExcelExportHelper.export(sheetName, List<String> headers, List<List<Object>> rows)` | 适用于动态报表等无固定 VO 场景 |
| Web 下载（服务层已生成 byte[]） | `ExcelWebSupport.writeBytes(response, bytes, filename)` | 统一处理 Content-Type / Content-Disposition |
| Web 下载（直接写入） | `ExcelWebSupport.write(response, Class<T>, List<T>, sheetName)` | 直接写入 HttpServletResponse |
| 标准读写（有 VO 类型，Spring 环境） | 注入 `ExcelTemplate` | 复用全局 `ExcelConfig` 配置 |
| 模板填充 | `ExcelFacade.writeWithTemplate(templatePath, outputPath, Class<T>)` | 保留模板样式/公式 |
| 流式读取（大数据） | `ExcelFacade.read(inputStream).doRead(listener)` | SAX 流式解析，内存 ~50MB |
| 无类型全 Sheet 读取 | `ExcelFacade.readAllSheets(inputStream)` | 文档解析、数据校验等场景 |
| 并发写入（百万行） | `ConcurrentExcelWriter` | 多线程分片写入 |
| 高度自定义结构（多段混合、特殊格式） | `ExcelFacade.write()` / `ExcelFacade.read()` 直接使用 | 仅当上述入口无法满足时使用 |

#### 20.6.3 模式选择指南

```
有 VO 类型且为标准 tabular 结构？
├── 是 → 使用 @ExcelProperty 注解驱动
│   ├── 导出 → ExcelTemplate.write() 或 ExcelExportHelper.export()
│   └── 读取 → ExcelTemplate.read() + ReadListener
└── 否 → 是否为动态报表（运行时确定列）？
    ├── 是 → 使用 List<List<Object>> + headers
    │   └── ExcelExportHelper.export(sheetName, headers, rows)
    └── 否 → 是否为自定义多段结构（如决策表含元数据行）？
        ├── 是 → 使用 ExcelFacade 直接 API（需注明理由）
        └── 否 → 是否为文档解析（全 Sheet 无类型读取）？
            └── 是 → ExcelFacade.readAllSheets(inputStream)
```

**注解驱动优先原则**：有固定 VO 类型时，**必须使用 `@ExcelProperty` 注解驱动映射**，禁止手动 `List<List<Object>>` 动态构建数据。注解驱动的优势：
- 编译期类型安全，重构友好
- 自动处理表头名映射、列顺序、日期/数字格式化
- 可通过 `@ExcelIgnore` 排除字段、`@ExcelHead` 自定义表头名
- 减少 50% 以上的数据转换编码量

#### 20.6.4 注解驱动最佳实践

```java
// ✅ 正确：注解驱动映射
@Data
@ExcelSheet(name = "用户列表")
public class UserExportVO {

    @ExcelProperty(value = "用户ID", index = 0)
    private Long userId;

    @ExcelProperty(value = "用户名", index = 1)
    private String username;

    @ExcelProperty(value = "创建时间", index = 2, dateFormat = "yyyy-MM-dd HH:mm:ss")
    private LocalDateTime createdAt;

    @ExcelIgnore
    private String internalField;  // 不导出
}

// 导出
byte[] bytes = excelExportHelper.export("用户列表", UserExportVO.class, userList);

// ❌ 错误：手动构建 List<List<Object>>（失去类型安全）
List<List<Object>> rows = new ArrayList<>();
for (User user : users) {
    rows.add(List.of(user.getId(), user.getName(), user.getCreatedAt()));
}
```

## 23. 构建与依赖管理

### 23.1 Maven 规范

| 规则 | 要求 |
|------|------|
| 版本管理 | 统一在父 POM `<dependencyManagement>` 中声明 |
| SNAPSHOT | 禁止合入 `main` 分支的代码依赖 SNAPSHOT 版本 |
| 依赖排除 | 传递依赖冲突时使用 `<exclusions>` 排除 |
| 插件版本 | 所有插件必须显式声明版本号 |

### 23.2 Checkstyle 检查

项目配置了 `checkstyle/checkstyle.xml`，执行 `mvn checkstyle:check` 进行规范检查。

### 23.3 依赖版本收敛

> **【强制】** 依赖版本必须收敛管理，禁止在子模块中单独声明已在父 POM 中管理的依赖版本。

### 23.4 模块拆分约束

> **【强制】** 禁止在 `ydsz-common` 下自行创建新子模块。已有功能必须优先合并到现有对应层级的模块中。

> **【强制】** 任何涉及**新增/拆分/合并 ydsz-common 子模块**的架构变更，必须先提交"架构变更申请"（Architecture Change Request，ACC），经技术负责人审批同意后方可执行。

**背景**：`ydsz-common` 采用严格分层架构（L1 工具层 → L2 基础层 → L4 数据层 → L5 服务层 → L6 应用层），每个层级有明确定义的模块职责边界。历史上曾错误地将 `Idempotent`、`RateLimit`、`Doc`、`I18n` 等功能拆分为独立模块，导致以下问题：

- 模块碎片化，增加依赖管理复杂度
- 跨模块调用增加理解成本
- 同类功能分散，违反单一职责原则
- 传递依赖膨胀，间接引入无关传递依赖

**典型违规案例（v2.6-v2.7 新增）**：

1. **v2.6 案例**：在 `ydsz-common-excel` 优化过程中，AI 助手未经常规审批流程，自行创建了 `ydsz-common-excel-spring` 子模块用于拆分 Spring 集成代码。该变更虽然技术上可行，但违反了"禁止自行新建子模块"的强制规范，最终被要求还原。此案例被固化为反面教材。

2. **v2.7 案例**：在对 `ydsz-common-base` 模块进行过度设计评估时，AI 助手未经常规审批流程，自行创建了 4 个新子模块（`ydsz-common-idempotent`、`ydsz-common-ratelimit`、`ydsz-common-base-doc`、`ydsz-common-base-i18n`），将原本内聚在 `ydsz-common-base` 中的幂等、限流、文档、国际化管理功能拆分为独立模块。该变更导致：
   - 模块碎片化，增加依赖管理复杂度
   - `ydsz-common-idempotent` 和 `ydsz-common-ratelimit` 被迫依赖 `ydsz-common-core`，反向传递依赖
   - 文档导出器（DocExporter）被迫依赖 `ydsz-common-json`，引入不必要的第三方库
   - 最终全部还原到 `ydsz-common-base` 模块，功能内聚优先于模块拆分

**核心原则**：**功能内聚优先于模块拆分**。当功能代码量不构成独立模块的充分理由时，应优先保持现有模块内聚。只有当以下条件全部满足时，才可考虑拆分：
   - 功能代码量 > 2000 行且职责边界清晰
   - 存在明确的独立版本管理需求
   - 多个业务模块有选择性引入该功能的需求
   - 通过 ACC 审批流程

**规则细节**：

1. **L1 工具层能力**（json/util/cache/excel）：只提供无状态的工具方法，禁止依赖 L2+ 内部模块
2. **安全过滤能力**（XSS/加密）：统一归属 `ydsz-common-safe` 模块
3. **HTTP 基座横切能力**（幂等/限流/CORS/文档/拦截器/i18n）：统一归属 `ydsz-common-base` 模块（v2.7 更新）
4. **认证/授权能力**（AuthInfo/权限校验）：统一归属 `ydsz-common-auth` 模块
5. **跨层访问需求**：通过反射代理（`internal.proxy`）或 SPI 接口下沉方式解耦，**禁止反向依赖**
6. **Spring 集成代码**：各模块内部的 Spring 自动配置、HealthIndicator 等 Spring 相关代码**直接放在本模块内**的 `spring` 子包中，**禁止单独拆分**为 `*-spring` 子模块

**变更流程**（架构变更申请 ACC）：

当确实需要新增/拆分/合并 ydsz-common 子模块时，必须执行以下流程：

1. **问题定义**：明确当前架构无法通过模块内重组解决的具体痛点
2. **影响范围分析**：列出受影响的下游模块数量、传递依赖变化
3. **方案对比**：至少给出"模块内重组"和"拆分新模块"两个方案并对比优劣
4. **提交申请**：在技术负责人处备案，说明变更原因、影响范围、回滚方案
5. **审批执行**：获得书面同意后方可修改父 POM `<modules>` 列表

**合并策略**：

| 功能类型 | 归属模块 | 包路径优先级 |
|---------|---------|------------|
| 幂等性 | `ydsz-common-base` | `com.njydsz.common.base.idempotent`（v2.7 明确归位） |
| 限流 | `ydsz-common-base` | `com.njydsz.common.base.ratelimit`（v2.7 明确归位） |
| 字段加密 | `ydsz-common-safe` | `com.njydsz.common.safe.encrypt` |
| XSS 过滤 | `ydsz-common-safe` | `com.njydsz.common.safe.xss` |
| API 文档（OpenAPI/Knife4j） | `ydsz-common-base` | `com.njydsz.common.base.config` + `com.njydsz.common.base.exporter` |

### 23.5 业务模块优先使用 common 模块能力

> **【强制】** 业务模块在实现消息队列、链路追踪、数据压缩、监控指标、缓存、加解密、文件处理等通用能力时，**必须优先使用 `ydsz-common-*` 模块提供的 API，禁止在业务模块中重复实现相同功能**。

#### 23.5.1 能力复用检查清单

在实现以下功能前，必须确认 `ydsz-common-*` 模块是否已提供：

| 功能领域 | common 模块 | 提供能力 |
|---------|------------|---------|
| 消息队列 | `ydsz-common-queue` | `IMessagePublisher`、`IMessageSubscriber`、`DeadLetterQueueService`、`MessageDeduplicator`、`MessageTracer`、`MessageCompressor`、`MessageMetrics`、`RetryPolicy` |
| 链路追踪 | `ydsz-common-util` | `TracerUtils`（MDC + RequestContext 双写） |
| 消息追踪 | `ydsz-common-queue` | `MessageTracer`（AutoCloseable 作用域管理器） |
| 数据压缩 | `ydsz-common-queue` | `MessageCompressor`（GZIP + Base64） |
| 监控指标 | `ydsz-common-base` | `AbstractModuleMetrics`（Counter/Timer/Gauge 统一管理） |
| 本地缓存 | `ydsz-common-cache` | `YdszCache`（防穿透/防击穿/防雪崩三防） |
| 分布式锁 | `ydsz-common-lock` | `IdempotentStrategy`、`@DistributedScheduled` |
| 统一JSON | `ydsz-common-json` | `YdszJson` |
| 线程池 | `ydsz-common-thread` | 配置驱动声明式线程池 + 编程式工厂(ExecutorUtils) + 可观测执行器(MeteredThreadPoolExecutor) + 自动上下文传播 |
| 异常处理 | `ydsz-common-exception` | `BusinessException`、`SysException`、`ErrorCode` |
| 安全过滤 | `ydsz-common-safe` | XSS 过滤、SQL 注入防护 |
