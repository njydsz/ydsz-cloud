# 云顶编码规范合规审计报告

> **审计对象**：`ydsz-cloud`（Spring Boot 4.1 + Spring Cloud 2025.1.2 微服务多模块平台）
> **基准规范**：`docs/云顶编码规范.md`（v2.7，2026-08-16 生效）
> **审计日期**：2026-08-16
> **审计方式**：静态文本扫描（3087 个 `.java` 文件，约 3.77 万行）+ 代表性文件人工抽查 + `docs/checkstyle.xml` 配置与 `pom.xml` 集成核查
> **环境说明**：本机未安装 Maven，无法执行 `mvn checkstyle:check` / `mvn verify`，故合规结论基于静态证据，**不依赖编译结果**。

---

## 一、总体结论

**结论：规范“设计落地较好、执行门禁缺失、少数强制规则存在代码级违规”。**

团队对云顶规范的核心红线理解到位、执行质量高（见第四节正面清单）；但**质量门禁（checkstyle）虽然已在 `pom.xml` 中配置，却并未真正拦截**，导致一批「强制」类格式/结构规则在代码中持续累积；同时有少量**明确的强制规则在业务模块层面存在系统性违规**（自建线程池、模块直接依赖、单元测试缺失）。

| 维度 | 评估 | 关键证据 |
|------|------|----------|
| 编码红线（FQN / 第三方 JSON / Seata 原生 / EventStore） | 🟢 优秀 | 行内 `new`/`cast` FQN = 0；业务代码直接 import JSON 库 = 0；业务模块 seata 原生 import = 0；EventStore 引用 = 0 |
| 安全/认证/审计能力复用（auth/safe/audit/feign/event） | 🟢 优秀 | `@AuthApiPermission` 386 处、`@Audit` 372 处、`@EnableYdszAuth` 9 处、Feign 原生注解 0、Fallback 误返回 0 |
| 基础格式（Tab / CRLF / 换行 / BigDecimal(double) / System.out） | 🟢 良好 | Tab=0、CRLF=0、BigDecimal(double)=0；System.out 仅集中在 CLI 工具 |
| 模块依赖与分层（common 复用 / 误拆子模块） | 🟡 基本合规 | v2.7 误拆子模块已还原；但 `cronjob`/`workflow` 直接依赖 `ydsz-message-api`（违反 ADR-001） |
| 并发规范（统一线程池 15.4.1） | 🔴 违规 | 业务模块约 20 处直接 `new ThreadPoolExecutor`/`Executors.new*`（cronjob/literule/agent/gateway） |
| 单元测试（13.5 覆盖率） | 🔴 严重缺失 | 8 个业务模块测试文件 0–5 个，整体测试占比 **4.8%**（main 2939 / test 148） |
| 构建期质量门禁（21.2 checkstyle） | 🔴 未落地 | 87 处通配符 import、329 文件行长>120、1 文件>2000 行仍存于 `src/main`，证明 `checkstyle:check` 未真正拦截 |
| Import 分组排序（5.3 强制） | 🟡 未遵守 | 抽样 `CompanyController`/`ConfigServiceImpl` 内部包与第三方包混排 |
| 超长文件（FileLength≤2000） | 🟡 1 处 | `FlowDefinitionServiceImpl.java` 2227 行 |

## 二、方法论与范围

1. **全量静态扫描**（Python 脚本，排除 `target/` 与 `.idea/`）：对 3087 个 `.java` 文件逐行检测 Tab、CRLF、行长、通配符 import、行内 FQN、System.out/err、printStackTrace、`BigDecimal(double)`、`SimpleDateFormat`、自建线程池、`Caffeine/Guava` 直建、seata 原生 import、第三方 JSON import、原生 `@EnableFeignClients`、`OutboxService`/`EventStore` 引用、TODO/FIXME、`== 数字` 等。
2. **架构/依赖核查**：`pom.xml` 依赖图（业务模块是否直连 `ydsz-message`）、`checkstyle.xml` 与 `pom.xml` 集成方式、common 子模块清单（是否误拆）。
3. **人工抽查**：`CompanyController`、`ConfigServiceImpl` 等代表性文件，核查 import 排序、Javadoc、命名、异常/日志、common 能力复用。
4. **局限性**：① 未编译，无法检测「未使用 import」「类型解析错误」「圈复杂度」等需语义分析的项（这些恰由 checkstyle/PMD 负责，见第三·2）；② `== 数字` 魔法值扫描噪声大（绝大多数为 `size()==0` 等控制流），仅作定向线索，不作硬违规计数；③ 安全脱敏（`@Sensitive`）、缓存 TTL 硬编码（18.5.4）等维度未做全量扫描，建议后续定向抽查。

## 三、详细发现（按优先级）

### 🔴 P0 — 阻断级 / 强制规则系统性失守

#### P0-1. 单元测试严重缺失（违反 13.5，且与 README 宣称的 CI 门禁矛盾）
- **证据**：测试文件共 **148** 个（其中 `ydsz-common` 占 143，作为基础设施底座尚可）；**8 个业务模块几乎零测试**：`ydsz-agent=0`、`ydsz-cronjob=0`、`ydsz-message=0`、`ydsz-nextwiki=0`、`ydsz-system=0`、`ydsz-userinfo=0`、`ydsz-workflow=0`，`ydsz-gateway=4`、`ydsz-literule=1`。整体测试占比 **4.8%**，远低于「核心逻辑 ≥80%、分支 ≥70%」要求。
- **影响**：核心业务（调度、工作流、规则、消息、权限）无回归保护，重构与迭代风险极高；README 声称 `mvn verify` 自动跑单测，实际门禁为空。
- **建议**：优先为 `*-server` 层核心领域逻辑（调度分发、流程引擎、规则求值、RBAC 判定）补单测；先立「新增代码必须带测试」的 PR 门禁，再逐步回填存量。

#### P0-2. 质量门禁（checkstyle）配置但未落地/未通过
- **证据**：`pom.xml` 已集成 `maven-checkstyle-plugin`（`configLocation=docs/checkstyle.xml`，扫描 `src/main`）。但以下**强制级**问题大量存在于 `src/main`，说明门禁从未真正拦截或长期被忽略：
  - 通配符 import **87** 处（违反 5.2 `AvoidStarImport`）；
  - 行长 >120 文件 **329** 个（违反 `LineLength`，排除 import/package/URL 后仍有 1+ 行超长）；
  - 单文件 >2000 行 **1** 个（违反 `FileLength`）。
- **影响**：规则停留在纸面，团队无持续反馈，违规随迭代累积。
- **建议**：将 `checkstyle:check` 绑定到 `verify` 阶段并保证 `failOnViolation=true`；或在 PR 流水线加 checkstyle 卡点 + 增量扫描；配套引入 `spotless`/`editorconfig` 自动格式化。

### 🔴 P1 — 强制规则在业务模块存在真实违规

#### P1-1. 业务模块自建线程池，违反统一线程池管理（15.4.1 强制）
- **证据**：在 `ydsz-cronjob`、`ydsz-literule`、`ydsz-agent`、`ydsz-gateway` 业务模块中，约 **20 处**直接用 `new ThreadPoolExecutor` / `new ScheduledThreadPoolExecutor` / `Executors.newScheduledThreadPool` / `newSingleThreadScheduledExecutor` 创建长生命周期线程池（如 `DefaultTaskDispatcher`、`JobScanner`、`SecondLevelScheduler`、`PreciseSchedulingManager`、`ParallelRuleEvaluator`、`RuleChain`、`ModelInputRegistry`、`FactProviderRegistry`、`NacosRouteDefinitionRepository`）。
- **说明**：15.4.1 的豁免仅限「`ydsz-common-thread` 内部实现 / 方法内短生命周期临时池 / JDK21 `Executors.newThreadPerTaskExecutor()`」。上述长生命周期字段级池不属于豁免。
- **建议**：迁移到 `ydsz.thread.pools.<name>` 声明式配置 + `@Resource`/`@Async` 注入；`ScriptRule` 中的 `Executors.newVirtualThreadPerTaskExecutor()` 属合规豁免，保留并补 `// CHECKSTYLE.OFF` 注释。

#### P1-2. 业务模块直接依赖 `ydsz-message`，违反 ADR-001 / 20.4.6（强制）
- **证据**：`ydsz-cronjob/ydsz-cronjob-server/pom.xml:78` 与 `ydsz-workflow/ydsz-workflow-server/pom.xml:113` 直接声明 `ydsz-message-api` 依赖。
- **规则**：ADR-001 规定业务模块发通知**只能依赖 `ydsz-common-notify` 的 `NotifyHelper`**，`ydsz-message` 仅通过 `NotifyChannelBridgeConfiguration` 运行时桥接，禁止业务模块直连。
- **建议**：移除上述两个 `pom.xml` 中的 `ydsz-message-api` 依赖，改为通过 `NotifyHelper` 统一发送；核查是否确有 `MessageChannel` 直调代码一并清理。

#### P1-3. Import 分组排序未遵守（5.3 强制）
- **证据（人工抽查）**：`CompanyController.java` 将内部包 `com.njydsz.common.audit.*` 置于 `org.springframework.*` **之前**，又把 `com.njydsz.common.core.*`、`com.njydsz.common.lock.*` 置于 `lombok`/`jakarta` **之后**；`ConfigServiceImpl.java` 将 `lombok` 置于内部包**之后**、`mybatis-plus` 与 `spring` 之间多插空行。二者均违反「`java → 第三方 → 内部(com.njydsz) → 静态`，组间单空行」的强制顺序。
- **建议**：开启 IDE `Optimize Imports` + 排序，配合 P0-2 的 checkstyle `ImportOrder` 卡点一次性治理。

#### P1-4. 通配符 import 87 处（5.2 强制）
- **证据**：主要集中在 `ydsz-common`（`import java.lang.annotation.*;` 于各注解类、`import java.util.*;` 于多文件），另 `ydsz-cronjob`、`ydsz-userinfo` 各 1 处。
- **说明**：功能无影响，但属强制红线且 checkstyle 可拦截；多为历史遗留。
- **建议**：随 P0-2 门禁落地后批量 `Optimize Imports` 清除。

#### P1-5. 单文件超 2000 行（FileLength）
- **证据**：`ydsz-workflow/ydsz-workflow-server/.../FlowDefinitionServiceImpl.java` **2227 行**（违反 `FileLength≤2000`）。
- **建议**：按职责（定义 CRUD / 版本 Diff / 校验 / 导入导出）拆分为多个 `*Delegate`/`*Helper`，同时呼应「单方法 ≤80 行」原则。

### 🟡 P2 — 建议优化 / 定向抽查

- **P2-1 行长 >120（329 文件）**：多为单行超长（SQL/正则/链式调用），工作量低；随 P0-2 门禁自然收敛。
- **P2-2 `SimpleDateFormat` 6 处**：集中在 `ydsz-common-json` 的 legacy-date 解析回退分支（局部变量、非共享，**线程安全无虞**，但属旧 API）。建议逐步改用 `DateTimeFormatter`；非紧急。
- **P2-3 魔法值 `== 数字`（自动命中 416 行）**：抽样显示绝大多数为 `size()==0`、`total==0`、`statusCode==401/403/404` 等控制流/HTTP 状态码，**非业务状态码魔法值**。建议针对「业务状态/类型整数字面量比较」做定向审查（如 `status == 3`），无需全量整改。
- **P2-4 安全能力复用抽查（17.6 / 26）**：尚未全量扫描业务模块是否存在自写 XSS/加密/脱敏/IP 封禁/权限判定。建议定向核查 `ydsz-userinfo`、`ydsz-gateway` 是否严格走 `common-safe`/`common-auth`，无重复造轮子。
- **P2-5 缓存 TTL/容量硬编码（18.5.4）**：建议抽查 `YdszCache.newBuilder()` 调用是否均经 `.name()` 且 TTL/容量来自 YAML，未硬编码。
- **P2-6 `@DataScope` 双层注解（26.5.2）**：Facade 层与实现层只保留一处，建议核查是否存在重复标注。
- **P2-7 `System.out` 复核**：49 处中约 40 处集中在 `ConfigCliTool`（CLI 标准输出，合规）；其余均为 Javadoc 注释中的示例代码（如 `RuleEffectivenessService`/`RuleLifecycleService`/`RuleTestRunner` 注释），**无真实生产调用**，合规。仅建议确认无遗漏。

## 五、下一步优化完善建议（行动路线）

### 第一阶段：把门禁立起来（最高优先级，1–2 周）
1. **落实 checkstyle 门禁**：`pom.xml` 中 `maven-checkstyle-plugin` 绑定 `verify` 且 `failOnViolation=true`；PR 流水线加 checkstyle 增量卡点。
2. **引入自动格式化**：`spotless`（Google-Java-Format）+ `.editorconfig` 一键对齐；一次性批量修复 87 通配符 import、329 行长、import 排序。
3. **建立测试门禁**：`mvn verify` 必须跑单测；设定「新增/修改核心逻辑须带单测」的 PR 规则，先堵增量。

### 第二阶段：消除强制规则代码级违规（2–4 周）
4. **线程池治理**：`cronjob`/`literule`/`agent`/`gateway` 约 20 处自建池迁移到 `ydsz-common-thread` 声明式配置；保留合规的虚拟线程豁免并补齐注释。
5. **解除 `ydsz-message` 直连**：`cronjob-server`、`workflow-server` 改用 `ydsz-common-notify.NotifyHelper`。
6. **拆分超大文件**：`FlowDefinitionServiceImpl`（2227 行）按职责拆分。

### 第三阶段：补齐测试与定向抽查（持续）
7. **补单元测试**：优先覆盖 `*-server` 核心领域逻辑（调度分发、流程引擎、规则求值、RBAC），目标核心逻辑 ≥80%。
8. **定向抽查**：安全脱敏/加密/权限（P2-4）、缓存 TTL 硬编码（P2-5）、`@DataScope` 双层（P2-6）、业务状态码魔法值（P2-3）。
9. **周期复检**：每月跑一次本审计脚本（见 `docs/` 下 `_audit_scan*.py`），跟踪 P0/P1 收敛曲线。

### 6.3 剩余项的标准化修复路线（需在 JDK21 / IDE 环境执行）

   - `pom.xml` 已绑定 `validate` + `failOnViolation=true`；问题在于本地 `mvnw-local.sh` 用 `-Denforcer.skip=true` 且 dev 流程未真正跑 `validate`。
   - 动作：CI 流水线加 `mvn checkstyle:check`（或 `mvn verify`）；本地开发统一执行 `mvn checkstyle:check` 做增量卡点。
   - 引入 `spotless`（Google-Java-Format）+ `.editorconfig`，PR 卡点自动格式化，一次性清除 42 通配符 import、714 行长、import 排序。

2. **线程池治理（P1-1，参照 Nacos exemplar）**
   - 业务模块（cronjob / literule / agent）的 `new ThreadPool*` / `Executors.new*`：全部改为 `ydsz.thread.pools.<name>` 声明 + `applicationContext.getBean("<name>Executor", ThreadPoolTaskExecutor.class)` 注入；每个模块补 `ydsz-common-thread` 依赖；对应 YAML 增加 pool 配置（可放 Nacos 共享配置 `ydsz-common.yaml`）。
   - 工具/桥接类（`ExecutorUtils`、`SeataExecutors`、`common-cache` / `common-event` 内部池）：若确属基础设施自管池，按 `AuditAutoConfiguration` 先例加 `// CHECKSTYLE.OFF: ThreadPoolCreate` 注释豁免并说明原因。
   - 合规虚拟线程豁免（`ScriptRule` 的 `newVirtualThreadPerTaskExecutor` 等）：补 `// CHECKSTYLE.OFF` 注释说明 JDK21 虚拟线程豁免。

3. **超大文件拆分（P1-5）**
   - `FlowDefinitionServiceImpl`（2221 行）按职责拆为 `*Delegate` / `*Helper`（定义 CRUD / 版本 Diff / 校验 / 导入导出），并对照「单方法 ≤80 行」。

4. **单元测试（P0-1）**
   - 优先为 `*-server` 核心领域逻辑（调度分发、流程引擎、规则求值、RBAC）补单测；先立「新增/修改核心逻辑须带单测」PR 门禁堵增量，再回填存量。

5. **定向抽查（P2）**
   - P2-3 魔法值：针对「业务状态/类型整数字面量比较」做定向审查（自动命中多为 `size()==0` 等控制流，非业务状态码）。
   - P2-5 缓存 TTL/容量：抽查 `YdszCache.newBuilder()` 调用是否均经 `.name()` 且 TTL/容量来自 YAML，未硬编码。
   - P2-6 `@DataScope` 双层注解：Facade 层与实现层只保留一处。

6. **周期复检**
   - 运行 `python3 docs/code-audit.py --json _audit_result.json` 跟踪 P0/P1 收敛曲线；建议将 `docs/code-audit.py` 入库作为复检工具（或加入 `.gitignore` 避免污染版本库）。
