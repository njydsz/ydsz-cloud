一、合规绿灯项 已达标

检查维度结论

二、P0 阻断级问题 — 构建期门禁失效 最高优先级

P0-1checkstyle 全局校验被跳过，纯净度门禁形同虚设
根 pom.xml 第 47 行 <checkstyle.skip>true</checkstyle.skip>，导致 checkstyle 插件绑定的 validate 阶段校验全部跳过。checkstyle v3.2 规则定义极其完善（JSON 红线、POI/Caffeine/Ehcache 禁用、Executors 禁用、集合容量、Javadoc、命名、复杂度等），但构建期完全不执行——一旦有人引入违规代码，CI 无法拦截，当前业务层"零违规"全靠人工自觉，不可持续。
D:\Code\open\ydsz-cloud\pom.xml:47  |  docs\checkstyle.xml（规则已就绪，仅开关关闭）
P0-2L1 工具层纯净度校验默认跳过
ydsz-common/pom.xml 第 68 行 <l1.module.skip>true</l1.module.skip>，L1 模块（json/util/cache/excel）禁止反向依赖 L2+ 的 enforcer 规则不生效。L1 模块可能悄悄引入对 core/domain/jdbc/redis 等的反向依赖而不被发现，破坏 L1-L6 单向依赖约束。

三、P1 架构一致性问题 需收敛

P1-1ArchUnit 架构测试依赖已引入但零落地
ydsz-common-util 与 ydsz-common 父 pom 声明了 archunit-junit5 依赖（标注 P3-2 编译期 enforce），但全项目搜索 @AnalyzeClasses / ArchRule 零结果——没有任何架构测试类。编译期架构反模式约束完全缺失，DDD 分层依赖方向、common 层单向依赖目前只能靠 checkstyle（且已被跳过）和人工 review 保证。
搜索 @AnalyzeClasses | ArchRule → No matches found
P1-2common-redis 绕过 common-cache 直接用 Caffeine
ydsz-common-redis 4 个文件直接 import com.github.benmanes.caffeine（MultiLevelCacheProvider / MultiLevelCacheAutoConfiguration / CacheProvider / RedisProperties）。作为多级缓存的本地层实现，应通过 L1 的 common-cache 统一封装暴露能力，而非 L4 数据层模块直接操作底层缓存库，造成缓存能力分散在两个模块、职责边界不清。
ydsz-common-redis/.../multilevel/MultiLevelCacheProvider.java 等 4 文件
P1-3多 common 模块各自创建线程池，未统一走 common-thread
common-cache（CacheThreadPoolManager）、common-audit、common-event、common-queue、common-search、common-sentry 等模块各自 new ThreadPoolExecutor / ScheduledThreadPoolExecutor。common-cache 虽用 // CHECKSTYLE.OFF 注释豁免声称"15.4 授权层"，但与"统一线程池管理"理念冲突，导致线程池散落各模块、无法统一监控与调优、关闭时序难以协调。建议这些模块的线程池统一委托 common-thread 管理。
CacheThreadPoolManager.java:140 及 common-audit/event/queue/search/sentry 多处

五、下一步优化建议（可执行待办）

按 P0 → P1 → P2 顺序推进，每项完成后回写基线文档消除 doc drift。

  • P0-1恢复 checkstyle 构建门禁：将 checkstyle.skip 改回 false，先单独执行 mvn checkstyle:check 统计违规量，逐模块清零后再纳入 CI 强制门禁（failOnError=true）。
  • P0-2激活 L1 纯净度校验：将 l1.module.skip 改回 false，校验 json/util/cache/excel 是否存在对 L2+ 的反向依赖，有则先解耦再开启。
  • P1-1编写 ArchUnit 架构测试：在 ydsz-common-core 或新建 arch 模块中编写 @AnalyzeClasses 测试，至少覆盖三条铁律：① 业务模块禁止 import 第三方 JSON/POI/Caffeine；② DDD 五层依赖方向（web→server→domain，infra 实现 domain 接口）；③ common 层 L1 禁止反向依赖 L2+。作为 P0 门禁的架构级补充。
  • P1-2收敛 common-redis 缓存职责：将 common-redis 的 Caffeine 本地缓存使用下沉到 common-cache，由 common-cache 暴露多级缓存统一门面，common-redis 仅负责 Redis 连接与分布式操作；或明确将 common-redis 的多级缓存部分并入 common-cache。
  • P1-3统一线程池到 common-thread：common-cache/audit/event/queue/search/sentry 的线程池改为委托 common-thread 创建与管理（通过 ysz.thread.pools.* 配置），移除各自 new ThreadPoolExecutor 与 CHECKSTYLE.OFF 豁免，实现全链路线程池可观测。
  • P2-1修复 ConfigCliTool 集合容量：26 处 new LinkedHashMap/ConcurrentHashMap 补充初始容量参数。
  • P2-2/3回写基线文档：更新 ydsz-system（136 文件/14 Service impl）与 ydsz-gateway（13 filter/19 config）的统计基线，消除 doc drift。
  • P2-4literule 测试线程池改用 common-thread。
