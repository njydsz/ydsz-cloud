🔴 P0 紧急修复（4 项）

1. main.ts 生产环境崩溃 — Sentry 调用未 import
P0 · 生产阻断

现状：src/main.ts 第 58-69 行调用 initSentry(...) 和 captureError(...)，但顶部未 import 这两个函数，且 auto-imports.d.ts 未含这两者。生产构建挂载后会抛 ReferenceError。

大厂标准：前端错误监控是生产环境的标配，Sentry SDK 必须正确初始化才能捕获运行时异常。Vue 3 项目集成 Sentry 需在 main.ts 中 import * as Sentry from '@sentry/vue' 并调用 Sentry.init()[1]。

风险：生产环境白屏 + Sentry 监控完全失效，所有前端异常无法上报。

影响范围：生产环境全部页面
预估工时：0.5 人日
在 main.ts 添加 import { initSentry, captureError } from '@/utils/sentry'；或在 auto-imports 配置中注册。同时将 @sentry/vue 和 @sentry/browser 添加到 package.json dependencies。
2. Sentry 依赖未声明 — @sentry/vue 和 @sentry/browser 缺失
P0 · 依赖缺失

现状：src/utils/sentry.ts 使用动态 import('@sentry/vue') 和 import('@sentry/browser')，但这两个包未在 package.json 中声明。虽然 Sentry SDK 设计为动态加载，但未声明依赖意味着 npm install 不会安装它们。

大厂标准：所有运行时依赖必须在 package.json 中显式声明，动态 import 的包也不例外[2]。

影响范围：错误监控系统
预估工时：0.5 人日
执行 pnpm add @sentry/vue @sentry/browser 添加到 dependencies；更新 .env.production 中 VITE_SENTRY_DSN 配置说明。
3. 硬编码凭证 — application.yml 中 DB 密码/JWT Secret/MinIO 凭证
P0 · 安全漏洞

现状：13 个模块的 application.yml 中存在硬编码默认凭证：

- DB 密码默认值 Limw1020（所有 DataSource 模块）

- JWT Secret 默认值 pmis-default-jwt-secret-key-please-change-...（auth 模块）

- MinIO 凭证 minioadmin/minioadmin（file 模块）

- OpenAI API Key sk-placeholder（agent 模块）

大厂标准：OWASP Top 10 A07:2021「身份识别和认证失效」明确将硬编码凭证列为高危漏洞[3]。所有敏感信息必须通过环境变量注入，配置文件中不得有任何默认值[4]。

风险：源码泄露即等于全部凭证泄露；等保三级测评将直接不通过。

影响范围：全部 13 个后端模块
预估工时：1 人日
将所有默认值移除，改为 ${DB_PASSWORD} 无默认值形式；在 .env.example 中说明必填项；CI 中添加凭证扫描（如 git-secrets/truffleHog）。
4. 4 个模块缺少 Redis 配置 — 但依赖 Redis 的 AOP 切面
P0 · 运行时错误

现状：audit、project、execution、agent 模块的 application.yml 中没有 spring.data.redis 配置，但它们依赖 common 模块中的 RateLimiterAspect、IdempotentAspect 等需要 StringRedisTemplate 的 AOP 切面。

风险：这些模块启动时可能因 Redis 连接失败而导致限流/幂等功能不可用，或在 AOP 切面触发时抛出运行时异常。

影响范围：audit / project / execution / agent
预估工时：0.5 人日
为这 4 个模块的 application.yml 添加 Redis 配置块（与 user/auth/config 模块一致）；或在 common 模块中添加 @ConditionalOnProperty 守护，Redis 不可用时降级跳过限流/幂等切面。

影响范围：前端项目详情聚合页 / 仪表盘汇总
预估工时：2 人日

9. ErrorBoundary 组件已编写但未接入
P1 · 健壮性缺陷

现状：ErrorBoundary.vue 基于 onErrorCaptured + Sentry 上报已实现，但仅在自身测试中被引用，未在 App.vue / layout / 任何页面实际包裹使用。错误边界能力形同虚设。

大厂标准：React/Vue 企业级应用必须在路由层级包裹 ErrorBoundary，防止局部错误导致整个应用白屏[5]。

影响范围：全部前端页面
预估工时：0.5 人日
在 App.vue 或 Layout.vue 中用 <ErrorBoundary> 包裹 <router-view>；为关键页面（如 dashboard、cockpit）添加独立 ErrorBoundary 实现局部降级。
10. 暗黑模式残缺 — 无持久化 / 无初始化 / 业务样式不适配
P1 · 体验缺陷

现状：三个问题：

- 无持久化：toggleTheme 不写 localStorage，刷新后重置

- 无初始化：app 启动未读取已存主题

- 业务样式割裂：variables.scss 全部为浅色硬编码，无 dark 变体，只有 Element Plus 组件跟随暗黑模式，自定义样式（.welcome-card / .metric-card 等）在暗黑模式下不切换

影响范围：全部前端页面
预估工时：2 人日
toggleTheme 写入 localStorage；app 初始化时读取并应用 dark class；将 variables.scss 改为 CSS 变量方案，在 [data-theme="dark"] 下覆盖变量值。
11. @RateLimit 注解已实现但零使用
P1 · 安全缺陷

现状：@RateLimit 注解和 RateLimiterAspect 已完整实现（基于 Redis 滑动窗口），但整个代码库中没有任何业务方法使用该注解。仅依赖网关层 Sentinel 限流。

大厂标准：登录、注册、密码重置、文件上传、数据导出等敏感接口必须在应用层添加限流注解，作为网关限流的补充[6]。

影响范围：AuthController / FileController / 导出接口
预估工时：1 人日
在 AuthController 登录/注册接口添加 @RateLimit(key = "login", permits = 5, timeout = 60)；在文件上传、数据导出接口添加限流；添加单元测试验证限流生效。

风险：消息消费者无法启动，异步消息发送/消费链路完全断裂；docker-compose.base.yml 中部署了 RocketMQ 但无服务连接。

影响范围：消息模块 / 审计异步 / 通知异步
预估工时：1 人日
在 message 模块 application.yml 添加 rocketmq.name-server 和 rocketmq.producer.group 配置；验证 MessageConsumer 能正常消费；或如果暂不使用则移除依赖避免误导。

大厂标准：企业级 SaaS 系统要求 i18n 覆盖率 ≥ 95%，所有用户可见文案必须通过 $t() 或 t() 引用[7]。

影响范围：约 35 个前端页面

📝 总结

审计结论：经 v1.1 优化批次后，项目在 DevOps 和架构健壮性上已显著提升，但第二轮深度审计发现 28 项残留缺陷。其中最严重的是 main.ts 生产环境崩溃（Sentry 调用未 import）、硬编码凭证（OWASP A07:2021）、4 模块 Redis 配置缺失，这 4 项 P0 级问题应在 1 周内紧急修复。
主要短板：v1.1 引入的 BFF 聚合、文件增强、工作流联动、报表生成等功能存在桩实现和 TODO，需补全真实业务逻辑。前端 ErrorBoundary 未接入、暗黑模式残缺、i18n 覆盖率仅 10%，是体验维度的三大短板。
优化策略：遵循"P0 紧急修复 → P1 功能补全 → P2 体验+DevOps → P3 改进"的顺序，分 4 个批次（33-36）推进。预计通过约 35-38 人日的持续优化，项目整体成熟度可从当前 82 分提升至 95 分以上，全面对标互联网大厂标准。
