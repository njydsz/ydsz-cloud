一、架构优化

📍 现状评估：架构设计已是项目最大亮点

四层分层（@core 零业务基础 → effects 业务无关能力 → comm 工具/状态/i18n → apps 微应用）依赖方向单向纯净。Qiankun 微前端采用 hover 按需预加载策略对标飞书方案，shared-auth 抽公共消除 9 个子应用约 360 行重复代码，RequestClient 封装拦截器管理 + retry + AbortController + 401 并发队列刷新，工程化程度高。

1.1 抽取子应用启动模板 P1
9 个子应用的 main.ts 中 bootstrap/mount/unmount 生命周期 + setupApp/createAppRouter 逻辑几乎一致，diff 仅注释和 basename 差异。虽然 setupSharedAuth(appName) 已收敛了 auth 部分，但启动样板仍有可观重复。
在 comm/effects/shared-business 中新增 createSubApp(options) 工厂函数，封装 qiankun 生命周期 + 路由创建 + 全局组件注册 + 指令注册 + 错误兜底，子应用 main.ts 缩减到 10 行以内配置式调用。
1.2 路由守卫下沉到 shared 层 P1
main 与各子应用的 setupCommonGuard（nprogress + loadedPaths）和 setupAuthGuard（白名单 + token 检查 + redirect）逻辑高度重复，仅白名单路径不同。
将守卫逻辑下沉到 shared-auth，通过参数注入白名单和 loginPath，各子应用只需 setupSharedGuards(router, { loginPath, whitelist }) 一行调用。
1.3 globalState 明文传递 token 存在安全隐患 P0
main/src/qiankun/global-state.ts 通过 initGlobalState 广播 { user, theme, locale, token, tenantId }，token 以明文形式在主子应用间传递，存在 XSS 窃取风险。大厂方案通常不在通信层传敏感凭据。
子应用通过 shared-auth 的 Proxy 延迟初始化机制直接从 SecureLS 读取 token（已有此能力），移除 globalState 中的 token 字段，仅传递 theme/locale/tenantId 等非敏感配置。
1.4 access store 职责过载，应拆分运行时态与持久化态 P1
accessStore 同时承载运行时态（accessMenus/accessRoutes/generateAccess）和持久化态（token/refreshToken/codes），职责混杂。auth-store.ts 中出现 (accessStore as any).refreshToken 类型断言绕过，说明类型设计已无法支撑现状。
拆分为 authStore（token/refreshToken/codes，持久化）和 accessStore（menus/routes/generateAccess，运行时），消除 as any 断言。
1.5 v-access 权限指令不支持响应式更新 P2
v-access:code / v-access:role 指令仅在 mounted 钩子判定一次，通过 el.remove() 物理移除元素。当权限码动态变更（如角色切换）时，已移除的元素无法恢复，需刷新整页。
改用 updated 钩子或渲染函数方案，监听 accessStore 变化动态控制 v-if，或推荐业务侧统一使用 <AccessControl> 组件 + useAccess() composable 替代指令。
1.6 tabbar Set 序列化隐患 P1
tabbarStore 的 cachedTabs 和 excludeCachedTabs 使用 Set<string>。虽然当前 persist 配置仅持久化 tabs 数组（未持久化 Set），但 Set 类型在 devtools 中不可观测，且如果后续误加入 persist 配置会静默丢失数据（JSON 序列化 Set 得到 {}）。
将 cachedTabs/excludeCachedTabs 改为 string[]，用 includes() 替代 has()；或在 persist 配置中显式声明 serializer 做数组↔Set 转换。

二、功能增强

📍 现状评估：功能覆盖面广，但工程化配套未跟上

9 个子应用覆盖用户/系统/项目/消息/定时任务/工作流/知识库/规则引擎/AI Agent 全链路，项目模块达 25 个视图（预算/合同/EVM/费用/收入/风险/费率等），功能深度可观。但 OpenAPI SDK 未真正接入业务、Storybook 组件文档空架子、错误监控仅 Web Vitals 缺异常上报。

2.1 OpenAPI SDK 生成后未接入业务，契约检测形同虚设 P0
openapi-generator-config.yaml 配置了 typescript-axios 输出到 src/api/sdk，CI 通过 git diff 检测接口变更阻断。但实际各 app 的 api/ 目录仍是手写文件（app.ts/dictType.ts 等），SDK 生成目录与手写 API 并存，契约检测实际无效——后端改了接口，前端手写代码不会自动同步。
制定迁移计划：(1) 确认 OpenAPI 规范文件来源（后端 Swagger 导出）；(2) 将手写 API 逐步替换为 SDK 调用，手写层仅保留业务逻辑包装；(3) CI 中加入 SDK 生成 + git diff --exit-code 强校验，确保 SDK 与后端契约一致。
2.2 Storybook 配置就绪但仅 1 个 stories 文件 P1
.storybook/main.ts + preview.ts 已配置 vue3-vite + a11y + essentials 插件，但全仓仅 loading.stories.ts 一个文件。ui-kit 有 33 个 shadcn-ui 原子组件 + 22 个业务封装组件 + 5 个领域 ui-kit 包，均无文档化。
优先为 ui-kit 高频组件（Button/Input/Select/Modal/Table/Form）补齐 stories，建立组件视觉规范和交互文档，降低团队沟通成本。可结合 AI 辅助批量生成 stories 骨架。
2.3 错误监控仅有 Web Vitals，缺 JS 异常上报 P1
comm/effects/monitor 包含 error-monitor 和 web-vitals，但 error-monitor 的实际上报链路不明确。大厂方案通常接入 Sentry/自研 APM，覆盖 JS 异常 + Promise rejection + 资源加载失败 + API 错误。
(1) 完善 error-monitor 的上报通道（接入 Sentry 或自研 APM 网关）；(2) 补充 window.onerror + unhandledrejection + error 事件捕获（资源加载失败）；(3) 在 RequestClient 的错误拦截器中自动上报 API 异常；(4) 上报数据携带 release 版本号便于版本回溯。
2.4 errorMessageResponseInterceptor 存在冗余分支 P2
preset-interceptors.ts 中 HTTP 500+ 分支与 default 分支都返回 internalServerError，逻辑重复。
合并 500+ 和 default 分支，或为不同 5xx 状态码映射更细粒度文案（502/503/504 网关类错误与 500 服务器内部错误区分提示）。
2.5 retry 缺少指数退避策略 P2
RequestClient 的 retryConfig 使用固定 retryDelay，在高并发失败场景下可能加剧服务端压力（惊群效应）。
增加指数退避 + 随机抖动选项：backoff: 'fixed' | 'exponential'，exponential 模式下 delay = baseDelay * 2^attempt + randomJitter。

三、性能提升

📍 现状评估：基础优化完备，缺极致压缩与缓存策略

已做：vendor 三分包（vue/element/vxe）、路由全懒加载、gzip 压缩、element-plus/vxe 按需引入、静态资源 immutable 长缓存、多阶段 Docker 镜像、HPA 自动伸缩、Lighthouse 性能预算门禁、visualizer 分析链路完整。Lighthouse 预算：FCP≤2s、LCP≤3s、CLS≤0.1、TBT≤300ms。

3.1 生产构建未 drop console，泄露风险 + 体积浪费 P0
conf/vite-config/src/config/application.ts 第 92-96 行，esbuild drop 配置中 'console' 被注释掉，仅 drop 'debugger'。生产环境保留了所有 console 日志，既有信息泄露风险（可能打印敏感数据），又增加产物体积。
取消注释，生产环境 drop ['console', 'debugger']。如果需要保留特定日志，可用 pure_funcs: ['console.log', 'console.info'] 保留 console.warn/error。
3.2 未启用 Brotli 压缩，gzip 可再降 15-20% P0
前端 vite-plugin-compression 仅启用 gzip（VITE_COMPRESS=gzip），nginx 也仅配置 gzip comp_level 6，未启用 brotli 模块。Brotli 对文本资源（JS/CSS/HTML）压缩率比 gzip 高 15-20%。
(1) 前端构建同时生成 gzip + brotli：compression({ algorithms: ['gzip', 'brotliCompress'] })；(2) nginx 安装 ngx_brotli 模块，配置 brotli on; brotli_types text/css application/javascript ...；(3) 或使用 brotli_static on 直接服务预压缩文件。
3.3 build target 过低，es2015 可提至 es2018+ P1
target: 'es2015'（ES6）会生成 polyfill 和降级代码。现代浏览器（Chrome 80+/Edge/Safari 14+）已全面支持 ES2018+（async/await/optional chaining/nullish coalescing），PMIS 系统用户群体通常为现代浏览器环境。
提升 build target 至 es2018 或 es2020，可减小产物体积 5-10%。配合 browserslist 配置精确控制兼容范围。
3.4 chunkSizeWarningLimit 偏高，掩盖超大 chunk 告警 P1
当前 chunkSizeWarningLimit: 2000（2MB），Rollup 默认 500KB。2MB 的阈值会让单个 chunk 超过 1MB 也不报警，掩盖了包体膨胀问题。
降低至 1000（1MB），配合 manualChunks 更细粒度拆分。对确实无法拆分的大包（如 vxe-table），在注释中标注豁免原因。
3.5 缺少图片压缩与字体子集化 P1
无 vite-plugin-imagemin 或类似图片压缩插件，无字体子集化（subsetting）处理。PMIS 项目中 project-web 有大量视图，可能包含较多图片资源。
(1) 引入 unplugin-imagemin 压缩 PNG/JPG/SVG；(2) 中文字体使用 font-spider 或 subset-font 按使用字裁剪，中文字体文件可从 5MB+ 降至 100KB 以内。
3.6 PWA 已配置但运行时关闭 P2
vite-plugin-pwa 插件代码存在但 VITE_PWA=false 关闭，globPatterns: [] 无缓存策略。对于 PMIS 这类高频使用的内部系统，PWA 的离线缓存可显著提升二次访问速度。
评估启用 PWA：配置 App Shell 缓存策略（precache 应用骨架），API 请求走 NetworkFirst（保证数据新鲜），静态资源走 CacheFirst。注意微前端场景下 Service Worker 的 scope 范围需匹配主应用。
3.7 importmap CDN 外置依赖关闭但插件驻留 P2
importmap 插件整套（含 html-minifier-terser、@jspm/generator、cheerio）默认禁用，vue/pinia 等仍打包进 vue-vendor。如果启用 CDN 外置，9 个子应用可共享同一份 vue/element-plus，显著减少总体积。
评估启用 importmap：将 vue/vue-router/pinia/element-plus 外置到 CDN，9 个子应用共享。对于微前端场景，这可避免每个子应用重复打包这些库（当前每个子应用 vue-vendor 约 80KB gzip × 9 = 720KB 冗余）。

四、体验改善

📍 现状评估：基础体验完善，微前端切换体验可优化

已做：nprogress 进度条、标签页拖拽 + keepAlive 缓存、SecureLS 加密持久化、i18n 延迟绑定、hover 预加载子应用、全屏/水印/锁屏功能。但微前端切换白屏、骨架屏缺失、错误边界薄弱等体验痛点仍存在。

4.1 微前端切换白屏问题 P0
Qiankun 切换子应用时，旧应用卸载 → 新应用加载 → 新应用挂载之间存在白屏间隙。虽然有 hover 预加载缓解首次加载，但已加载子应用切换时仍有可感知的白屏（尤其 project-web 这类重应用）。大厂方案通常有骨架屏或 loading 占位。
(1) 在 SubAppContainer 中增加骨架屏/loading 占位，监听 qiankun 的 beforeLoad/afterMount 生命周期切换显示状态；(2) 配合 prefetch 策略预加载常用子应用 JS；(3) 评估使用 keep-alive 缓存已激活子应用（qiankun 支持但需注意内存）。
4.2 缺少全局错误边界 P1
Vue 3 的 app.config.errorHandler 和 onErrorCaptured 未在子应用启动模板中统一配置。当某个子应用渲染异常时，可能导致整个微前端框架白屏，而非优雅降级到错误页。
(1) 在 createSubApp 工厂中统一注入 errorHandler，捕获后渲染错误 fallback 组件；(2) 在 SubAppContainer 增加 errorCaptured，子应用崩溃时显示"应用加载失败，请刷新"提示并提供重试按钮。
4.3 网络异常体验不够友好 P1
errorMessageResponseInterceptor 将错误转为 ElMessage 提示，但弱网/超时场景下用户体验差：消息一闪而过、无重试入口、列表页空白无反馈。
(1) 对列表页引入空状态/错误状态/重试组件（参考 vxe-table 的 empty 插槽）；(2) 对关键操作（提交/保存）失败后保留表单数据，提供重试按钮；(3) 网络断开时全局展示离线提示条。
4.4 registerLoadingDirective 参数不一致 P2
主应用调用 registerLoadingDirective 传 'loading' 字符串，子应用传 false，参数语义不一致，可能导致指令行为差异。
统一参数类型和语义，在 shared-auth 或 createSubApp 工厂中统一调用，消除手动传参差异。
4.5 骨架屏（Skeleton）缺失 P2
路由懒加载的页面组件加载期间无骨架屏，首屏和数据加载阶段用户看到空白。大厂方案通常有页面级骨架屏。
为高频访问页面（Dashboard、列表页）设计骨架屏组件，在 Suspense fallback 或路由组件 loading 配置中使用。

五、过度设计精简

📍 现状评估：部分插件配置维护成本高于收益

项目追求工程化全面性，引入了较多"以防万一"的配置，部分功能默认关闭但仍驻留代码和依赖，增加了维护成本和认知负担。

5.1 三套格式化工具并存 过度
ESLint 中 prettier 插件、@stylistic/stylelint-plugin、eslint-plugin-perfectionist 三套格式化工具并存，部分规则互相关闭（perfectionist 关闭与 prettier 冲突的规则，stylelint 也关 prettier 冲突项）。三套工具的规则协调成本高，新人理解门槛大。
统一格式化入口：Prettier 负责 JS/TS/Vue/JSON/MD 格式化，Stylelint 仅管 CSS/SCSS 语法规则（不用 stylistic），perfectionist 仅管 import 排序（不用格式化规则）。明确各工具职责边界，删除重叠配置。
5.2 archiver 每次构建生成 dist.zip 多余 过度
archiver: true 配置每次构建都生成 dist.zip，但 CI 已直接使用 dist/ 目录构建 Docker 镜像，zip 文件无人消费，徒增构建耗时。
确认 zip 消费方后决定：若无使用方则关闭 archiver；若用于离线包分发则仅在有 VITE_ARCHIVE=true 环境变量时生成。
5.3 rollup-plugin-node-polyfills 可能不必要 过度
全局 alias 了 buffer/process/stream/crypto 等 Node 内建模块。如果项目无 Node 内建依赖（纯浏览器运行的前端项目），这些 polyfill 徒增体积和构建耗时。
排查是否有依赖引用了 Node 内建模块（depcheck 或构建产物分析），若无则移除 node-polyfills 配置。
5.4 importmap 插件整套维护成本高但默认禁用 过度
importmap 插件含 @jspm/generator、cheerio、html-minifier-terser 等依赖，维护成本不低，但默认关闭（condition: isBuild && importmap，importmap 未传）。如果长期不启用，应移除以降低维护成本。
决策：要么启用（见 3.7 建议，微前端场景收益明显），要么移除。不要让"可能用到"的代码长期驻留。
5.5 license 注入每个 entry chunk 重复 过度
license 注入到每个 entry chunk，微前端多入口场景下重复注入相同 license 文本。
改为生成独立 LICENSE.txt 文件，或在主应用统一注入一次。
5.6 cspell 拼写检查投入产出比低 过度
cspell 配置了 ~50 个自定义词，对所有 */*.ts 和 README 执行拼写检查。对于中文为主的 PMIS 项目，拼写检查的主要价值在于变量名拼写正确性，但误报率高、自定义词库维护成本持续存在。
评估是否保留：如果团队无强制要求可降级为可选检查（不纳入 check 命令），或仅检查 commit message 而非全量代码。

六、工程质量补齐

📍 现状评估：规范配置齐全但门禁未落地，这是最大短板

TypeScript 严格模式全开（strict + noUncheckedIndexedAccess + verbatimModuleSyntax）、ESLint 18 模块 + 17 插件、Stylelint 四件套、commitlint 13 种 type——配置层面已对标大厂。但 lefthook 钩子全部注释、changesets 未初始化、测试无覆盖率门槛，导致规范形同虚设。

6.1 Lefthook 钩子全部注释，本地质量门禁失效 P0
lefthook.yml 中 pre-commit、pre-push、commit-msg 钩子全部被注释掉，仅保留 post-merge 自动 install。这意味着提交前不执行任何 lint/type-check/commit 校验，所有质量保障完全依赖 CI——而 CI 只在 PR 时触发，本地直接 push 到分支则无任何拦截。
立即启用 lefthook 钩子（取消注释），建议分阶段：(1) 先启用 commit-msg（commitlint 校验，最快见效）；(2) 再启用 pre-commit 的 lint-md/lint-vue/lint-js（仅对 staged 文件，--cache 加速）；(3) 最后启用 pre-push 的 type-check（耗时较长放 push 前）。如担心影响效率，可配置 {staged_files} 仅检查变更文件。
6.2 Changesets 依赖已引入但未初始化 P0
package.json 依赖 @changesets/cli + @changesets/changelog-github，但项目内不存在 .changeset/ 目录及配置文件，版本管理能力未落地。monorepo 多包版本管理没有 changesets 会非常混乱。
运行 npx changeset init 初始化配置，补充 .changeset/config.json，在 package.json 增加 changeset 和 version-packages 脚本。或如果确认不使用 changesets，则移除相关依赖减少误导。
6.3 测试无覆盖率门槛，业务应用几乎零单测 P0
34 个 .test.ts 集中在 comm/@core/base/shared/utils、comm/stores、comm/effects/request 等公共包，业务应用 apps/* 几乎无单测。Vitest 未配置 coverage provider 与阈值。E2E 仅 1 个 spec 5 个用例（chromium 单浏览器），断言宽泛（多处 if isVisible 软断言），用例硬编码 admin/admin123。
(1) 配置 vitest coverage：provider: 'v8'，设定公共包覆盖率阈值 80%、业务包逐步补齐；(2) 公共工具函数（utils/request/auth）优先补齐单测；(3) E2E 扩展到 chromium+firefox 双浏览器，去掉硬编码凭据改用环境变量，补充关键业务流（项目创建/审批流/消息发送）；(4) 考虑引入 @vitest/coverage-v8 + CI 上传覆盖率到 Codecov/Coveralls。
6.4 tsconfig 未配置 paths，IDE 跳转受限 P1
conf/tsconfig 各层配置均未设置 paths 路径别名，#/ 别名仅靠 Vite alias 解析。TypeScript 类型检查和 IDE 跳转/补全可能受限（虽然 vue-tsc 能配合 vite alias 工作，但纯 tsc 场景失效）。
在 tsconfig/base.json 中补充 paths 映射，与 Vite alias 保持同步。可使用 vite-tsconfig-paths 插件自动同步，避免双重维护。
6.5 缺少 PR 模板和 Issue 模板 P1
.github/ 仅有 workflows/frontend-ci.yml 一个 CI 文件，缺少 PR 模板和 Issue 模板。大厂开源项目标配 PULL_REQUEST_TEMPLATE.md + ISSUE_TEMPLATE/（bug/feature/question 分类）。
补充 .github/PULL_REQUEST_TEMPLATE.md（变更说明/测试方式/影响范围 checklist）和 .github/ISSUE_TEMPLATE/{bug_report,feature_request}.yml。
6.6 check-circular 仅 warn 不 fail P1
vsh check-circular 使用 circular-dependency-scanner 检测循环依赖，但仅 warn 不 fail。循环依赖是架构腐化的信号，应阻断构建。
在 CI 的 check 命令中改为 fail 模式。如果当前存在历史循环依赖，先标记允许列表（ignore pattern），新增量不允许引入循环依赖。
6.7 CI 缺少缓存优化 P2
frontend-ci.yml 的 lint→build→docker→deploy 四阶段，Docker 层有 gha 缓存，但 pnpm install 和 turbo build 的缓存策略不明确。
(1) 使用 pnpm/action-setup + actions/setup-node 缓存 pnpm store；(2) 配置 turbo 的 Remote Cache（可选自建或 Turbo Cloud）；(3) CI 中并行执行 check 和 build（build 依赖 check 通过可拆为两个 job）。
6.8 E2E 测试用例薄弱 P2
Playwright 仅 1 个 core-flows.spec.ts（登录成功/失败/导航/登出 5 用例），chromium 单浏览器，断言宽泛，凭据硬编码。对于 9 个子应用的 PMIS 系统覆盖严重不足。
(1) 扩展浏览器矩阵：projects: [chromium, firefox]；(2) 凭据改为 process.env.E2E_USER；(3) 补充各子应用核心流 E2E（项目管理/工作流审批/消息发送）；(4) 断言改用 expect(locator).toBeVisible() 替代 if isVisible。
