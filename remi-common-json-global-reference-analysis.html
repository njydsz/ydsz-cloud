一、整体态势评估

1.1 正面结论

✅ JSON 能力 100% 收敛于 remi-common-json
全项目 9 个业务模块、19 个 Maven 子模块、129 个 Java 源文件统一使用 RemiJson。Java 源码中零 com.fasterxml.jackson、com.google.gson、com.alibaba.fastjson、org.json 的直接引用。这是极高水平的依赖治理成果。
✅ 无重复造轮子
全项目未发现任何命如 JsonUtils、GsonUtils、JacksonUtils 的独立 JSON 工具类。所有 JSON 相关封装（如 RemiJsonRedisSerializer、JsonEncoder/JsonDecoder）都是对 remi-common-json 引擎的合理适配，而非重新实现。
✅ 无手写 JSON 字符串拼接
未发现任何 String.format("{\"key\":\"%s\"}", value) 或 StringBuilder 拼接 JSON 的模式。所有 JSON 操作均通过 API 完成，安全性高。
✅ 注解生态完全自闭环
remi-common-json 内置 27 个 Jackson 兼容注解。全项目所有 @JsonProperty、@JsonIgnore、@JsonFormat、@JsonPropertyOrder 等注解均来自 com.remisoft.common.json.annotation 包，无任何 Jackson 注解引用。
✅ 第三方 JSON 库排除机制完善
remi-common-feign（排除 OpenFeign/Resilience4j 传递的 Jackson）、remi-common-queue（排除 RocketMQ 传递的 fastjson/fastjson2）等模块通过 Maven exclusions 彻底阻断外部 JSON 库泄露。

1.2 核心不足

⚠️ 高级能力利用率偏低
remi-common-json 提供的 JSON Schema 验证、JsonView 视图过滤、JsonModule SPI 自定义序列化器、AutoType 安全检查等高级特性，仅被 1-2 个模块使用，存在显著的能力浪费。

四、规范不统一问题详析

4.1 Gateway 模块：toJson() + .getBytes() 冗余模式

remi-gateway 共 12 个 Java 文件中出现以下模式，应统一替换为 RemiJson.toJsonBytes()：

// ❌ 当前模式（出现在 12 个文件中） byte[] bytes = RemiJson.toJson(body).getBytes(StandardCharsets.UTF_8); // ✅ 推荐替代 byte[] bytes = RemiJson.toJsonBytes(body);

4.2 对象类型转换的多种写法

同样的 Map -> POJO 转换，项目中存在三种不同写法：

// 写法 A：toJson + fromJson 链式（literule, cronjob 中出现） RuleDefinition def = RemiJson.fromJson(RemiJson.toJson(ruleMap), RuleDefinition.class); // 写法 B：JsonMapper.convertValue（message 模块中使用） MessageRequest req = JsonMapper.getDefault().convertValue(arg, MessageRequest.class); // 写法 C：解析 Map 后手动 set（workflow 中大量出现） Map<String, Object> ext = RemiJson.parseMap(node.getExt()); flow.setXxx((String) ext.get("xxx"));

建议：提供 RemiJson.convertValue() 静态便捷方法并制定使用指引。

4.3 树 API 命名风格不一致

ObjectNode 同时提供了两种风格的 API：

// RemiJson 原生风格（小驼峰） ObjectNode obj = RemiJson.parseObject(json); String name = obj.getString("name"); int age = obj.getIntValue("age"); // FastJSON2 兼容风格 ObjectNode child = obj.getJSONObject("child"); // "JSON" 全大写 ArrayNode items = obj.getJSONArray("items");

这两种风格混用降低了 API 的一致性。建议保留原生风格为主，将 getJSONObject/getJSONArray 标记为 @Deprecated 并引导迁移。
