PMIS 自研工作流引擎采用 7+1 表极简设计（对标 Warm-Flow），以零第三方 BPMN 依赖的 DOM 解析器为核心，已覆盖审批流核心链路的 22 项能力，包括 4 种会签类型（或签/顺序/并行/票签）、10 种审批操作（通过/驳回/转办/委派/前加签/后加签/跳转/批量审批/撤回/催办）、双层事件机制（同步监听器 + 异步 Spring 事件）、多租户全链路、SPI 办理人解析（9 种类型）、版本管理、历史归档、审计轨迹与时间线。

对标国内主流引擎后，核心审批操作覆盖度约 80%，但在流程设计器、表单引擎、SLA 自动化、消息通知、效率分析五大领域存在明显差距。其中流程设计器与表单引擎为 P0 关键差距——所有竞品（含开源 Warm-Flow/FlowLong 和 SaaS 钉钉/飞书）均已标配可视化拖拽设计器与动态表单，而当前引擎仅有节点坐标存储接口，无实际设计器。

Top 3 行动项

  • 集成可视化流程设计器（前端）：引入 bpmn.js 或仿钉钉 SIMPLE 设计器，对接已有 updateNodeCoordinate / deploy / updateDefinition 接口 P0 / 2-3 周
  • 补全 SLA 自动化链路：接入已有 scheduler 模块的 JobHandler，实现到期自动催办 + 超时自动升级/自动通过/拒绝 P1 / 1-2 周
  • 实现抄送(CC)节点与消息通知通道：激活已有 FlowNodeType.CC(2) 枚举，对接站内信/邮件/企业微信推送 P1 / 1-2 周

    5核心能力差距分析

    P0 关键差距（阻塞核心使用场景）

    P0
    1. 可视化流程设计器缺失
    当前仅有 updateNodeCoordinate 坐标存储接口和 model_value 字段（CLASSICS/MIMIC），无实际设计器前端。所有竞品（含开源 Warm-Flow 的 jar 集成设计器、FlowLong 的仿飞书设计器、ruoyi-vue-pro 的双设计器）均已标配可视化拖拽设计器。流程定义只能通过手写 BPMN XML 或 JSON 完成，非开发人员无法使用。[1][2][3]
    建议：前端引入 bpmn.js（标准 BPMN 设计器）或基于 LogicFlow/AntV X6 自研仿钉钉 SIMPLE 设计器，对接已有 deploy/updateDefinition/updateNodeCoordinate 三个后端接口。可参考 ruoyi-vue-pro 的双设计器模式（SIMPLE 日常 + BPMN 复杂场景）。
    P0
    2. 表单引擎缺失
    当前仅有 form_path（前端路由）和 form_custom（Y/N）两个字段，无表单设计器、无动态表单、无字段级权限控制。钉钉支持按节点设置字段可编辑/只读/隐藏[7]，飞书提供计算公式、外部数据源关联选项、智能显示条件等最丰富的表单控件[8]，ruoyi-vue-pro 和 JeecgBoot 均有动态表单设计器[4][6]。表单与流程的联动（如表单字段决定审批路由、按节点控制字段权限）是审批系统的核心体验。
    建议：P0 阶段先实现表单字段权限（按节点配置可编辑/只读/隐藏），在 pmis_flow_node 增加 form_fields_config JSON 字段；P1 阶段引入轻量表单设计器（可基于 FormMaking/VForm 等开源方案），实现拖拽式表单设计与流程绑定。

    P1 重要差距（影响用户体验）

    P1
    3. SLA 超时自动化链路缺失
    pmis_flow_task 表已有 due_at 字段和 listOverdue 查询，但仅支持 timeoutTask 手动标记。无到期自动催办、无超时自动升级、无超时自动通过/拒绝。FlowLong 支持超时自动通过或拒绝 + 自动提醒（短信/邮件/微信/钉钉，可设提醒次数）[2]，JeecgBoot 支持超时提醒推送[5]，行业惯例为 24h 自动提醒、48h 升级[11]。项目已有 scheduler 模块的 JobHandler 机制可复用。
    建议：在 scheduler 模块新增 FlowTimeoutJobHandler，定时扫描 due_at < now AND task_status = 'PENDING' 的任务，按配置策略执行：催办通知 → 升级上级 → 自动通过/拒绝。在 pmis_flow_node 增加 sla_config JSON 字段（含 timeout_minutes/action/reminder_count）。
    P1
    4. 消息通知通道未对接
    urge() 方法仅返回被催办人 ID 列表，未实际发送通知。无站内信、邮件、企业微信/钉钉推送。FlowLong 支持短信/邮件/微信/钉钉多通道通知[2]，钉钉/飞书均支持 App 推送通知[7][8]。项目已有 message 模块（@EnableAsync 异步消息）可复用。
    建议：定义 FlowNotificationService 接口，在 FlowEventListener 的 onTaskCreated/onTaskUrged 回调中调用，通过已有 message 模块发送站内信 + 邮件。预留企业微信/钉钉 Webhook 扩展点。
    P1
    5. 抄送(CC)节点未实现
    FlowNodeType.CC(2) 枚举已定义，但 DefaultFlowAdvancer 和 FlowTaskService 中无抄送节点处理逻辑——不生成抄送通知、不跳过、不阻塞流程。钉钉/飞书/企业微信均将抄送节点作为标配[7][8][9]，FlowLong 有"沟通"能力[2]。
    建议：在 DefaultFlowAdvancer.advance() 中增加 CC 节点判断：遇到 CC 类型节点时，生成抄送记录（复用 pmis_flow_audit_log 或新增 pmis_flow_cc_record 表），触发通知事件后自动跳过，不阻塞主流程。
    P1
    6. 子流程未实现
    FlowNodeType.SUBPROCESS(7) 枚举已定义，BpmnXmlParser 可解析 callActivity，但 DefaultFlowAdvancer 无子流程启动/等待/回跳逻辑。FlowLong 支持同步/异步子流程 + 结束自动回跳主流程[2]，飞书支持子流程自动触发[8]，Flowable 原生支持 Call Activity[10]。
    建议：在 DefaultFlowAdvancer 增加子流程处理：遇到 SUBPROCESS 节点时，通过 WorkflowFacade.startProcess() 启动子流程实例，在 pmis_flow_instance 增加 parent_instance_id / parent_node_code 字段记录父子关系，子流程完成时通过事件回调推进主流程。
    P1
    7. 审批人为空时无兜底处理
    当 ROLE/DEPT/POSITION 展开后实际办理人为空时，任务会卡在 PENDING 状态无法推进。钉钉提供"自动通过/转交给管理员/指定人员审批"三种策略[7]，这是避免流程卡死的关键兜底机制。
    建议：在 FlowTaskServiceImpl.createTask() 的 resolveAssignee 之后增加空值检查：若展开结果为空，按 pmis_flow_node.ext 中配置的 emptyStrategy（AUTO_PASS / TRANSFER_ADMIN / ASSIGN_SPECIFIED）处理。
    P1
    8. 减签操作缺失
    已实现前加签（countersignBefore）和后加签（countersignAfter），但缺少减签——从会签任务中移除某个审批人。Warm-Flow、FlowLong、ruoyi-vue-pro 均支持加减签[1][2][3]。
    建议：在 FlowTaskService 增加 countersignRemove(FlowTaskOperateDTO dto) 方法：从 pmis_flow_user 中标记指定用户为 SKIPPED，若移除后 approveCount 需同步调整。

    P2 增强差距（提升竞争力）

    P2
    9. 审批效率分析看板不足
    已有 nodeDurationStats（节点平均耗时）和 listOverdue（超期任务），但缺少审批效率看板。飞书的效率诊断看板支持单量/平均耗时/代批率/瓶颈分析（团队+个人双视角）[8]，是行业标杆。
    建议：基于已有 pmis_flow_his_task 聚合统计，新增 API：审批单量趋势、平均审批时长、代批率（非本人完成比例）、节点瓶颈排名（耗时 Top N）。前端用 ECharts 渲染。
    P2
    10. 包容网关语义不完整
    FlowNodeType.INCLUSIVE(5) 已定义且 isJoinNode 包含该类型，但 resolvePassSkips 未区分包容网关与排他网关的语义差异——包容网关应允许多条匹配的出边同时通过（类似并行），而当前排他网关互斥逻辑会截断。FlowLong 和 Flowable 均完整支持包容网关[2][10]。
    建议：在 resolvePassSkips 中增加节点类型判断：CONDITION 排他互斥（break），INCLUSIVE 包容不 break（允许多条匹配），其余节点取全部匹配。
    P2
    11. 并行网关 join 逻辑边界场景
    当前 join 聚合通过 countPendingByNode(instanceId, nodeCode) 判断是否有未完成任务，但仅按 nodeCode 统计可能遗漏跨分支场景。此外缺少对"分支已完成但 join 节点未激活"的显式状态跟踪。
    建议：引入 pmis_flow_token 令牌表或在 pmis_flow_instance.variable 中维护分支完成计数器，确保 join 聚合的精确性。
    P2
    12. 动态流程/自由流程缺失
    当前流程定义必须预先部署，运行时不可动态修改。FlowLong 支持追加（发起后动态追加节点处理人）+ 动态构建任务 + 暂存待审[2]，ruoyi-vue-pro 支持自由指定下一环节审批人[3]，钉钉支持发起人自选审批人[7]。
    建议：P2 阶段实现"发起人自选审批人"（在 FlowStartProcessDTO 增加 nodeAssignees Map 参数，启动时按节点注入），满足灵活审批场景。
    P2
    13. 会签并发安全
    incrementFinished 使用 SQL UPDATE SET approve_finished = approve_finished + 1 虽然是原子操作，但缺少完成条件判断的并发保护——两个线程同时读取 approve_finished=2（阈值=3），各自+1 后都判断未达阈值，导致多推进一次。Flowable 使用乐观锁（version 字段）解决此问题[10]。
    建议：在 doParallelPass / doVotePass 推进判断处加分布式锁（Redis SET NX EX，项目已有幂等锁基础设施），或使用 SELECT ... FOR UPDATE 行锁确保 approve_finished 读取-判断-推进的原子性。
    P2
    14. 已阅/沟通能力缺失
    无"已阅"（标记已查看但不审批）和"沟通"（向他人征询意见但不转移审批权）能力。FlowLong 支持已阅 + 沟通[2]。
    建议：在 FlowTaskService 增加 markRead(taskId, userId) 和 communicate(taskId, targetUserId, comment) 方法，复用 pmis_flow_audit_log 记录。
    P2
    15. 流程模板库缺失
    当前预置 4 个业务流定义（立项/合同变更/销项/请假），但无通用模板库。飞书提供 100+ 模板覆盖 10+ 行业[8]。
    建议：沉淀 PMIS 领域常用流程模板（采购审批/费用报销/出差申请/用印申请等），支持一键导入。
    P2
    16. 历史数据归档策略优化
    当前任务完成后立即归档到 pmis_flow_his_task，但无定时清理策略和分区优化。ruoyi-vue-pro 支持定时归档 30 天前数据 + 按 tenant_id HASH 分区[3]。
    建议：在 scheduler 模块增加 FlowHistoryArchiveJobHandler，定期将已完成实例+历史任务迁移到冷存储表或归档库，保持热表性能。

    6SWOT 分析

    优势 (Strengths)

    • 7+1 表极简设计，零第三方 BPMN 依赖，维护成本低
    • BPMN 2.0 XML 解析能力（多数轻量引擎仅 JSON），兼容标准流程图
    • 4 种会签类型完整覆盖，含票签权重
    • 双层事件机制（同步+异步），SPI 扩展点设计良好
    • 9 种办理人路由类型，含 SELF_SELECT/MULTI_LEADER
    • 多租户全链路、provider_trace_id 链路追踪
    • Facade 门面模式隔离业务，110 个单元测试覆盖核心逻辑

    劣势 (Weaknesses)

    • 无可视化流程设计器，非开发人员无法配置流程
    • 无表单引擎，表单与流程联动能力缺失
    • SLA 仅手动标记，无自动化超时处理
    • 无消息通知通道，催办仅返回列表
    • 抄送/子流程枚举已定义但未实现
    • 会签并发安全缺乏分布式锁保护
    • 审批效率分析仅基础统计，无看板

    机会 (Opportunities)

    • 项目已有 scheduler 模块和 message 模块可直接复用
    • 前端已集成 ECharts，可快速搭建效率看板
    • 已有 FlowAssigneeResolver SPI 接口，业务模块可注入实现
    • 国产权信创趋势下，自研引擎无 License 风险
    • PMIS 项目管理领域流程相对标准化，模板可复用性高

    威胁 (Threats)

    • Warm-Flow/FlowLong 社区活跃迭代快，功能差距可能扩大
    • 钉钉/飞书审批免费且体验优秀，客户可能要求对接而非自建
    • 若流程设计器/表单引擎迟迟不补，业务方可能绕过工作流模块
    • 会签并发问题在高并发场景下可能引发数据不一致

    7优化路线图

    P0 第一阶段：补全核心可用性（2-4 周）
    目标：让非开发人员能够可视化设计流程并配置表单权限，达到"可用"门槛
    • 集成可视化流程设计器（bpmn.js 或 LogicFlow 仿钉钉 SIMPLE 设计器），对接 deploy/updateDefinition/updateNodeCoordinate 2-3 周
    • 表单字段权限：pmis_flow_node 增加 form_fields_config 字段，按节点配置字段可编辑/只读/隐藏 3-5 天
    • 审批人为空兜底处理：createTask 中增加空值检查 + emptyStrategy 策略 2-3 天
    • 包容网关语义修正：resolvePassSkips 区分 CONDITION(互斥) vs INCLUSIVE(多匹配) 1 天
    P1 第二阶段：补全审批体验链路（3-4 周）
    目标：SLA 自动化、消息通知、抄送/子流程/减签全面落地，达到"好用"水平
    • SLA 自动化：scheduler 新增 FlowTimeoutJobHandler，实现到期催办 + 超时升级/自动通过/拒绝 1-2 周
    • 消息通知通道：定义 FlowNotificationService，对接 message 模块发站内信+邮件，预留企微/钉钉 Webhook 1 周
    • 抄送(CC)节点实现：DefaultFlowAdvancer 增加 CC 处理逻辑，生成抄送记录+通知后自动跳过 3-5 天
    • 子流程实现：advance 增加 SUBPROCESS 处理，parent_instance_id 字段，子流程完成事件回调推进主流程 1 周
    • 减签操作：FlowTaskService 增加 countersignRemove 方法 2-3 天
    • 会签并发安全：doParallelPass/doVotePass 增加分布式锁或行锁 2-3 天
    P2 第三阶段：差异化与竞争力提升（4-6 周）
    目标：效率分析看板、动态流程、表单设计器、流程模板库，达到"领先"水平
    • 审批效率分析看板：基于 his_task 聚合，新增单量趋势/平均耗时/代批率/瓶颈排名 API + ECharts 前端 1-2 周
    • 轻量表单设计器：引入 VForm/FormMaking 等开源方案，实现拖拽式表单设计与流程绑定 2-3 周
    • 发起人自选审批人：FlowStartProcessDTO 增加 nodeAssignees 参数，启动时按节点注入 3-5 天
    • 已阅/沟通能力：markRead + communicate 方法 2-3 天
    • 流程模板库：沉淀 PMIS 领域 8-10 个常用模板，支持一键导入 1 周
    • 历史数据归档策略：scheduler 新增 FlowHistoryArchiveJobHandler 定期归档 3-5 天
    • 并行网关 join 令牌机制优化：引入分支完成计数器确保精确聚合 1 周

    8差异化策略

    策略层含义具体行动
    Catch-up 追赶 竞品普遍已有但本项目缺失的能力 流程设计器、表单引擎、SLA 自动化、消息通知、抄送、子流程、减签——P0/P1 阶段全部补齐
    Differentiate 差异化 本项目已有优势或可领先的领域 BPMN 2.0 XML 双模式部署（Warm-Flow/FlowLong 仅 JSON）、PMIS 领域流程模板库（项目管理专用审批场景沉淀）、provider_trace_id 全链路追踪（微服务可观测性优势）
    Innovate 创新 蓝海机会，竞品未覆盖 AI 审批辅助（项目已有 Agent 模块，可接入智能路由决策/风险预警/自动审批建议）、项目-流程联动（基于 PMIS 预算/合同/成本数据驱动审批条件路由，非通用 OA 可实现）
