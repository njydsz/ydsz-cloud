🔧 核心能力差距分析

✓ 已完成 — 本节 3 项 P0 级优化（Seata 分布式事务 / WebSocket 实时推送 / CI 质量门禁）均已落地，含 12 个后端测试类 + 5 个前端测试文件。
1. 分布式事务未启用 — Seata 依赖引入但 @GlobalTransactional 缺失
P0 · 必须修复

现状：Seata 2.0.0 依赖已引入 pom.xml，deploy/seata/ 有部署配置，但代码中未使用任何 @GlobalTransactional 注解。跨服务写操作（如商机转立项、执行模块发消息、对账冲销）仅依赖本地事务 + Feign 调用 + 补偿模式。

大厂标准：关键跨服务写路径必须使用 Seata AT 模式或 TCC/Saga 模式保证最终一致性。阿里、美团等大厂的订单/财务类系统均强制要求分布式事务覆盖。[1]

风险：Feign 调用失败后上游已提交、下游未执行，导致数据不一致（如立项已创建但流程未启动、发票已开具但消息未发送）。

影响范围：商机转立项 / 合同签订 → 流程启动 / 对账冲销
预估工时：3-5 人日
识别 5-8 个关键跨服务写路径，添加 @GlobalTransactional；在 deploy/seata/ 下完善 Nacos 配置注册；编写分布式事务回滚测试验证 AT 模式 undo_log 正常。
2. 无实时通信能力 — 缺失 WebSocket 推送
P0 · 必须修复

现状：全系统无 WebSocket 实现。通知中心 (notification) 和消息中心 (message) 均为拉取式 API；告警派发 (AlertDispatch) 依赖定时轮询；驾驶舱报表无实时刷新。

大厂标准：企业级管理系统必须具备实时推送能力：通知即时到达、告警秒级触达、看板数据实时刷新、多人协作状态同步。WebSocket 是大厂标配的实时通信方案。[2][3]

影响：用户需手动刷新查看新通知；告警延迟可达轮询间隔 (5s-60s)；驾驶舱数据非实时影响决策效率。

影响范围：通知中心 / 告警中心 / 驾驶舱 / 工单协作
预估工时：5-8 人日
在 gateway 或 notification 模块集成 Spring WebSocket + STOMP；前端封装 useWebSocket composable 自动重连 + 心跳；告警/通知通过 WebSocket 实时推送到前端消息中心组件。
3. Elasticsearch 已配置但未集成 — 全文检索能力缺失
P1 · 高优先级

现状：docker-compose.base.yml 中配置了 Elasticsearch 8.15，但后端代码中无 ES 客户端集成，无索引定义，无同步逻辑。所有搜索依赖 PostgreSQL LIKE 查询。

大厂标准：项目管理系统的项目/合同/任务/审计日志等核心实体应支持全文检索、组合过滤、高亮匹配。ES 是大厂搜索标配，通过 Canal/Logstash 同步 MySQL/PG 数据到 ES。

影响：大数据量下 LIKE 查询性能急剧下降；无法支持中文分词、同义词、纠错等高级搜索；审计日志检索效率低。

影响范围：全局搜索 / 审计日志 / 项目/合同检索
预估工时：8-12 人日
引入 spring-data-elasticsearch；为项目/合同/任务/审计日志建立 ES 索引；通过 RocketMQ 延迟消息或定时任务同步增量数据到 ES；前端添加全局搜索栏 (Cmd+K 快捷键)。
4. 文件处理能力薄弱 — 缺失病毒扫描/分片上传/在线预览
P1 · 高优先级

现状：file 模块仅实现 MinIO 上传/下载/元数据管理，无病毒扫描、无分片上传、无在线预览、无文件类型限制校验。

大厂标准：企业级文件服务必须包含：ClamAV 病毒扫描、大文件分片上传 + 断点续传、Office/PDF 在线预览、文件类型白名单、文件大小限制。

影响：恶意文件上传安全风险；大文件上传失败后无法续传；用户需下载后才能查看附件内容。

影响范围：合同附件 / 交付物 / 发票凭证 / 项目文档
预估工时：6-10 人日
集成 ClamAV daemon 做异步病毒扫描；前端实现分片上传组件 (slice + MD5 秒传)；集成 kkFileView 或 OnlyOffice 实现在线预览；file 模块添加文件类型白名单 + 大小限制配置。
5. 无定时报表生成与分发机制
P1 · 高优先级

现状：所有报表 (驾驶舱/高管看板/EVM/利用率) 均为按需拉取式 API，无定时生成、无邮件/钉钉分发、无报表订阅机制。

大厂标准：关键运营报表应支持定时生成 (日/周/月)、自动推送到邮箱/钉钉/企微、支持订阅与自定义推送规则。

影响：管理层需手动登录系统查看报表；无主动数据洞察推送；报表生成高峰期可能影响在线查询性能。

影响范围：驾驶舱 / 高管看板 / EVM / 利润报表
预估工时：5-8 人日
在 scheduler 模块新增 ReportScheduleJob；报表生成后通过 message 模块发送邮件/钉钉；前端添加报表订阅页面 (选择报表 + 频率 + 接收人)；利用已有 EasyExcel 导出能力生成 PDF/Excel 附件。
6. 无数据一致性校验机制
P2 · 中优先级

现状：模块间数据一致性 (如发票总额 vs 回款总额、预算 vs 实际成本、WBS 进度 vs 工时完成率) 依赖人工对账页面查看，无定时自动校验 + 告警。

大厂标准：关键财务数据应有定时对账任务自动校验一致性，差异超阈值自动告警。已有 ReconcileService (日对账/月对账) 但未接入定时调度 + 告警链路。

影响范围：财务对账 / 预算执行 / EVM 数据准确性
预估工时：3-5 人日
在 scheduler 注册 DailyReconcileJob 调用已有 ReconcileService；差异超阈值时调用 AlertDispatchService 派发告警；前端对账页面增加差异标红 + 一键重算功能。

🎨 细节体验差距分析

✓ 已完成 — 本节 9 项 P1 级优化（ES 全文搜索 / 文件增强 / 定时报表 / 骨架屏 / 批量操作 / 虚拟滚动 / 审计 Diff / 自定义仪表盘 / 表单草稿/收藏/内联编辑）均已落地，含 13 个测试文件。
7. 缺失骨架屏 — 内容区白屏闪烁
P1 · 高优先级

现状：页面加载时仅有全局 NProgress 进度条 + ElLoading 遮罩，内容区在数据返回前为空白状态，视觉上出现"白屏闪烁"。

大厂标准：内容密集型页面 (列表/卡片/详情) 应使用骨架屏 (Skeleton) 占位，消除白屏感、提升感知性能。Element Plus 已提供 el-skeleton 组件但项目未使用。[4]

封装 SkeletonCard / SkeletonTable / SkeletonDetail 三个骨架组件；在 PageLayout 中增加 loading="skeleton" 模式；列表页首次加载使用骨架屏，翻页使用遮罩。
8. 列表页无批量操作
P1 · 高优先级

现状：所有列表页仅支持单行操作 (编辑/删除/审批)，vxe-table 的 selection 能力未启用。用户处理 50 条工时审批需点击 50 次。

大厂标准：列表页必须支持批量操作：批量审批、批量导出、批量删除、批量状态变更。vxe-table 原生支持 checkbox 列 + 批量操作工具栏。

在 PageLayout 中增加 selection 模式配置；封装 BatchToolbar 组件 (选中数提示 + 操作按钮组)；为工时审批/任务分配/发票管理/风险处理等高频列表添加批量操作。
9. 大数据量表格无虚拟滚动
P1 · 高优先级

现状：vxe-table 已引入但业务页面未配置虚拟滚动 (scroll-y)。工时明细、审计日志、对账记录等页面在数据量超 500 行时可能出现卡顿。

大厂标准：1000+ 行表格必须启用虚拟滚动，DOM 节点数固定在可视区域 + 缓冲区，性能不随数据量增长而下降。[5]

为审计日志、工时明细、对账记录等高频大数据表格配置 vxe-table scroll-y；封装虚拟滚动配置预设；性能测试验证 5000 行渲染 FPS ≥ 55。
10. 数据变更历史无 UI 呈现 — 审计日志仅简单列表
P1 · 高优先级

现状：后端有完善的 4 类审计日志 (操作/登录/敏感/导出)，但前端审计页面仅为简单时间线列表，无字段级 diff 可视化、无实体变更时间轴。

大厂标准：关键业务实体 (合同/预算/发票) 应支持"变更历史"标签页，展示字段级修改前后对比 (before/after diff)，类似 Jira 的 Issue History。

后端 OperationLog 扩展 beforeData/afterData JSON 字段；前端封装 EntityHistoryDrawer 组件，渲染字段级 diff (绿色新增/红色删除/黄色修改)；合同/预算/发票详情页增加"变更历史"Tab。
11. 数据导出无进度反馈 — 同步导出导致 UI 冻结
P2 · 中优先级

现状：数据导出为同步调用，后端生成 Excel/PDF 后直接返回文件流。大数据量导出 (如全量工时、全量审计日志) 时前端长时间无响应。

大厂标准：大数据量导出应改为异步任务：提交导出请求 → 后端异步生成 → WebSocket/轮询通知完成 → 下载中心下载。

后端 ReportExportService 改为异步生成 + 存储到 MinIO；前端导出按钮改为提交任务 → 显示进度条 → 完成后通知下载；新增"下载中心"页面管理导出文件。
12. 仪表盘不可定制 — 固定布局
P2 · 中优先级

现状：Dashboard 和 Cockpit 页面为固定布局，所有角色看到相同的 KPI 卡片和图表。项目经理、财务、高管关注的指标完全不同。

大厂标准：仪表盘应支持拖拽布局、组件选择、个性化配置 (类似 Grafana 面板)。至少提供 3-4 种角色预设布局。

引入 vue-grid-layout 实现拖拽布局；后端新增 DashboardLayoutDO 存储用户自定义布局 JSON；提供 PM/财务/高管/资源经理 4 种预设布局模板。
13. 表单无草稿/自动保存 — 长表单数据丢失风险
P2 · 中优先级

现状：所有表单 (立项申请、合同录入、预算编制) 均为即时提交模式，无草稿保存、无自动保存、无页面刷新恢复。

大厂标准：长表单应支持自动保存草稿 (localStorage + 后端草稿表)、页面刷新后恢复未提交内容、定时保存提示。

封装 useFormDraft composable (防抖自动保存到 localStorage)；后端新增草稿表支持按 entity_type + user_id 存储；FormDialog 增加"存为草稿"按钮和草稿恢复提示。
14. 无收藏/快速访问机制
P2 · 中优先级

现状：用户每次使用系统都需通过完整菜单导航。无收藏功能、无最近访问记录、无快捷入口。

大厂标准：支持收藏常用页面/常用项目、显示最近访问记录、首页快捷入口卡片。

后端新增 UserFavoriteDO 和 RecentAccessDO；前端 Layout 侧边栏顶部增加收藏区；Dashboard 首页增加"最近访问"和"我的收藏"卡片；浏览器 Cmd+K 快捷搜索。
15. 无行内编辑 — 简单字段更新需打开弹窗
P2 · 中优先级

现状：所有字段编辑均需点击"编辑"打开 FormDialog 弹窗，修改后提交关闭。对于状态变更、指派人员、日期调整等简单操作，交互成本高。

大厂标准：状态、指派人、优先级、日期等字段应支持表格内行内编辑 (inline edit)，点击即改、回车确认。

vxe-table 启用 edit-config (trigger: click, mode: cell)；为 WBS 任务状态/指派人、工时审批状态、风险等级等字段配置行内编辑组件；保存时调用单字段更新 API。

16. CI 缺失质量门禁 — SonarQube/安全扫描未集成到流水线
P0 · 必须修复

现状：CI 流水线 (backend-ci.yml / frontend-ci.yml) 仅执行 build + test，未集成 SonarQube 静态分析、OWASP dependency-check、ZAP 安全扫描。Checkstyle 和 JaCoCo 插件在 pom 中配置但 skip=true。然而 README 和 code-quality.md 声称这些工具"已集成到 CI"，存在文档与实现不一致。[6][7]

大厂标准：CI 必须包含质量门禁 (Quality Gate)：静态分析 + 安全扫描 + 覆盖率检查，门禁不通过禁止合并。SonarQube 质量门禁是 DevSecOps 标配。

影响范围：全部代码质量保障
预估工时：3-5 人日
CI 新增 quality job：mvn verify 启用 Checkstyle + JaCoCo → SonarQube scan → OWASP dep-check (CVSS≥7 失败) → 前端 eslint + vue-tsc 严格模式；PR 合并必须质量门禁通过；修正 README 与实际不一致的描述。
17. 无 CD 流水线 — 部署依赖手动操作
P1 · 高优先级

现状：CI 仅完成 build + test，镜像构建/推送/部署均需手动执行 Ansible/Helm。Argo Rollouts 配置已就绪但未与 CI 串联。

大厂标准：CI/CD 应一体化：代码合并 → 自动构建镜像 → 推送镜像仓库 → Argo Rollouts 自动灰度发布 → Prometheus SLO 验证 → 全量/回滚。

CI 增加 build-push job (docker build + push to registry.cn-hangzhou.aliyuncs.com)；Argo Rollouts ImageUpdater 自动监听镜像新版本触发灰度；部署后自动运行健康检查 + 冒烟测试。
18. 契约测试与性能测试未纳入 CI
P1 · 高优先级

现状：Postman 契约测试集合 (32 端点) 和 JMeter 性能基线脚本 (6 场景) 已存在但未纳入 CI 流水线，仅手动运行。

大厂标准：契约测试应在每次 PR 中自动运行 (Newman CLI)；性能基线应定期 ( nightly or weekly ) 执行，结果与基线对比，回归 >10% 告警。

CI 增加 contract job (newman run pmis-contract.postman_collection.json)；新增 nightly 性能测试 cron job (JMeter headless + 结果上传 Grafana)；性能回归 >10% 自动创建 Issue。
19. 仓库存在调试残留文件
P2 · 中优先级

现状：ydsz-pmis-backend/logs/ 下存在 .bat / .ps1 / .err / .out 等调试脚本和输出文件，疑似本地调试残留，应加入 .gitignore 或清理。

大厂标准：代码仓库应保持整洁，日志/临时文件通过 .gitignore 排除，CI 中增加 repository cleanliness 检查。

完善 .gitignore 排除 logs/*.err / logs/*.out / *.bat / *.ps1；执行 git rm --cached 清理已跟踪的调试文件；CI 增加 lint 检查禁止提交日志文件。
20. 前端业务页面测试覆盖不足
P2 · 中优先级

现状：前端 37 个测试文件中，页面组件测试仅 5 个 (Dashboard/Cockpit/Chaos/Executive/OrchestrationPipeline)。约 40 个业务页面 (system/execution/project 等模块的 index.vue) 无组件级单元测试。API 层测试仅覆盖 5 个模块。

大厂标准：每个业务页面应有基础组件测试 (渲染验证 + 交互验证 + 权限验证)；API 层 100% 覆盖；关键页面有 E2E 覆盖。

按模块优先级补充测试：P1 执行管理 (15 页) → P2 项目管理 (6 页) → P3 系统管理 (9 页)；每个页面至少 3-5 个测试用例 (渲染/搜索/表单提交/权限)；API 层补全剩余 7 个模块。

21. 自研工作流引擎的维护风险
P1 · 高优先级

现状：自研轻量级 BPMN 流程引擎 (BpmnXmlParser / FlowAdvancer / FlowAssigneeResolver)，8 个流程表 + 110 个单元测试。功能覆盖流程定义/实例/任务/历史/跳转/审计。

大厂标准：大厂通常使用成熟的 Flowable/Activiti/Camunda 引擎，经过大规模生产验证。自研引擎在复杂场景 (会签/或签/委派/加签/退回任意节点/子流程/定时边界事件) 可能存在边界缺陷。

评估：当前自研引擎满足基本审批需求 (项目立项审批流)，但若未来需要复杂流程编排 (如多分支并行审批、超时自动审批、流程版本迁移)，自研引擎的投入产出比下降。

短期保持自研引擎但补充边界场景测试 (会签/或签/超时/退回)；中期评估迁移到 Flowable 的成本收益；若业务复杂度增长则逐步替换，保留 PmisWorkflowFacade 接口不变实现平滑切换。
22. 无 BFF/聚合层 — 前端多次请求组装复合视图
P2 · 中优先级

现状：前端加载一个复合页面 (如项目详情含立项+合同+WBS+EVM) 需分别调用 4-5 个后端 API，在网络延迟叠加下首屏加载较慢。

大厂标准：通过 BFF (Backend for Frontend) 层或 Gateway 聚合接口，一次请求返回复合数据，减少网络往返。

在 gateway 或 execution 模块新增聚合 Controller (如 /api/v1/project-detail/{id} 一次返回立项+合同+WBS概览+EVM摘要)；前端封装 useAggregateData composable 并行请求 + 客户端聚合作为过渡方案。
23. 无 API 版本管理策略
P2 · 中优先级

现状：所有 API 统一在 /api/v1/ 下，但无版本协商机制、无废弃策略、无向后兼容性约束文档。

大厂标准：API 应有明确的版本管理策略 (URL path versioning / Header versioning)，旧版本有 deprecation notice + sunset date，新版本保持向后兼容至少 2 个版本。

制定 API 版本管理规范 (docs/api/ 下新增 api-versioning.md)；破坏性变更需新增 /api/v2/ 并保留 v1 至少 6 个月；在 OpenAPI 文档中标注 deprecated 接口 + sunset header。
24. 无多租户架构 — SaaS 化前置条件缺失
P3 · 远期规划

现状：单租户设计，所有数据共享同一 schema，无 tenant_id 隔离字段。若未来需要 SaaS 化运营，改造成本极高。

大厂标准：SaaS 级 PMIS 应支持多租户隔离 (行级 tenant_id 或 schema 级隔离)，租户间数据完全隔离，支持租户级配置 (品牌/流程/权限)。

若 SaaS 化在路线图中，尽早为核心表添加 tenant_id 字段 + MyBatis-Plus 租户拦截器；若保持私有化部署则标注为非目标，避免过度设计。
